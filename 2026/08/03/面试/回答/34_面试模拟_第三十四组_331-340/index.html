面试模拟 - 第三十四组（331-340题）

基于简历项目经历，模拟面试回答

331. 亿级裁判文书如果只用MySQL条件筛选和LIKE查询，怎么升级为结构化筛选、全文检索、分面统计和语义检索结合的系统？

回答：

这个问题其实很有现实意义，因为很多项目起步时就是MySQL一把梭，量大了才发现扛不住。我会分几个阶段来升级：

第一阶段：从LIKE到全文检索

MySQL的LIKE %keyword%不走索引，亿级数据下就是全表扫描。第一步是换成MySQL自带的全文索引（FULLTEXT），用MATCH AGAINST做布尔模式搜索，性能提升至少一个数量级。但MySQL全文索引对中文支持有限，所以这只是过渡方案。

第二阶段：引入Elasticsearch做全文检索+分面统计

把裁判文书同步到ES，利用它的倒排索引和分词器（比如IK分词器）处理中文。ES的优势在于：

  • 结构化筛选： 案由、法院级别、审判年份、法官等字段可以建为结构化字段，用filter精确过滤
  • 全文检索： 支持布尔查询、短语查询、模糊匹配，比LIKE强太多
  • 分面统计： 按年份、案由、法院层级做聚合统计，一个aggs查询搞定，MySQL得写一堆子查询

第三阶段：引入Milvus做语义检索

这是最关键的升级。关键词搜索有一个硬伤——用户输入的是"夫妻离婚财产怎么分"，但裁判文书里写的是"婚姻关系存续期间共同财产分割"，关键词不匹配就搜不到。所以需要做语义检索：

  • 把裁判文书按段落切分，用embedding模型（比如text-embedding-v3）向量化，存入Milvus
  • 用户输入案情描述，同样转成向量，在Milvus里做近似检索
  • 召回结果后和ES的全文检索结果做融合排序

具体架构：

用户输入 → Query Rewrite（改写案情描述）
           ↓
     ES全文检索（精确匹配案由、法条等）
     Milvus语义检索（匹配案情相似性）
           ↓
     结果合并 → Reranker重排序 → 返回Top-K

第四阶段：分面+语义联合查询

用户可以在界面选择"案由：离婚纠纷、年份：2024、法院：北京市一中院"，这些作为结构化filter先筛掉一大片，再在剩下的结果里做语义检索。这样既保证精确性，又保证召回率。

这套方案我在法律助手项目中做过类似的设计，只是规模没到亿级，但架构思路是通用的。

332. 1亿条1024维float32向量大约需要多少存储，如何通过向量精度、量化和索引方案降低存储成本？

回答：

先算一下账：

原始存储：

  • 1亿条 × 1024维 × 4字节（float32）= 4096亿字节 ≈ 381GB
  • 加上ID字段（int64，8字节）和元数据字段，总存储大约在400GB左右
  • 如果建索引，IVF类的索引需要额外约10-20%的存储，HNSW索引需要额外约30-50%

所以裸存就是400GB左右，加上索引奔着500-600GB去了。在生产环境中，这个成本确实不低。

降成本方案：

1. 降低向量精度（float32 → float16 / int8）

float32降到float16，精度减半，存储直接砍半，从381GB降到190GB。在召回率测试中，float16的精度损失不到1%，几乎无感。如果再降到int8，存储降到95GB，但召回率会下降3-5%，需要根据业务场景权衡。

2. 量化——PQ（Product Quantization）

PQ把向量切成若干子段，每个子段用聚类中心索引代替原始向量。比如切分成M段，每段用k个聚类中心b比特表示，存储从1024维×4字节降到M×b比特。

  • M=64, k=256（8比特）时，存储降到64字节/条，1亿条仅需6GB
  • 这属于有损压缩，召回率会下降，但通过调整参数（M和k）可以在存储和召回率之间找平衡

3. 索引方案选择

不同索引方案对存储和召回率的影响：

  • IVF_FLAT： 标准索引，存储和原始向量差不多，但聚类后搜索效率高
  • IVF_PQ： 结合PQ量化，存储大幅降低，适合亿级数据
  • IVF_SQ8： Scalar Quantization，每个维度用1字节（int8）存储，存储降到原始1/4，召回率损失小
  • HNSW： 图索引，召回率最高，但存储额外增加30-50%，亿级数据用HNSW成本很高

4. 分片和分层检索

不一定要把所有向量存到一张表。可以按年份、案由等维度分片，用户查询时先定位到相关分片，只在分片内检索，这样每个分片的向量量级就小多了。

综合推荐方案：

对于亿级裁判文书场景，我会用 IVF_SQ8 + 分片 的组合：

  • IVF_SQ8把存储降到约100GB
  • 按年份分片（比如10个分片），每个分片10GB
  • 配合GPU推理，延迟控制在可接受范围内
  • 召回率可以做到95%以上

333. 长裁判文书应该怎么切分和向量化，才能根据用户输入的案情召回真正相似的案例，而不只是事实表面相似？

回答：

这个问题问得很细，核心挑战在于：裁判文书很长（可能上万字），但用户关心的只是其中一段案情描述，如果整篇文书作为一个向量，语义会极度稀释，召回效果很差。

我的切分策略：

裁判文书有固定的结构——首部、当事人信息、诉讼请求、事实与理由、法院查明、本院认为、判决结果。结构就是天然的切分边界。

我会按语义段落切分，而不是按固定字符数：

  • 法院查明部分： 这是案情事实的核心，单独切出来，每段500-800字
  • 本院认为部分： 这是法院的法律推理过程，单独切出来
  • 诉讼请求+事实与理由： 这是原告视角的案情描述，单独切
  • 判决结果部分： 单独存，但向量化时权重可以降低，因为这部分是结论不是案情

向量化策略：

  1. 案情向量（主向量）： 用"法院查明"部分的段落做向量，因为这是最客观的案情描述
  2. 法条向量（辅助向量）： 文书引用的法条，单独提取并向量化，用于匹配法律问题类型
  3. 案由标签： 作为结构化字段，不参与向量化，但用于筛选

如何避免"表面相似"？

很多案件表面相似——都是"离婚"或"借贷"，但事实细节天差地别。我的做法是：

方案一：Query改写+细节抽取

用户输入"我借了20万给朋友，他没打借条，现在不还钱"，不要直接搜全文。用大模型改写，提取关键要素：

  • 法律关系：民间借贷
  • 证据类型：无书面借条
  • 争议焦点：还款义务认定

改写后，用这些要素组合成搜索query，同时做结构化筛选和语义检索。

方案二：多路召回+重排序

  • 一路按案由结构化筛选（精确匹配法律类型）
  • 一路按案情语义检索（匹配事实细节）
  • 一路按争议焦点关键词检索（匹配法律问题）

三路结果合并，用Reranker重新打分。Reranker能看到完整的query和chunk，能判断"这个案子的案情细节是否和用户描述一致"。

方案三：事实要素提取

在向量化之前，用大模型提取文书的"事实要素"——借贷金额、担保方式、利息约定、还款期限等，然后把要素结构化成字段存储。用户查询时，同样提取要素进行结构化匹配，精度更高。

334. 如果把判例检索封装成Agent Tool，应该如何定义工具描述、输入参数、返回字段、结果数量以及失败返回格式？

回答：

这个我很有经验，因为政策补贴系统里我们就把政策检索封装成了Agent Tool。核心原则是：让大模型能正确理解并调用，返回结构要清晰，错误处理要完备。

工具定义（以LangChain Tool格式为例）：

工具名称：search_case_precedent
工具描述：
  用于检索中国裁判文书网中的历史判例。
  当用户询问某个案件类型、案由、法律问题或相似案情时，
  调用此工具检索相关判例。
  适用于：合同纠纷、侵权、离婚、劳动争议、借贷纠纷等常见案由。
  不适用于：查询法律法规条文本身（请用search_legal_provision工具）。

输入参数：

参数名 类型 必填 说明
case_type string 否 案由，如"离婚纠纷"、“民间借贷纠纷”
keyword string 否 关键词，案情描述或法律问题
court_level string 否 法院层级：基层法院/中级法院/高级法院/最高院
year int 否 裁判年份，如2024
province string 否 省份/地区
page_size int 否 返回数量，默认5，最大10

关键设计点： 参数尽量用可选，不要让大模型凑齐所有参数才能调用。跟用户说"帮我找一下北京地区的离婚纠纷判例"，只传province和case_type也能查到结果。

返回字段：

{
  "total_count": 128,
  "cases": [
    {
      "case_id": "（2024）京01民终1234号",
      "title": "张某与李某离婚纠纷二审民事判决书",
      "court": "北京市第一中级人民法院",
      "judgment_date": "2024-03-15",
      "case_type": "离婚纠纷",
      "summary": "双方因感情不和分居满两年，法院认定感情确已破裂，准予离婚。共同财产分割方案为...",
      "key_facts": "婚后购置房产两套，无子女，无共同债务",
      "legal_basis": ["民法典第1079条", "民法典第1087条"],
      "judgment": "准予离婚，房产各得一套",
      "relevance_score": 0.92
    }
  ]
}

结果数量控制：

默认返回5条，因为大模型上下文有限，给太多也看不完。如果用户说"多找一些"，可以允许page_size调到10。超过10条建议返回摘要列表，让用户选感兴趣的再展开。

失败返回格式：

{
  "error": true,
  "error_type": "NO_RESULTS",
  "message": "未找到匹配的判例，请尝试：1. 扩大案由范围 2. 减少筛选条件 3. 使用更通用的关键词",
  "suggestions": {
    "expanded_query": "离婚纠纷",
    "similar_case_types": ["婚姻家庭纠纷", "同居关系析产纠纷"]
  }
}

为什么要这样设计失败返回？ 大模型看到NO_RESULTS不会直接死心，它会根据suggestions调整参数重新调用，或者告诉用户"目前没有完全匹配的判例，但类似的案由有这些，要不要看看？"体验比干巴巴的"没查到"好很多。

335. Word文书生成中，"结构化字段+固定模板"和"Agent生成代码+沙箱执行"两种方案各有什么优缺点，应该如何选型？

回答：

这个问题我实际遇到过，法律助手项目里就需要生成法律意见书和合同审查报告。两种方案我都调研过，各有适用场景。

方案一：结构化字段+固定模板

思路是预定义好Word模板，用占位符标记需要填充的位置，后端把结构化数据填入，生成最终文档。

优点：

  • 稳定可靠，生成的文档格式完全可控
  • 运行速度快，毫秒级生成
  • 不需要沙箱环境，安全风险低
  • 法律文书这种格式严格、结构固定的场景非常合适

缺点：

  • 灵活性差，模板之外的格式需求改起来成本高
  • 如果字段不是预定义的，就得频繁改模板
  • 表格的行数、列数不固定时处理起来麻烦

方案二：Agent生成代码+沙箱执行

思路是让大模型根据用户需求写一段Python代码（比如用python-docx库），在沙箱环境里执行，生成Word文档。

优点：

  • 灵活度极高，用户想要什么格式都能生成
  • 支持动态表格、图表、复杂排版
  • 适合需要高度定制化的场景

缺点：

  • 不稳定，大模型生成的代码可能跑不通
  • 安全风险，沙箱逃逸、资源滥用等问题需要防范
  • 生成速度慢，代码生成+执行+纠错可能耗时十几秒
  • 调试成本高，代码跑飞了得重新生成

我的选型建议：

用方案一的情况：

  • 文书格式固定，比如判决书、法律意见书、通知函
  • 内容结构化程度高，字段可预定义
  • 对格式稳定性要求高，不能出错

用方案二的情况：

  • 用户需要高度定制化格式，比如投标书、项目方案
  • 模板数量太多维护不过来
  • 内容结构不固定，比如用户想生成一个包含各种图表的数据报告

我们在法律助手项目中的实际做法：

混合方案。 对于标准法律文书（合同审查报告、法律意见书），用方案一，模板预定义好，LLM填充结构化字段。对于用户自定义的文书（比如"帮我把这个案子写一份分析报告，要包含案情摘要、法律分析、胜诉概率预测"），用方案二，但加了限制：只允许调用固定的python-docx API，不开放文件读写和网络请求，沙箱用Docker容器隔离。

336. 你参与过的本地模型部署具体使用什么模型、GPU和量化方案？支持多少并发，显存、KV Cache和吞吐量如何配置？

回答：

我在法律助手项目中做过本地模型部署，主要部署的是Qwen3-32B，用于法律问答生成。

硬件配置：

  • GPU：单张A100（80GB显存）
  • 模型：Qwen3-32B（参数量321亿）

量化方案：

我们用了QLoRA微调+4bit量化推理的组合。Qwen3-32B如果全精度加载，需要64GB显存（32B×2字节，bf16格式），加上KV Cache和中间激活，单卡A100勉强但很紧张。所以我们用GPTQ做4bit量化，模型权重从64GB降到16GB，配合LoRA权重（约2GB），总显存占用约20GB。

量化方案对比：

方案 显存占用 推理速度 质量损失
bf16（全精度） ~64GB 基线 无
8bit（GPTQ） ~32GB 快10% 几乎无感
4bit（GPTQ） ~16GB 快20% 可接受，困惑度增加约1-2
4bit（AWQ） ~16GB 快25% 比GPTQ略好一点

我们选4bit GPTQ，因为显存省得最多，而且质量损失在可控范围内。

并发和吞吐量配置：

  • 最大并发数： 8个并发请求（考虑了显存上限）
  • KV Cache配置： 每个请求最大上下文2048 tokens，KV Cache使用page attention（vLLM的机制），8个并发下约占用8GB显存
  • 单次推理延迟： 首token延迟约300ms，生成速度约40 tokens/s（输入512 tokens，输出512 tokens的情况下）
  • 吞吐量： 8个并发下，约320 tokens/s

部署框架：

我们用的是vLLM做推理框架，搭配FastAPI对外提供服务。vLLM的PagedAttention机制让KV Cache管理高效很多，支持Continuous Batching，GPU利用率高。

优化技巧：

  1. 显存预留： 给KV Cache预留了20GB，剩下的给模型权重和中间激活
  2. 请求排队： 超过8个并发时，请求进入队列，不直接拒绝
  3. 动态batch： vLLM的continuous batching让不同长度的请求可以一起推理，提高GPU利用率
  4. 预热： 服务启动后先发几个预热请求，让GPU进入稳定状态，避免首请求特别慢

337. 你这两个项目系统架构是怎么设计的

回答：

我参与的两个项目是法律助手和政策补贴智能匹配系统，架构设计思路不同，因为面向的业务场景不一样。

法律助手——RAG系统架构：

这是一个典型的RAG问答系统，核心是"知识库检索+LLM生成"。

用户端（Vue3 + Element Plus）
      ↓ HTTP/WebSocket
后端（FastAPI + asyncio）
      ↓
  ┌──────────────────────────────┐
  │         LangGraph工作流        │
  │  Query Rewrite → 精确检索 →    │
  │  语义检索 → 结果合并 → Reranker│
  │  → 生成回答 → 答案校验          │
  └──────────────┬───────────────┘
                 ↓
  ┌──────────────┴───────────────┐
  │       数据层                   │
  │  MySQL（结构化数据/法条原文）    │
  │  Milvus（向量索引）             │
  │  Redis（缓存/会话管理）         │
  └──────────────────────────────┘
                 ↓
  ┌──────────────┴───────────────┐
  │       模型层                   │
  │  Qwen3-32B（本地部署，生成）    │
  │  text-embedding-v3（向量化）    │
  │  bge-reranker-v2-m3（重排序）   │
  │  Qwen-plus（复杂推理兜底）      │
  └──────────────────────────────┘

关键设计决策：

  • 用LangGraph编排工作流，而不是简单的Chain，因为需要条件路由和错误重试
  • 两路检索（精确+语义）互补，精确检索处理法条编号等确定性查询，语义检索处理开放性问题
  • Reranker做最后一道过滤，确保给LLM的上下文质量高

政策补贴系统——多Agent系统架构：

这是一个多Agent协作系统，核心是"Agent分工+工作流编排"。

用户端（Vue3 + TypeScript）
      ↓ HTTP
网关层（API Gateway，路由分发）
      ↓
  ┌──────────────────────────────┐
  │     Supervisor Agent（主控）   │
  │     理解用户意图，分派任务       │
  └──────┬──────┬──────┬─────────┘
         ↓      ↓      ↓
  ┌────────┐┌────────┐┌──────────┐
  │企业画像 ││政策匹配 ││材料审核   │
  │Agent   ││Agent   ││Agent     │
  │(采集企业││(匹配政策││(审核申请  │
  │ 信息)   ││ 条件)   ││ 材料)    │
  └────────┘└────────┘└──────────┘
         ↓      ↓      ↓
  ┌──────────────────────────────┐
  │       数据层                   │
  │  Neo4j（政策知识图谱）          │
  │  MySQL（企业信息/业务数据）      │
  │  Redis（缓存/会话/状态）        │
  └──────────────────────────────┘

关键设计决策：

  • 用LangGraph管理Agent之间的状态流转，每个Agent是一个节点
  • 内置知识图谱（Neo4j）存储政策实体关系，8类实体、12种关系、500+政策、3000+条件节点
  • 企业画像Agent负责采集企业信息，匹配准确率92%以上，响应时间<1.5秒

338. 你认为你的项目的亮点是什么

回答：

两个项目各有亮点，我说几个印象最深的：

法律助手项目的亮点：

1. 检索召回率从68%提升到94%

这不是靠单一技术实现的，而是组合拳：Query Rewrite解决口语化问题→精确检索解决法条编号匹配→语义检索解决同义表达→Reranker做最后一轮筛选。每一步都贡献了效果，叠加起来效果就很明显。

2. 离线可用率100%

法律场景对可用性要求很高，不能因为网络问题律师就查不到法条。我们把核心模型（Qwen3-32B 4bit量化）和向量数据库都部署在本地，断网也能用。这在企业级RAG项目里其实不多见，大部分方案还是依赖云端API。

3. LLM幻觉控制

法律场景不能容忍编造法条。我们设计了"双校验"机制：先让LLM基于知识库生成回答，再用一个独立的校验模型判断答案是否和知识库一致，不一致就拒绝输出。这个机制把幻觉率降到了很低。

政策补贴系统项目的亮点：

1. 多Agent协作的完整落地

不是概念演示，是真正上线跑的业务系统。Supervisor Agent + 3个子Agent（企业画像、政策匹配、材料审核）分工明确，Supervisor Agent负责理解用户意图并分派任务，子Agent各司其职。这个架构在企业级应用中很有参考价值。

2. 政策知识图谱

构建了8类实体、12种关系、500+政策和3000+条件节点的知识图谱。政策匹配不靠关键词硬匹配，而是通过在知识图谱中游走、逐层筛选条件来实现，匹配准确率92%以上。

3. 企业画像采集完整率95%以上

企业信息采集不仅仅是OCR扫描营业执照，而是多源数据融合——工商信息、税务信息、社保信息、知识产权信息，通过Agent自动采集和校验，采集完整率95%以上。

两个项目共通的亮点：

工程化落地能力强。 两个项目都是Docker Compose部署，有完整的CI/CD流程，有监控告警，有日志收集。不是实验室demo，是真正能跑在生产环境的产品。

339. 你这个项目设计了哪些技术点

回答：

从两个项目里提炼一下，我梳理了几个核心的技术点：

1. RAG多路检索与融合排序

法律助手项目中，不依赖单一检索方式。而是做精确检索（法条编号、条款号精确匹配）+ 语义检索（Milvus向量相似度）+ 关键词检索（ES全文检索）三路并行，结果用Reranker重排序。这个方案的好处是各种类型的查询都有对应的检索方式覆盖。

2. 查询改写（Query Rewrite）

用户说"离婚财产怎么分"，不能直接拿去搜，因为法律文书写的是"婚姻关系存续期间共同财产分割"。我们设计了一个Prompt让LLM把口语化问题改写为法律检索表达，同时保留原始事实。这个改写对召回率影响很大。

3. 多Agent协作与状态管理

政策补贴系统里，用LangGraph实现了多Agent的工作流编排。每个Agent工作在一个共享状态图上，Supervisor Agent根据当前状态决定下一步派发到哪个子Agent。状态管理是核心难点——子Agent执行过程中出错了怎么办、超时了怎么办、返回的数据格式不对怎么办，这些都需要在LangGraph的状态机里定义好fallback逻辑。

4. 知识图谱驱动的政策匹配

政策匹配不是简单的"关键词命中"，而是在知识图谱中做条件游走。比如"科技型中小企业"这个政策，它有多个条件：企业注册时间、营收规模、研发投入占比、知识产权数量等。每个条件在知识图谱中是一个节点，Agent从根节点出发，逐层游走判断企业是否满足条件。这个比纯RAG的匹配方式准确很多。

5. 本地化大模型部署与量化

Qwen3-32B用4bit量化部署在单卡A100上，支持8个并发请求。这个过程中踩了不少坑——KV Cache怎么配置、batch size怎么调、量化后的精度损失如何评估，这些都是工程化的实践经验。

6. 知识图谱+向量数据库的混合存储

法律助手用Milvus存向量，政策补贴系统用Neo4j存知识图谱。两个系统有不同的数据特点：法律数据适合向量检索（语义相似度高），政策数据适合图结构（条件分支多、关系复杂）。选型的时候是根据数据特点决定的。

340. 如果想优化还可以使用什么Agent架构

回答：

如果让我重新设计政策补贴系统的Agent架构，或者做下一代版本，我会考虑几个方向：

1. Orca架构——分层规划+执行分离

当前架构是Supervisor+子Agent的扁平结构，任务稍微复杂一点，Supervisor的Prompt就变得很重。Orca架构的思路是：规划层和执行层分离。规划层只负责拆解任务、制定计划，执行层只负责执行具体工具调用。这样规划层的Prompt可以很专注，执行层的工具调用也更清晰。

2. Plan-and-Execute（计划-执行模式）

当前的Agent是"边想边做"（ReAct），遇到复杂任务时可能会反复横跳。Plan-and-Execute是先让Agent生成一个完整计划（Plan），然后按计划执行。如果执行过程中发现计划有问题，可以回退到Plan阶段修改计划。这种模式特别适合政策性补贴这种步骤多、条件分支复杂的场景。

3. 引入记忆管理模块

当前Agent只有短期记忆（对话上下文），没有长期记忆。如果引入记忆管理模块，比如Mem0或MemGPT的方案，Agent可以记住：

  • 企业的历史申请记录和偏好
  • 用户常问的政策类型
  • 之前匹配过的条件组合

下次同企业再来咨询时，Agent不需要重新采集所有信息，直接从记忆里调取，体验会好很多。

4. 多Agent的通信优化

当前Agent之间通过共享状态通信，其实有点笨重。可以考虑用消息队列做异步通信：Agent A完成工作后，把结果发到消息队列，Agent B订阅了相关主题就能收到。这样Agent之间解耦，可以独立扩缩容，高并发场景下更灵活。

5. Mirror Agent——自我反思机制

增加一个"反思Agent"，它不是直接回答用户问题，而是观察其他Agent的回答质量，给出改进建议。比如政策匹配Agent推荐了某个政策，反思Agent会检查：这个政策是否真的匹配、是否有更优的政策被遗漏了、匹配理由是否充分。相当于给系统加了一层质量保障。

6. 评估驱动的Agent迭代

这是偏工程化的方向。建立一个Agent行为评估数据集，包含各种用户查询和期望的Agent行为路径。每次Agent架构改动后，用这个数据集自动评估，看Agent的决策是否正确、工具调用是否合理。这样迭代有数据支撑，而不是凭感觉改。
