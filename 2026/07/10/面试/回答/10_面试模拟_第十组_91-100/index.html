面试模拟 - 第十组（91-100题）

基于简历项目经历，模拟面试回答

91. 该怎么解决多agent之间交流会出现信息丢失的情况，哪些情况会出现，怎么解决？

回答：

信息丢失的典型场景：

1. 上下文截断丢失
Agent A传给Agent B的上下文太长，超过B的输入窗口，后面的信息被截断。

2. 格式转换丢失
Agent A输出JSON格式，Agent B期望自然语言，转换过程中丢失细节。

3. 状态覆盖丢失
Agent A和Agent B同时写入同一个状态字段，后写的覆盖先写的。

4. 异步时序丢失
异步执行时，Agent A的结果还没返回，Agent B已经开始执行，用了旧状态。

解决方案：

场景 解决方案
上下文截断 设计上下文压缩节点，只传递关键信息，而不是全部原始数据
格式转换 统一Agent间通信格式，用结构化schema而不是自然语言
状态覆盖 用LangGraph的checkpoint机制，每次状态变更都原子化
异步时序 设置依赖关系，确保上游Agent完成后再触发下游

政策补贴系统中的实践：
我们给每个Agent的输出定义了标准schema（Pydantic模型），Agent间传递的是结构化数据而不是自由文本，从根源上避免了格式转换丢失。同时用LangGraph的状态图确保执行顺序，避免时序问题。

92. 大模型词表这一块，为什么会用字节BPE这个词表，说一下你的理解？

回答：

BPE（Byte Pair Encoding，字节对编码）的核心思想是从字符级别出发，通过合并高频相邻对来构建词表。

为什么用BPE：

1. 解决OOV问题
传统按词分词，遇到词表外的词就无法处理。BPE从字节/字符出发，任何词都能拆解成已知的子词单元。

2. 平衡词表大小和序列长度

  • 字符级：词表小但序列长，训练慢
  • 词级：序列短但词表大，稀疏词学不好
  • BPE子词级：两者平衡

3. 处理多语言
中文、英文、代码可以共用一套词表，BPE自动学习不同语言的切分粒度。

字节级BPE的优势：
Qwen等模型用的是字节级BPE，直接在UTF-8字节上做合并，好处是：

  • 词表更紧凑（256个基础字节+合并规则）
  • 天然支持任何语言和特殊字符
  • 不需要预分词

在项目中的体现：
法律文本中有很多专业术语（如"不可抗力"、“连带责任”），BPE能自动把这些高频术语作为整体编码，减少token消耗，提升推理效率。

93. 词表是越大越好么？

回答：

不是，词表大小需要平衡。

词表大的优缺点：

优点 缺点
序列更短，推理更快 Embedding层参数多，显存占用大
罕见词有独立表示 低频词训练不充分，表示质量差
减少分词碎片化 模型参数量增加

词表小的优缺点：

优点 缺点
Embedding层参数少 序列更长，推理更慢
每个token都能充分训练 需要更多子词组合，可能丢失语义

平衡点在哪里：

  • 一般3万-15万是主流范围
  • Qwen用15万词表，支持中英文混合
  • LLaMA用3.2万词表，英文为主

实际考量：
在我们的法律助手中，Qwen的15万词表对中文法律术语覆盖很好，"不可抗力"这类术语能被整体编码，token数比小词表模型少30%+，这对长文档处理很有帮助。

94. 假设一个场景，我要知道这个公司，这些产品线，近几年的情况，做一个总结，你的rag怎么做？

回答：

这是一个典型的多实体、多维度、时间序列查询场景。

我的RAG设计：

1. 查询理解与分解
用LLM把用户问题分解为多个子查询：

  • 子查询1：该公司基本信息（行业、规模、资质）
  • 子查询2：该公司产品线列表
  • 子查询3：各产品线近几年的业绩数据

2. 多路检索策略

子查询 检索方式 数据源
公司信息 知识图谱查询 Neo4j公司实体
产品线 知识图谱+向量检索 Neo4j关系+Milvus
业绩数据 结构化查询+向量检索 数据库+文档

3. 时间维度处理

  • 在知识图谱中，产品线节点关联年份属性
  • 向量检索时，在metadata中过滤时间范围
  • 按年份排序，构建时间线

4. 结果聚合与摘要
把检索到的分散信息聚合，用LLM按结构生成总结：

  • 公司概况
  • 各产品线介绍
  • 近3年发展趋势
  • 关键指标变化

关键优化：

  • 用企业画像Agent预加载公司基础信息，减少重复检索
  • 时间范围用metadata过滤，而不是纯语义检索，更精确

95. 你的知识图谱数据库是什么语言做的，是基于python脚本写的么？你查库也是这个语言么？

回答：

图数据库选择：Neo4j

为什么用Neo4j：

  • 成熟稳定，社区活跃
  • 支持Cypher查询语言，比Gremlin更直观
  • Python驱动完善（neo4j库）
  • 可视化工具好用，方便调试

技术实现：

环节 技术
数据库 Neo4j（Java实现）
数据入库 Python脚本，用neo4j驱动
查询接口 Python FastAPI封装
图谱构建 Python脚本，解析政策文档

查询方式：

cypher
MATCH (p:Policy)-[:HAS_CONDITION]->(c:Condition)
WHERE c.name CONTAINS '高新技术'
RETURN p.name, c.description

Python端用neo4j驱动执行Cypher查询，返回结构化结果。

架构设计：
Neo4j作为图存储层，上层用Python FastAPI封装REST API，其他服务通过HTTP调用图谱查询服务，解耦了语言依赖。

96. 你用的大模型怎么从库里进行查找和获取的，整个回答过程是怎样的？

回答：

完整调用链路（法律助手为例）：

用户提问 → 问题理解 → 检索调度 → 向量检索 → 重排序 → 答案生成 → 溯源输出

详细步骤：

1. 问题理解
用户输入"劳动合同解除的赔偿标准是什么"
→ LLM提取意图和关键词：劳动法、解除合同、经济补偿

2. 检索调度
根据意图判断走哪条检索路径：

  • 法律条款查询 → 向量检索Milvus
  • 知识图谱查询 → Neo4j图遍历
  • 混合查询 → 两者并行

3. 向量检索

  • 用text-embedding-v3把query向量化
  • 在Milvus中检索top-20相似chunk
  • 相似度阈值过滤（>0.7）

4. 重排序
用Cross-Encoder对top-20重排序，选出top-5

5. 答案生成
把top-5 chunk作为context，拼接prompt：

你是法律顾问，根据以下法条回答用户问题。
Context: {chunk1} {chunk2}...
Question: {user_query}

6. 溯源输出
从chunk metadata中提取法条编号，附在答案后面

耗时分布：

  • 向量检索：100ms
  • 重排序：200ms
  • LLM生成：1-2s
  • 总计：<3s

97. 召回的chunk是按照什么顺序做凭借传给模型的

回答：

召回chunk的排序直接影响答案质量，我们用的是多因素加权排序。

排序策略：

1. 重排序得分（权重最高）
经过Cross-Encoder重排序后的得分，这是语义相关性的最强信号。

2. 位置信息

  • 标题chunk优先于正文chunk
  • 章节开头的chunk优先于中间的

3. 时间新鲜度
政策类文档会更新，新版本的chunk优先于旧版本。

4. 元数据匹配度
如果query提到了具体法条编号，包含该编号的chunk优先。

拼接顺序：
[最相关的chunk] → [次相关的chunk] → [补充信息chunk]

实际做法：

python

按重排序得分降序排列

chunks.sort(key=lambda x: x.rerank_score, reverse=True)
取top-5拼接

context = "\n\n".join([c.text for c in chunks[:5]])

效果对比：

  • 随机排序：准确率78%
  • 按向量相似度排序：准确率85%
  • 重排序后排序：准确率91%

排序策略对最终答案质量影响很大，这是我们召回率能到94%的关键因素之一。

98. 介绍一下transformer架构，decoder的流程

回答：

Transformer的核心是自注意力机制，让模型能关注到序列中任意位置的信息。

整体架构：

  • Encoder：把输入编码成上下文表示
  • Decoder：基于上下文自回归生成输出

Decoder流程（以GPT为例，只有Decoder）：

1. 输入嵌入
token → Embedding向量 + 位置编码

2. 自注意力计算

  • Q、K、V矩阵：输入向量分别乘以三个权重矩阵
  • 注意力分数：Q和K做点积，得到每个位置的相关性分数
  • 缩放：除以√d_k防止梯度消失
  • 掩码：用因果掩码（Causal Mask），只关注前面的token
  • 加权求和：用注意力分数对V加权求和

3. 前馈网络（FFN）
两层全连接网络，中间用激活函数（GELU）

4. 残差连接 + 层归一化
每层都有残差连接，防止梯度消失

5. 重复N层
GPT-3有96层，Qwen3-32B有64层

6. 输出层
最后的隐藏状态 → 线性层 → Softmax → 预测下一个token

为什么Decoder能生成文本：
每次预测一个token，把预测结果作为下一步输入，自回归生成完整序列。

99. 说一下机器学习，KNN，决策树，K-MEANS

回答：

KNN（K近邻）

  • 类型：监督学习，分类/回归
  • 原理：找距离最近的K个邻居，投票决定类别
  • 特点：简单直观，无需训练，但预测慢
  • 应用：我们用KNN做过简单的FAQ匹配，问题向量找最近的FAQ

决策树

  • 类型：监督学习，分类/回归
  • 原理：按特征逐步分裂，构建树状决策规则
  • 特点：可解释性强，容易过拟合
  • 改进：随机森林（多棵树投票）、XGBoost（梯度提升）
  • 应用：我们用决策树做过用户意图分类的baseline

K-Means

  • 类型：无监督学习，聚类
  • 原理：随机选K个中心点，迭代分配样本到最近中心，更新中心
  • 特点：简单高效，但需要预设K值
  • 应用：我们用K-Means对政策文档做聚类，发现潜在的政策类别

对比总结：

算法 类型 优点 缺点
KNN 监督 简单，无需训练 预测慢，维度灾难
决策树 监督 可解释，处理混合特征 容易过拟合
K-Means 无监督 快速聚类 需要预设K，对初始值敏感

在大模型时代，这些传统算法在特征工程、数据预处理、baseline对比中仍有价值。

100. 解释一下CNN，RNN，LSTM

回答：

CNN（卷积神经网络）

  • 核心：卷积核提取局部特征
  • 优势：参数共享，平移不变性
  • 应用：图像识别、文本分类
  • 在NLP中：TextCNN用于短文本分类，提取n-gram特征

RNN（循环神经网络）

  • 核心：隐藏状态传递时序信息
  • 优势：处理变长序列，捕捉时序依赖
  • 问题：长序列梯度消失，无法捕捉长距离依赖
  • 应用：早期机器翻译、语言模型

LSTM（长短期记忆网络）

  • 核心：门控机制解决RNN的梯度消失
  • 三个门：遗忘门、输入门、输出门
  • 优势：能捕捉长距离依赖
  • 应用：机器翻译、文本生成、序列标注

对比：

模型 核心机制 长距离依赖 并行计算
CNN 卷积核 弱（局部） 强
RNN 隐藏状态 弱（梯度消失） 弱（顺序计算）
LSTM 门控机制 较强 弱（顺序计算）

与Transformer的关系：
Transformer的自注意力机制解决了RNN/LSTM的所有痛点：

  • 长距离依赖：直接关注任意位置
  • 并行计算：所有位置同时计算

所以在大模型时代，Transformer几乎完全取代了RNN/LSTM，但理解它们对掌握深度学习演进很重要。
