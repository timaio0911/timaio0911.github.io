面试模拟 - 第八组（71-80题）

基于简历项目经历，模拟面试回答

71. Agent里上下文窗口怎么设计，上下文太长怎么处理？

回答：

上下文窗口设计是Agent系统的核心问题，我在政策补贴系统中遇到过上下文超长的情况，主要通过以下策略处理：

第一，滑动窗口机制：

我设计了一个滑动窗口，只保留最近N轮对话。比如保留最近5轮对话，早期对话会被压缩或丢弃。这样既能保证上下文连贯性，又能控制token数量。

第二，摘要压缩：

对于历史对话，用大模型生成摘要，替代原始对话内容。比如前10轮对话可能有2000token，压缩成摘要后只有200token，但保留了关键信息。

第三，关键信息提取：

用正则或NLP提取关键实体和意图，存储在结构化字段中。比如企业名称、行业类型、申请条件等，这些信息单独存储，不受上下文窗口限制。

第四，分层存储：

短期记忆用上下文窗口，中期记忆用Redis缓存，长期记忆用数据库持久化。根据信息的重要性和时效性选择存储层级。

在项目中的实现：

政策补贴系统的多轮对话中，我会把企业基本信息提取出来存入State，后续Agent直接读取State，不需要每次都传入完整对话历史。这样上下文长度始终控制在2000token以内。

72. 异步函数是线程，进程，还是协议？

回答：

异步函数本质上是协程（Coroutine），不是线程也不是进程，而是基于事件循环的并发模型。

协程的本质：

协程是用户态的轻量级线程，由程序员主动让出控制权（通过await），而不是由操作系统强制切换。Python的asyncio就是协程的实现框架。

和线程的区别：

线程是操作系统调度的，有内核态切换开销；协程是程序内部调度的，切换开销极小。一个线程可以运行多个协程，协程在IO等待时主动让出，让其他协程执行。

和进程的区别：

进程是资源分配的单位，有独立的内存空间；协程共享同一个进程的内存空间，创建和销毁成本极低。

协议层面：

异步函数遵循的是协程协议，Python通过async/await语法实现。底层是基于事件循环（Event Loop）的IO多路复用，用select/epoll监听IO事件。

在项目中的应用：

FastAPI使用uvicorn作为ASGI服务器，内部就是事件循环。当一个请求在等待Milvus查询结果时，事件循环会去处理其他请求，这样单个线程就能处理高并发。我在政策补贴系统中，单线程就能支持200+ QPS。

73. Agent里状态爆炸是什么，怎么处理？

回答：

状态爆炸是指Agent的状态随着对话轮次增加而不断膨胀，最终导致内存溢出或响应变慢。

状态爆炸的原因：

第一，每轮对话都往State中追加数据，没有清理机制。第二，多个Agent各自维护状态副本，数据冗余。第三，中间结果没有及时清理，累积占用大量内存。

解决策略：

第一，状态裁剪：

设计状态的有效期，过期数据自动清理。比如对话历史只保留最近5轮，早期数据压缩或丢弃。

第二，状态压缩：

用大模型对历史状态做摘要，保留关键信息。比如10轮对话的State从5000token压缩到500token。

第三，分层存储：

热数据放内存（当前对话State），温数据放Redis（本次会话历史），冷数据放数据库（历史会话）。根据访问频率选择存储层级。

第四，状态共享：

多个Agent共享同一个State对象，避免重复存储。用LangGraph的统一State管理，确保数据只有一份。

在项目中的实现：

我在政策补贴系统中，每个会话的State大小控制在10KB以内。关键信息（企业信息、匹配结果）保留在State中，对话历史压缩后存Redis，查询日志异步写入数据库。

74. 分别讲讲skill和MCP的组成，有什么区别？

回答：

Skill和MCP是两种不同的能力扩展机制，我在项目中都有使用。

Skill的组成：

Skill是预定义的能力模块，通常包含：触发条件（什么时候用）、执行逻辑（怎么做）、输出格式（返回什么）。比如我的"法条检索Skill"，触发条件是用户询问法律问题，执行逻辑是调用Milvus检索，输出格式是结构化的法条列表。

MCP的组成：

MCP（Model Context Protocol）是模型上下文协议，主要包含：工具定义（Tool Schema）、调用接口（API）、上下文管理。它更像是一种标准化的工具调用协议，让模型能够理解和调用外部工具。

核心区别：

第一，抽象层级不同： Skill是业务层面的能力抽象，关注"做什么"；MCP是技术层面的协议抽象，关注"怎么调用"。

第二，灵活性不同： Skill通常预定义，运行时难以动态调整；MCP支持动态注册和发现，更灵活。

第三，耦合度不同： Skill和业务逻辑耦合紧密；MCP是标准化接口，和具体实现解耦。

在项目中的应用：

在政策补贴系统中，我用Skill封装业务逻辑（如政策匹配、企业画像），用MCP协议调用外部工具（如Milvus、Neo4j）。这样既保证了业务逻辑的清晰，又实现了工具调用的标准化。

75. 讲讲你Milvus里面的索引，原理是什么？为什么用这个索引？

回答：

我在Milvus中使用的是IVF_FLAT索引，这是最常用的向量索引类型之一。

IVF_FLAT的原理：

IVF全称是Inverted File，倒排文件索引。核心思想是先聚类再检索：

第一，训练阶段：用K-means算法将所有向量聚类成nlist个簇（比如1024个），每个簇有一个中心点。

第二，插入阶段：每个向量被分配到距离最近的簇中。

第三，检索阶段：先计算查询向量和所有簇中心的距离，选出最近的nprobe个簇（比如16个），然后只在这几个簇中做精确搜索。

为什么选择IVF_FLAT：

第一，召回率高： FLAT是精确计算，只要nprobe设置合理，召回率可以达到95%以上。我在法律助手项目中，法条召回率从68%提升到94%，索引选择是关键因素。

第二，适合中等规模数据： 我的法律知识库有几万条法条，IVF_FLAT在10万级数据上性能和精度平衡最好。

第三，调参简单： 主要就两个参数：nlist（聚类数）和nprobe（搜索簇数），容易调优。

参数设置：

nlist设为1024，nprobe设为16。这样在保证94%召回率的同时，检索延迟控制在50ms以内。

76. 讲讲LangChain和LangGraph框架，作用分别是什么？

回答：

LangChain和LangGraph都是AI应用开发框架，但定位不同。

LangChain的作用：

LangChain是一个工具集成框架，主要解决"怎么调用各种AI组件"的问题。它提供了统一的接口来调用不同的大模型、向量数据库、工具等。比如用LangChain可以一行代码切换OpenAI和Qwen，不需要改业务逻辑。

核心组件：

  • Model：封装各种LLM的调用接口
  • Prompt：管理提示词模板
  • Chain：串联多个组件的调用链
  • Agent：带工具调用能力的智能体
  • Memory：对话历史管理

LangGraph的作用：

LangGraph是一个流程编排框架，主要解决"多个Agent怎么协作"的问题。它用图结构来定义Agent之间的流转关系，支持条件分支、循环、并行等复杂流程。

核心概念：

  • Node：处理节点，每个节点是一个Agent或函数
  • Edge：连接线，定义节点之间的流转关系
  • State：共享状态，所有节点都可以读写
  • Checkpoint：检查点，支持流程中断和恢复

在项目中的组合使用：

我在政策补贴系统中，用LangChain封装各个Agent的内部逻辑（调用大模型、检索工具），用LangGraph编排多个Agent的协作流程（信息收集 -> 政策匹配 -> 结果生成）。两者配合，既简化了单个Agent的开发，又实现了复杂的多Agent协作。

77. LangGraph的流程具体做了什么，怎么做的？

回答：

我在政策补贴系统中用LangGraph实现了多Agent协作流程，具体如下：

整体流程设计：

用户输入 -> 意图识别Agent -> 信息收集Agent -> 政策匹配Agent -> 结果生成Agent -> 输出

节点实现：

每个节点都是一个Python函数，接收State作为输入，返回更新后的State。比如信息收集Agent节点：

def collect_info(state: State) -> State:
    # 从state中读取用户输入
    query = state["user_query"]
    # 调用大模型提取企业信息
    company_info = llm.extract(query)
    # 更新state
    state["company_info"] = company_info
    return state

边的定义：

用条件边实现分支逻辑。比如意图识别后，根据意图类型路由到不同节点：

def route_by_intent(state: State) -> str:
    if state["intent"] == "查询政策":
        return "policy_search"
    elif state["intent"] == "匹配资质":
        return "qualification_match"
    else:
        return "general_chat"

状态管理：

用TypedDict定义State结构，包含user_query、intent、company_info、match_results等字段。所有节点共享同一个State对象。

执行流程：

LangGraph会根据定义的图结构，自动调度节点执行。从START节点开始，按边的定义流转，直到到达END节点。

78. LangGraph怎么具体的调用一个工具？

回答：

在LangGraph中调用工具，主要通过Tool Node实现，我在政策补贴系统中的做法如下：

第一，定义工具：

用@tool装饰器定义工具函数，描述工具的功能和参数：

from langchain_core.tools import tool

@tool
def search_policy(industry: str, scale: str) -> list:
    """根据行业和规模搜索适用的补贴政策"""
    # 调用Milvus或Neo4j查询
    results = milvus_search(industry, scale)
    return results

第二，绑定工具到Agent：

将工具列表传给LLM，让模型知道有哪些工具可用：

tools = [search_policy, get_company_info]
llm_with_tools = llm.bind_tools(tools)

第三，在节点中调用：

Agent节点调用LLM时，LLM会返回tool_calls字段，包含要调用的工具名和参数。然后用ToolNode执行：

from langgraph.prebuilt import ToolNode

tool_node = ToolNode(tools)
# 在图中添加工具节点
graph.add_node("tools", tool_node)

第四，处理工具结果：

工具执行完后，结果会自动写入State的messages字段。Agent根据工具结果决定下一步动作。

在项目中的实例：

政策匹配Agent调用search_policy工具，传入行业=“制造业”、规模=“大型”，工具返回匹配的政策列表，Agent再对结果进行排序和解释。

79. 你怎么验证你项目中所选的大模型是合适的？

回答：

我在项目中通过定量评估和定性评估相结合的方式来验证模型选择。

定量评估：

第一，准确率测试：

准备测试集，包含100个典型问题和标准答案。用模型回答后，计算准确率。法律助手项目中，Qwen3-32B的准确率达到91%，高于其他测试模型。

第二，响应时间测试：

统计模型的平均响应时间。Qwen-plus的响应时间在500ms以内，满足实时交互需求。

第三，成本计算：

统计每天的API调用量和费用。Qwen-plus的性价比最高，每月成本控制在预算范围内。

定性评估：

第一，专业领域测试：

测试模型在法律、政策领域的专业能力。比如问"劳动合同法第38条"，看模型能否准确引用。

第二，指令跟随测试：

测试模型是否能按照Prompt要求输出格式。比如要求输出JSON格式，看输出是否规范。

第三，边界case测试：

测试模型对模糊、歧义问题的处理能力。比如用户问"我想了解一下"，看模型能否合理追问。

在项目中的验证过程：

我对比了GPT-4、Qwen-plus、DeepSeek三个模型，在准确率、响应时间、成本三个维度综合评估，最终选择Qwen-plus作为主模型，Qwen3-32B用于微调场景。

80. RAG数据怎么清洗的？

回答：

RAG数据清洗是保证检索质量的关键步骤，我在法律助手中做了以下清洗工作：

第一，格式统一：

法律条文来自不同来源（PDF、网页、Word），格式不统一。我用MinerU解析PDF，用BeautifulSoup解析网页，统一转换为纯文本格式。

第二，噪声去除：

去除页眉页脚、页码、版权声明等无关内容。用正则表达式匹配并删除这些噪声信息。

第三，分段处理：

法律条文有章节结构，我按照"第X章"、"第X条"进行分段，保留层级关系。每个条文作为一个独立的chunk，方便检索。

第四，去重处理：

不同来源可能有重复内容，用文本相似度（编辑距离）检测重复，保留最完整的版本。

第五，质量校验：

抽检清洗后的数据，检查是否有乱码、截断、缺失等问题。有问题的条文标记后人工复核。

第六，元数据补充：

为每个chunk添加元数据，包括：法律名称、章节、条文号、发布日期等。这些元数据用于后续的过滤和排序。

清洗效果：

原始数据约10万条，清洗后保留8万条高质量数据。法条召回率从68%提升到94%，说明数据清洗对检索质量的提升非常显著。
