171. 多语言处理的过程中，语言是怎么处理的

回答：

多语言处理的核心问题在于：不同语言的语法结构、分词方式、语义表达差异很大，不能简单地用同一套规则去套。

分几个层面来说：

第一层：分词（Tokenization）

不同语言的分词策略不同。英文天然以空格分隔，中文需要分词器（比如jieba、HanLP），日韩语言也有自己的分词方式。现在大模型用的BPE（Byte Pair Encoding）或SentencePiece，把文本切分成子词单元，不依赖语言边界，所以天然支持多语言。比如"Transformer"在英文里可能被切成"Trans"+“former”，在中文里"注意力机制"可能被切成"注意"+“力”+“机制”。模型不知道什么是语言边界，它只知道统计上哪些子词序列更常见。

第二层：Embedding空间的对齐

多语言模型（比如mBERT、XLM-R）在训练时，会把不同语言的句子映射到同一个语义空间。技术上通过跨语言对比学习来实现——让意思相同的句子（比如"苹果很好吃"和"Apples are delicious"）在向量空间中的距离尽可能近。这样模型"理解"了中文和英文说的是一回事，即使句法结构完全不同。

第三层：实际落地中的处理

在项目实践中，我遇到过用户混合使用中英文提问的情况，比如"帮我查一下民法典中关于intellectual property的条款"。我的做法是：

  1. 不事先做语言检测，让模型直接处理混输
  2. 知识库里的法律文本是中文为主，但Query Rewrite阶段，如果检测到英文关键词，会保留原文不翻译，因为法律术语翻译可能不准确
  3. 检索时，向量化模型（text-embedding-v3）本身支持多语言，中文query能匹配到英文法条释义，反之亦然

经验总结： 多语言处理现在主要靠大模型自身的多语言能力，工程上不需要做太多额外工作。但要注意的是，知识库的质量比语言处理更重要——如果知识库本身只有中文，那模型再强也回答不了英文问题。

172. workflow和agent的区别

回答：

这个问题很关键，我在选型的时候也反复纠结过。

核心区别：确定性 vs 自主性

Workflow（工作流）： 预定义的、确定性的执行路径。你画好流程图，每个节点的输入输出、条件分支、执行顺序都是提前定义好的。比如在法律助手项目中，我用的LangGraph工作流：Query Rewrite → 精确检索 → 语义检索 → 结果合并 → Reranker → 生成回答。每个步骤做什么、做完后去哪个节点，都是固定的。

Agent（智能体）： 自主决策的执行单元。它有一个目标，自己决定用什么工具、走什么路径去达成目标。比如政策补贴系统中的企业画像Agent，它知道目标是"采集企业信息"，至于先查工商信息还是先查社保信息，它自己判断。如果某个工具失败了，它会尝试另一个工具，而不是死板地走预定义路径。

打个比方：

  • Workflow就像流水线——每个工位的人做固定的事，零件按顺序经过每个工位
  • Agent就像自由职业者——你告诉他"帮我搞定这件事"，他自己决定先做什么、用什么工具、遇到问题怎么解决

什么时候用Workflow：

  • 流程固定、不常变化（比如法律检索的标准流程）
  • 对可靠性要求高，不能有偏差
  • 容易被审计和调试

什么时候用Agent：

  • 任务开放、路径不固定（比如企业信息采集，不同企业的数据源不同）
  • 需要灵活应对异常情况
  • 用户需求多样化，难以穷举所有路径

实际项目中的组合使用：

在政策补贴系统中，我实际上是把Agent放在Workflow里面。Workflow是宏观的"匹配—审核—推荐"流程，其中每个节点内部是一个Agent，自主决策如何完成自己的任务。这样既保证了整体的可控性，又保留了局部的灵活性。

173. 文档超过模型上下文窗口时怎么做摘要

回答：

这是一个很实际的问题，法律助手里经常遇到——一份合同可能几万字，但模型的上下文窗口最多32K tokens。

我的做法分场景：

场景一：Map-Reduce（最常用）

把长文档切成多个片段，每个片段分别做摘要，再把所有摘要合并做最终摘要。这就像"先读每章，再综合作者要表达什么"。

具体做法：

  1. 按段落或章节切分文档，每个片段不超过模型上下文的一半
  2. 对每个片段独立生成摘要（map阶段）
  3. 把所有片段的摘要拼接起来，再做一次摘要（reduce阶段）

优点是实现简单，没有丢失信息。缺点是成本高（每个片段都调用一次LLM），而且片段之间的上下文关系可能丢失。

场景二：滑动窗口（Streaming）

用一个滑动窗口逐段处理，每次窗口包含前一段的摘要+当前段落。比如：

  • 处理第1段，生成摘要A
  • 处理第2段，输入是"摘要A + 第2段原文"，生成摘要B
  • 处理第3段，输入是"摘要B + 第3段原文"，生成摘要C

这样每段只处理一次，且保留了上下文连续性。我的合同审查功能就用这个方案，因为合同条款之间逻辑关联性强，不能丢失前文信息。

场景三：分层摘要（Hierarchical）

适用于超长文档（比如几万字的裁判文书）。先做小片段摘要，再把小片段摘要合并成中片段摘要，再合并成最终摘要。类似于金字塔结构。

场景四：提取关键信息（结构化摘要）

不是所有文档都需要完整摘要。在政策补贴系统中，企业上传的资质文件可能几百页，但我不需要全文摘要，只需要提取关键字段——企业名称、注册时间、经营范围、资质证书编号等。用LLM做结构化提取，比做摘要效率高得多。

我的选型建议：

如果是法律合同这种逻辑连贯、有关键条款的文档，用滑动窗口。如果是政策文件这种分章节、每章相对独立的文档，用Map-Reduce。如果只是想提取关键信息，用结构化提取。

174. 如何检测链表是否存在环？

回答：

这是经典的算法题，最常用的方法是快慢指针（Floyd判圈算法）。

思路很简单： 两个指针同时从链表头部出发，慢指针每次走一步，快指针每次走两步。如果链表有环，快指针终会追上慢指针（两者相遇）；如果没有环，快指针会先到达末尾。

为什么要用两步？ 其实走三步、四步也可以，但两步是最优的——保证快指针相对慢指针以1步/次的速度逼近，在任何环上都能相遇，不会跳过。

在实际项目中用过吗？

说实话，在AI应用开发中，直接手写链表判环的场景很少。但它的底层思想在Agent开发中很有用——防止路由死循环。在LangGraph工作流中，Agent在多个节点之间跳转，如果路由逻辑设计不当，可能会陷入A→B→C→A的死循环。我处理这个问题的方法就是借鉴了快慢指针的思路：在Agent状态中维护一个"访问历史"，如果某个节点被访问超过一定次数，就强制中断或走默认路径。

175. 有用过docker和k8s么，分别介绍一下？

回答：

两个项目都用Docker部署，k8s在政策补贴系统中用过。

Docker——应用的打包和运行环境标准化

Docker解决的问题是"在我电脑上能跑"的尴尬。项目中，我把法律助手拆成几个容器：

  • legal-app：FastAPI后端
  • legal-frontend：Vue3前端（Nginx容器）
  • milvus：向量数据库
  • redis：缓存
  • mysql：关系数据库

用Docker Compose一键启动，所有服务在同一个网络里，互相通过服务名访问。开发环境、测试环境、生产环境用同一套Dockerfile，彻底消除了环境不一致的问题。

K8s——容器的编排和集群管理

政策补贴系统上线后，单机Docker不够用了，需要多机部署、自动扩缩容、滚动更新，所以引入了K8s。

K8s的核心概念：

  • Pod：最小的部署单元，一个Pod里可以跑一个或多个容器
  • Deployment：管理Pod的副本数和滚动更新
  • Service：服务发现和负载均衡
  • ConfigMap/Secret：配置管理

用了K8s的哪些功能？

  1. 自动扩缩容（HPA）： 根据CPU和内存使用率自动调整Pod数量。政策补贴系统在申报季流量会暴涨，HPA自动从3个Pod扩展到10个，流量回落后再缩回去
  2. 滚动更新： 更新代码时不中断服务，先启动新Pod，等它Ready后再关掉旧Pod
  3. 健康检查： Liveness Probe检测容器是否存活，Readiness Probe检测服务是否就绪，不健康时自动重启

Docker vs K8s的选型建议：

如果只是单机部署、服务不多，Docker Compose就够了，没必要上K8s（运维成本很高）。如果有多台机器、需要弹性伸缩、服务比较多，才值得上K8s。

176. python异步协程和线程的区别？

回答：

核心区别一句话：线程是操作系统级别的并发，协程是用户级别的并发。

线程：

  • 由操作系统调度，多个线程可以同时运行在多个CPU核心上（真正的并行）
  • 切换线程需要操作系统介入，有上下文切换开销（保存寄存器、栈等）
  • 线程间共享内存，需要锁来避免数据竞争
  • 适合CPU密集型任务或真正的并行计算

协程（async/await）：

  • 由事件循环调度，单线程内运行，同一时间只有一个协程在运行（并发而非并行）
  • 协程切换是用户态操作，开销极小（保存几个变量就行了）
  • 不需要锁，因为单线程内不会同时执行两个协程
  • 适合I/O密集型任务——网络请求、文件读写、数据库查询

在项目中的实际使用：

法律助手后端用FastAPI，天然支持异步。我遇到最多的场景是：用户提问后，需要同时查询Milvus（向量检索）和MySQL（精确检索），两路检索是独立的，用协程并行执行：

milvus_task = asyncio.create_task(search_milvus(query))
mysql_task = asyncio.create_task(search_mysql(query))
results = await asyncio.gather(milvus_task, mysql_task)

这里两路检索是并发执行的，总耗时等于较慢的那一路，而不是两路串行的和。如果用线程也能实现，但协程的创建和切换开销更小，适合这种大量I/O等待的场景。

选型总结：

  • I/O密集型（网络请求、数据库查询、文件读写）→ 协程，开销小，代码更简洁
  • CPU密集型（计算、数据处理）→ 多进程，利用多核
  • 两者混合 → 多进程+协程，每个进程内用协程处理I/O

177. 什么是IO密集型场景

回答：

I/O密集型指的是程序的性能瓶颈在输入输出操作，而不是在CPU计算上。

典型的I/O操作：

  • 网络请求（HTTP调用、API请求）
  • 数据库查询（MySQL、Redis、Milvus）
  • 文件读写（读取PDF、写入日志）
  • 磁盘操作（读写数据库文件）

怎么判断是不是I/O密集型？ 看CPU的利用率。如果程序大部分时间在等待I/O完成（CPU空闲），只有小部分时间在做计算（CPU忙），那就是I/O密集型。

在项目中的例子：

法律助手系统里，用户提一个问题，后端要做的事情：

  1. Query Rewrite → 调用LLM API（网络I/O，等LLM返回）
  2. 精确检索 → 查MySQL（数据库I/O，等MySQL返回）
  3. 语义检索 → 查Milvus（网络I/O，等Milvus返回）
  4. 结果合并 + Reranker → 调用Reranker模型（计算+少量I/O）
  5. 生成回答 → 调用LLM API（网络I/O，等LLM返回）

这整个流程中，大部分时间花在等待网络和数据库返回上，CPU基本是空闲的。这就是典型的I/O密集型场景。

I/O密集型场景的优化策略：

  1. 异步编程： 用asyncio让程序在等待I/O时去做其他事，而不是干等
  2. 并发请求： 不相关的I/O操作并行执行（比如同时查MySQL和Milvus）
  3. 缓存： 高频查询的结果缓存到Redis，减少I/O次数
  4. 连接池： 复用数据库连接，减少建立连接的开销
  5. 批量操作： 把多个小I/O合并成一个大I/O（比如批量插入替代逐条插入）

178. python怎么实现生成器

回答：

生成器（Generator） 是一种特殊的迭代器，它的特点是惰性求值——需要的时候才生成下一个值，而不是一次性生成所有值。

最简单的方式：yield关键字

def read_chunks(file_path, chunk_size=500):
    with open(file_path, 'r') as f:
        chunk = []
        for line in f:
            chunk.append(line)
            if len(''.join(chunk)) >= chunk_size:
                yield ''.join(chunk)
                chunk = []
        if chunk:
            yield ''.join(chunk)

这个生成器每次yield返回一个切片，不一次性把整个文件读入内存。这在处理大文件时非常有用。

生成器表达式： 类似列表推导式，但用圆括号

squares = (x**2 for x in range(10))  # 生成器，不会立即计算

生成器在项目中的应用：

在法律助手项目中，我们处理几百份PDF文档时，不可能一次性把所有的文本都加载到内存里。用生成器逐页读取、逐页处理：

def extract_pdf_pages(pdf_path):
    # 用MinerU逐页解析PDF
    for page_num in range(get_page_count(pdf_path)):
        page_text = extract_page(pdf_path, page_num)
        yield clean_page_text(page_text)

然后对每一页文本做切片、向量化、入库，处理完一页就释放内存，再处理下一页。这样即使文档有几百页，内存占用也始终很小。

生成器的好处：

  1. 节省内存： 不需要一次性把所有数据加载到内存
  2. 惰性计算： 可能不需要全部数据，用多少算多少
  3. 表示无限序列： 可以生成理论上的无限数据流

179. pytorch相似的框架有哪些？

回答：

PyTorch是目前最主流的深度学习框架，但也有很多同类型或定位不同的框架：

1. TensorFlow / Keras

谷歌出品的框架，曾经是行业老大。PyTorch和TensorFlow的定位差异：

  • PyTorch是动态图（Define-by-Run），写起来像写Python代码，调试方便
  • TensorFlow 1.x是静态图（Define-and-Run），先建图再执行，调试困难
  • TensorFlow 2.x也支持动态图（Eager Execution），但生态已经被PyTorch超越了

2. JAX

Google的另一个框架，定位更底层。特点是：

  • 函数式编程风格，没有可变状态
  • 自动微分（grad）和JIT编译（jit）非常优雅
  • 支持向量化（vmap）和并行化（pmap）
  • 适合研究新算法，但生态不如PyTorch成熟

3. PaddlePaddle（飞桨）

百度的框架，在国内有一定用户基础。特点是：

  • 动态图和静态图都支持
  • 中文文档完善
  • 有预训练模型库PaddleNLP、PaddleCV
  • 在某些工业场景（如百度内部）有深度应用

4. MXNet / Gluon

Apache基金会的框架，曾经是AWS的首选，但现在用户越来越少。

5. Lightning（PyTorch Lightning）

不是替代PyTorch，而是PyTorch的上层封装。它把训练循环、验证循环、日志记录、分布式训练等样板代码封装起来，让开发者只需要关注模型和数据。我在微调Qwen3-32B时用过，确实省了很多代码。

实际选型建议：

做研究、快速原型、中小型项目 → PyTorch（生态最丰富，社区最活跃）
做工业级部署、多平台支持 → TensorFlow（TFLite、TF Serving等部署工具成熟）
做高性能计算、研究新算法 → JAX（在学术界越来越流行）
做中文NLP、国内部署 → PaddlePaddle（中文生态好，有中文预训练模型）

我个人的选择是PyTorch，因为它的生态系统最完善，HuggingFace就是基于PyTorch的，微调模型、部署推理都方便。

180. Tensorflow和pytorch的区别

回答：

核心区别一句话：PyTorch是动态图，TensorFlow是静态图出身（但2.x也支持动态图了）。

1. 计算图构建方式

这是最根本的区别：

  • PyTorch（动态图）： 边运行边建图，每次执行都重新构建计算图。写起来就像写普通Python代码，print()能看到中间变量，pdb可以断点调试。对开发者友好，特别适合研究探索。
  • TensorFlow（静态图，1.x时代）： 先建一个完整的计算图，再送数据进去执行。建图和执行是分离的，调试困难（不能直接print中间变量）。但静态图有优化空间，部署时性能更好。

2. 调试体验

PyTorch的调试体验好太多。在PyTorch里，你可以直接打断点看张量的值，可以print中间结果。TensorFlow 1.x时代，你需要在Session里跑完才能看到结果，debug非常痛苦。

3. 生态系统

PyTorch的生态更活跃。HuggingFace Transformers、Diffusers、torchvision、torchaudio等主流库都是基于PyTorch的。TensorFlow的生态也不错（TFLite、TF Serving、TFX），但在学术研究和AI应用开发领域，PyTorch已经占主导地位。

4. 部署

TensorFlow的部署工具链更成熟——TFLite（移动端）、TF Serving（服务端）、TensorFlow.js（浏览器端），一套工具覆盖所有平台。PyTorch的部署相对弱一些，需要用TorchScript或ONNX做转换，或者用PyTorch Serve。

5. 在项目中的实际感受

我在法律助手项目中，微调Qwen3-32B用的是PyTorch + HuggingFace Transformers，因为：

  • 微调框架（如QLoRA）都是基于PyTorch的
  • 调试方便，train loss不对劲可以随时打断点看
  • HuggingFace生态太强了，模型、数据集、评测一站式

推理部署用的是vLLM，它底层也是PyTorch，但做了大量优化（PagedAttention、Continuous Batching等），性能比原生PyTorch推理好很多。

总结： 做研究和AI应用开发，选PyTorch。做工业级多平台部署，TensorFlow可能更合适。但现在的趋势是PyTorch也在补部署能力的短板，两者的差距在缩小。
