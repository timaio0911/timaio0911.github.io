1. 介绍一下python装饰器，什么场合会使用？

回答：

装饰器是Python的高级特性，本质是一个函数，用来修改其他函数的行为，我在项目中经常使用。

什么是装饰器：
装饰器就是一个接受函数作为参数的函数，返回一个新的函数。用@语法糖放在函数定义前面，就能在不修改原函数代码的情况下增加功能。

核心原理：
装饰器利用了Python中函数是一等公民的特性，函数可以作为参数传递，也可以作为返回值。装饰器本质上就是一个高阶函数。

使用场合：

  1. 日志记录：记录函数的调用时间、参数、返回值
  2. 性能测试：计算函数执行时间
  3. 权限校验：检查用户是否有权限执行某个操作
  4. 缓存：缓存函数的计算结果，避免重复计算
  5. 重试机制：函数执行失败时自动重试

我在项目中的应用：

政策补贴系统中，我用装饰器做了几个通用功能：

  1. 日志装饰器：记录每个Agent的调用日志，方便调试
  2. 计时装饰器：监控工具调用的响应时间，性能优化
  3. 异常处理装饰器：统一捕获异常，返回友好的错误信息
  4. 缓存装饰器：用functools.lru_cache缓存重复查询的结果

实际案例：
政策检索工具用了缓存装饰器，同样的查询条件直接返回缓存结果，响应时间从2秒降到100毫秒。

注意事项：
装饰器会改变函数的元信息（如__name__、doc），可以用functools.wraps保留原函数信息。

2. 什么是知识蒸馏

回答：

知识蒸馏是模型压缩的核心技术，我在法律助手项目中了解过，用于把大模型的能力迁移到小模型。

核心原理：
知识蒸馏的基本思想是用一个"教师模型"（大模型）来指导"学生模型"（小模型）学习。教师模型的输出（soft label）包含比硬标签（hard label）更多的信息，学生模型通过模仿教师模型的输出来学习。

为什么有效：

  1. 信息更丰富：教师模型的输出概率分布包含了类别之间的关系信息
  2. 学习更容易：soft label比hard label更容易学习，收敛更快
  3. 泛化更好：学生模型能学到教师模型的泛化能力

蒸馏方法：

  1. 输出蒸馏：学生模型学习教师模型的输出概率分布
  2. 特征蒸馏：学生模型学习教师模型的中间特征表示
  3. 关系蒸馏：学生模型学习样本之间的关系

我在项目中的应用：

法律助手项目中，我用Qwen3-32B作为教师模型，蒸馏到一个7B的小模型：

  1. 准备数据：用Qwen3-32B对法律问答数据集生成回答
  2. 训练学生：用这些数据训练7B模型
  3. 效果对比：7B模型在法律问答任务上达到了32B模型90%的效果，但推理速度快3倍

实际效果：
蒸馏后的小模型部署成本低，单卡可以支持更多并发，适合生产环境。

知识蒸馏 vs 微调：

  • 蒸馏：大模型指导小模型，保留大模型能力
  • 微调：在小模型上直接训练，可能丢失通用能力

3. hermes框架是什么？

回答：

Hermes是一个开源的AI Agent框架，专注于构建多Agent协作系统。

核心特点：

  1. 多Agent协作：支持多个Agent之间通信和协作，每个Agent有独立的职责
  2. 工具调用：标准化的工具调用协议，支持各种外部工具
  3. 记忆管理：支持短期记忆和长期记忆，管理Agent的状态
  4. 工作流编排：支持复杂的任务编排和流程控制

架构设计：

  1. Agent层：定义Agent的角色、能力、记忆
  2. 工具层：封装各种外部工具，提供统一接口
  3. 通信层：Agent之间的消息传递机制
  4. 编排层：定义工作流和任务分配

和其他框架的对比：

  1. LangChain：更通用，支持各种LLM应用，Agent功能相对简单
  2. LangGraph：专注状态图和工作流，适合复杂流程
  3. Hermes：专注多Agent协作，Agent间通信更方便

我在项目中的选择：

政策补贴系统用LangGraph而不是Hermes，原因是：

  1. LangGraph和LangChain生态兼容性好
  2. 状态图模型更适合我们的业务流程
  3. 社区更活跃，文档更完善

适用场景：
Hermes适合需要多个独立Agent协作的场景，比如客服系统、研究助手、创意写作等。

4. 大量agent任务里面，如何定义任务是否完成，完成率怎么计算？

回答：

任务完成定义和完成率计算是Agent系统评估的关键，我在政策补贴系统中建立了完整的评估体系。

任务完成的定义：

  1. 目标达成：任务是否达到了预期目标
  2. 质量达标：输出是否满足质量要求
  3. 无错误：执行过程中没有不可恢复的错误
  4. 用户满意：用户是否接受任务结果

完成率计算方法：

1. 二元完成率
最简单的计算方式，任务要么完成（1），要么未完成（0）。
完成率 = 完成的任务数 / 总任务数

2. 部分完成率
考虑任务的部分完成情况，比如完成了80%的步骤。
完成率 = 平均完成度

3. 加权完成率
不同任务权重不同，核心任务权重高。
完成率 = Σ(任务完成度 × 任务权重) / Σ(任务权重)

我在项目中的实践：

政策补贴系统的任务评估：

  1. 任务分解：把复杂任务分解成子任务
  2. 子任务评估：每个子任务独立评估完成度
  3. 整体计算：加权计算整体完成率

评估维度：

  1. 功能完成度：是否完成了所有功能
  2. 质量评分：输出质量的人工评分
  3. 时间效率：是否在规定时间内完成
  4. 错误率：执行过程中的错误数量

实际效果：
通过完整的评估体系，我们的Agent任务完成率从75%提升到92%，质量评分从3.5分提升到4.2分（满分5分）。

5. 在claude code的场景下，我想要建一个评测集，是一个多轮交互的评测集，数据集怎么设置，多轮交互评什么，多轮交互怎么构建指标，给我专业答案

回答：

Claude Code的多轮交互评测是个复杂问题，需要从数据集设计、评估维度、指标构建三个方面来考虑。

数据集设置：

1. 场景覆盖

  • 代码生成：从需求描述到代码实现
  • 代码调试：从报错信息到问题定位和修复
  • 代码优化：从性能问题到优化方案
  • 代码重构：从代码质量到重构建议

2. 多轮设计

  • 轮次数量：3-10轮，模拟真实交互
  • 难度梯度：从简单到复杂，逐步深入
  • 分支设计：根据用户反馈调整后续对话

3. 标注内容

  • 用户输入：每轮用户的查询或反馈
  • 期望输出：每轮期望Claude Code的响应
  • 评估标准：每轮的评估要点

多轮交互评什么：

1. 上下文理解

  • 是否理解前几轮的对话内容
  • 是否能正确引用之前提到的代码或问题

2. 任务推进

  • 是否逐步推进任务
  • 是否在正确的方向上工作

3. 错误恢复

  • 遇到错误时是否能正确处理
  • 是否能从失败中学习

4. 交互质量

  • 响应是否清晰、有条理
  • 是否主动询问不明确的地方

指标构建：

1. 自动指标

  • 代码正确率：生成的代码是否能运行
  • 测试通过率：代码是否通过测试用例
  • 响应时间：每轮响应的时间

2. 人工指标

  • 任务完成度：人工评估任务完成情况
  • 代码质量：代码的可读性、可维护性
  • 交互体验：对话的流畅度、自然度

3. 综合指标

  • 多轮一致性：前后响应是否一致
  • 上下文利用率：是否有效利用历史对话
  • 任务收敛性：是否逐步接近目标

我在项目中的参考：

虽然不是Claude Code，但政策补贴系统的多轮对话评估有参考价值：

  1. 任务分解：把复杂任务分解成可评估的子任务
  2. 逐步评估：每轮都评估任务推进情况
  3. 最终评估：整体评估任务完成质量

6. 制度文档是总分结构的，一级标题和二级标题语义确实怎么解决

回答：

制度文档的总分结构确实是个挑战，我在政策补贴系统中处理过类似的政策文档。

问题本质：
制度文档通常是一级标题（总则、分则）和二级标题（具体条款）的层级结构，但语义上可能存在：

  1. 语义重叠：不同层级的标题可能包含相似内容
  2. 语义缺失：某些层级的标题可能过于笼统
  3. 语义断裂：上下级标题之间缺乏语义关联

解决方案：

1. 结构化解析

  • 层级识别：识别文档的层级结构（标题、条款、子条款）
  • 归属关系：建立上下级标题的归属关系
  • 内容提取：提取每个标题下的具体内容

2. 语义补充

  • 上下文补充：把上级标题的语义补充到下级标题
  • 关键词提取：从内容中提取关键词，补充标题的语义
  • 语义合并：把相关标题的语义合并

3. 索引优化

  • 分层索引：不同层级的标题用不同的索引策略
  • 关联索引：建立标题之间的关联索引
  • 语义索引：用向量表示标题的语义

我在项目中的实践：

政策补贴系统处理政策文档：

  1. 文档解析：用正则表达式和LLM解析文档结构
  2. 层级构建：建立政策→章节→条款的层级关系
  3. 语义补充：把政策标题的语义补充到具体条款
  4. 索引构建：用Milvus构建向量索引，同时保留层级信息

技术实现：

  • 用Pydantic定义文档结构模型
  • 用LLM提取标题和内容的语义关系
  • 用Neo4j存储层级关系
  • 用Milvus存储语义向量

实际效果：
通过结构化解析和语义补充，制度文档的检索准确率提升了25%，用户查询时能准确找到相关条款。

7. checkpoint是干啥的？

回答：

Checkpoint是训练和推理中的重要机制，用于保存和恢复状态。

训练中的Checkpoint：

  1. 定期保存：训练过程中定期保存模型参数
  2. 断点续训：训练中断后可以从checkpoint恢复，不用从头开始
  3. 模型选择：保存多个checkpoint，选择效果最好的

推理中的Checkpoint：

  1. 状态保存：保存推理过程中的中间状态
  2. 长文本处理：处理长文本时，可以分段处理，保存checkpoint
  3. 错误恢复：推理出错时，可以从最近的checkpoint恢复

Agent系统中的Checkpoint：

  1. 任务状态：保存Agent的执行状态和中间结果
  2. 回溯能力：任务失败时，可以回溯到之前的checkpoint
  3. 状态共享：不同Agent可以共享checkpoint

我在项目中的应用：

政策补贴系统用LangGraph的checkpoint机制：

  1. 状态保存：每个Agent处理完后，保存状态到Redis
  2. 错误恢复：如果某个Agent执行失败，从上一个checkpoint恢复
  3. 调试支持：可以查看任意时刻的状态，方便调试

技术实现：

  • 用Redis存储checkpoint，支持快速读写
  • 每个任务有唯一的checkpoint ID
  • checkpoint包含完整的状态信息

实际效果：
通过checkpoint机制，系统的容错性大大提升，任务失败率从15%降低到5%。

checkpoint vs 缓存：

  • checkpoint：保存完整状态，支持恢复
  • 缓存：保存计算结果，提升性能

8. mcp和function有啥区别？

回答：

MCP（Model Context Protocol）和Function Calling是两种不同的工具调用方式，我在项目中都有使用。

Function Calling：

  1. 定义：模型调用预定义的函数，获取外部信息或执行操作
  2. 特点：和模型绑定，不同模型有不同的实现
  3. 接口：JSON格式的函数定义和调用

MCP：

  1. 定义：标准化的工具调用协议，跨模型、跨框架通用
  2. 特点：协议标准化，一次开发多处使用
  3. 接口：标准化的请求/响应格式

核心区别：

1. 标准化程度

  • Function Calling：每个模型有自己的实现，接口不统一
  • MCP：标准化协议，所有模型和框架都支持

2. 可移植性

  • Function Calling：换模型需要修改代码
  • MCP：换模型不需要修改工具代码

3. 生态系统

  • Function Calling：模型厂商提供
  • MCP：开源社区维护，工具更丰富

4. 功能范围

  • Function Calling：主要是函数调用
  • MCP：支持工具、资源、提示词等多种能力

我在项目中的选择：

政策补贴系统用MCP而不是Function Calling，原因是：

  1. 可扩展性：新工具开发方便，遵循MCP协议即可
  2. 可维护性：工具代码和模型代码解耦
  3. 可移植性：换模型不需要修改工具层

实际案例：
政策检索工具用MCP实现，最初用Qwen模型，后来换成Claude模型，工具代码完全不用改。

总结：
MCP是Function Calling的升级版，标准化、可移植、生态丰富。新项目建议用MCP。

9. 多agent最后得出的结果不一样如何裁决，裁决逻辑是什么？

回答：

多Agent结果裁决是多Agent系统的难点，我在政策补贴系统中实现了多种裁决策略。

裁决场景：

  1. 政策匹配：不同Agent匹配到不同的政策
  2. 企业画像：不同Agent对企业的评估不同
  3. 报告生成：不同Agent生成的报告内容不一致

裁决策略：

1. 投票机制

  • 多数投票：选择最多Agent支持的结果
  • 加权投票：不同Agent权重不同，权威Agent权重高
  • 阈值投票：超过阈值的结果才被采纳

2. 置信度机制

  • 置信度比较：选择置信度最高的结果
  • 置信度加权：根据置信度加权计算最终结果
  • 置信度阈值：置信度低于阈值的结果被过滤

3. 规则机制

  • 优先级规则：不同Agent有不同优先级
  • 业务规则：根据业务逻辑选择结果
  • 冲突规则：定义冲突时的处理规则

4. 人工介入

  • 人工审核：关键决策人工审核
  • 用户确认：让用户选择最终结果
  • 专家仲裁：请领域专家仲裁

我在项目中的实现：

政策补贴系统的裁决逻辑：

  1. 政策匹配：用加权投票，权威政策数据库权重高
  2. 企业画像：用置信度机制，选择置信度最高的画像
  3. 报告生成：用规则机制，根据业务逻辑选择内容

技术实现：

  • 用Redis存储每个Agent的结果和置信度
  • 用Python实现裁决逻辑
  • 用Pydantic验证结果格式

实际效果：
通过多种裁决策略，系统的决策准确率从85%提升到95%。

核心原则：
裁决逻辑要根据业务场景设计，没有通用的解决方案。

10. 状态存取响应速度慢该怎么处理？

回答：

状态存取响应速度慢是Agent系统的常见问题，我在政策补贴系统中遇到过并解决了。

问题场景：
政策补贴系统的状态存在Redis中，随着数据量增加，响应速度从10ms增加到100ms。

优化策略：

1. 存储优化

  • 数据压缩：压缩状态数据，减少存储和传输量
  • 字段精简：只存储必要字段，去除冗余信息
  • 格式优化：用高效的序列化格式（如MessagePack）

2. 缓存优化

  • 本地缓存：热点数据缓存在内存中
  • 多级缓存：本地缓存+Redis缓存
  • 缓存预热：提前加载可能用到的数据

3. 访问优化

  • 批量读取：一次读取多个状态，减少网络往返
  • 异步读取：用异步IO，不阻塞主流程
  • 预读取：提前读取可能需要的状态

4. 架构优化

  • 分片存储：把状态分散到多个Redis实例
  • 读写分离：读请求走从库，写请求走主库
  • 数据分层：热数据放Redis，冷数据放数据库

我在项目中的实践：

政策补贴系统的状态优化：

  1. 数据压缩：用gzip压缩状态数据，大小减少70%
  2. 本地缓存：用LRU缓存热点状态，命中率80%
  3. 批量操作：用Redis Pipeline批量读写，减少网络开销
  4. 异步处理：用asyncio异步读取状态，不阻塞主流程

技术实现：

  • 用functools.lru_cache做本地缓存
  • 用aioredis做异步Redis操作
  • 用MessagePack做高效序列化

实际效果：
通过优化，状态存取响应时间从100ms降低到15ms，系统整体性能提升明显。

监控告警：
