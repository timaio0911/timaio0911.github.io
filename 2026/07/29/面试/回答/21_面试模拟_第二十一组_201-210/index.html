面试模拟 - 第二十一组（201-210题）

基于简历项目经历，模拟面试回答

201. AI是否可以帮助我们从架构体系和业务开发全部完成？

回答：

我的看法是：AI可以极大地辅助架构设计和业务开发，但现阶段还不能完全替代人完成全部工作。 它更像是一个超级协作者，而不是一个全能的替代者。

AI能做什么：

1. 架构设计层面

  • AI可以帮助我们做技术选型分析，比如对比不同框架的优劣
  • 可以生成初版架构图、模块划分方案
  • 能根据需求文档快速生成项目骨架代码

2. 业务开发层面

  • 代码生成能力很强，像Claude Code、Cursor这些工具，写CRUD、API接口、数据模型已经非常成熟
  • 能辅助写单元测试、文档注释
  • 可以帮我们做代码审查、发现潜在bug

3. 实际项目中的体会

在做法律助手项目时，我用AI辅助写了大量代码，包括FastAPI的接口定义、Pydantic模型、MinerU的PDF解析逻辑等。但有几个关键点还是需要人来把控：

  • 业务理解：法律条款的切片策略、检索逻辑的优化方向，这些需要深入理解业务场景
  • 架构决策：为什么用Milvus而不是ES，为什么用Neo4j做政策图谱，这些权衡需要人来判断
  • 异常处理：AI生成的代码往往缺少边界情况的处理，需要人工补充

AI的局限：

方面 说明
复杂业务逻辑 多条件交织的业务规则，AI容易遗漏
系统集成 老系统对接、数据迁移等需要大量上下文理解
安全合规 数据隐私、权限控制等需要专业判断
性能优化 深层次的性能瓶颈定位，AI缺少全局视角

我的观点： AI目前能做到70%-80%的编码工作，但架构设计、关键技术决策、复杂问题排查还是需要人来主导。善用AI的话，一个人的产出可以抵上一个三人的小团队。

202. 可以提前通过约束doc来对cursor的行为进行约束么？

回答：

可以的，而且这正是Cursor等AI编程工具的最佳实践方式。通过约束文档（rules文件、指令文件）来提前定义AI的行为边界，能显著提升代码质量和一致性。

具体的做法：

1. .cursorrules 文件（最常用）

在项目根目录下创建 .cursorrules 文件，里面可以定义：

# 技术栈约束
- 使用 FastAPI + Pydantic v2
- 使用 Vue3 + TypeScript + Element Plus
- 使用 SQLAlchemy 2.0 异步模式

# 代码风格约束
- 使用类型注解（Type Hints）
- 函数长度不超过50行
- 变量命名使用snake_case

# 项目规范
- API响应格式统一为 {code, message, data}
- 所有异常需要自定义错误码
- 数据库操作必须使用事务

2. 项目级文档约束

在项目中放置 README.md、CONTRIBUTING.md、ARCHITECTURE.md 等文档，Cursor会读取这些文件作为上下文。比如我的法律助手项目就在项目根目录放了一个 docs/技术规范.md，里面定义了：

  • 目录结构规范
  • 数据库命名规范
  • API设计规范
  • 日志规范

3. 高级用法 - 角色定义

可以给Cursor设定一个"角色"，比如：

你是一个有5年经验的Python后端工程师，专注于AI应用开发。
你擅长：FastAPI、LangChain、向量数据库、异步编程。
你的代码风格：简洁、类型安全、异常处理完善。

我在项目中的实际经验：

做政策补贴系统时，我在项目里放了 rules.md 文件，里面定义了：

  • LangGraph节点的命名规范
  • Agent的接口协议
  • 状态管理的约束

效果很明显，AI生成的代码几乎不需要修改就能直接合并。但要注意：

  • 约束要具体：不要写"代码要优雅"这种模糊的话，要写"函数不超过50行"这种可检查的规则
  • 约束要可执行：AI不会主动遵守复杂的规则，所以规则最好能通过lint工具自动检查
  • 定期更新：项目迭代过程中，规则也要同步更新

总结： 通过约束文档来约束AI行为是非常有效的方法，但需要花时间写好规则，而且要持续维护。

203. 详细讲一下怎么用prompt来设定agent的行为？

回答：

用Prompt来设定Agent行为，本质上是通过系统提示词（System Prompt）来定义Agent的角色、职责、行为边界和输出规范。做政策补贴系统时，我在这方面花了不少功夫。

核心思路：

1. 角色定义（Role）

给Agent一个清晰的"人设"：

你是一个企业政策补贴匹配专家，熟悉国家和地方的政策补贴规则。
你的职责是：根据企业画像，分析该企业可能符合哪些政策补贴条件。

2. 行为边界（Scope）

明确Agent能做什么、不能做什么：

你可以做的：
- 查询政策知识库
- 分析企业信息
- 生成匹配建议

你不能做的：
- 给出最终审批结果（需要人工确认）
- 修改企业信息
- 生成虚假政策条款

3. 输出格式规范（Format）

定义输出的结构，让Agent的输出可解析：

输出格式必须为JSON：
{
  "matched_policies": [
    {
      "policy_name": "政策名称",
      "match_score": 0-1,
      "reason": "匹配理由",
      "required_conditions": ["条件1", "条件2"]
    }
  ],
  "summary": "总体分析摘要"
}

4. 推理步骤（Reasoning）

引导Agent的思考过程，比如ReAct模式的Prompt：

请按以下步骤思考：
1. 先理解用户的问题：用户想了解什么？
2. 查询知识库：从政策库中检索相关政策
3. 分析匹配度：逐条对比企业信息和政策条件
4. 给出结论：输出匹配结果和建议

政策补贴系统中实际用的Prompt示例：

你是一个企业政策补贴匹配Agent。

【角色】
你是企业政策补贴智能匹配系统的核心Agent，负责分析企业画像和政策条件。

【输入】
你将收到：
1. 企业信息（行业、规模、营收、员工数、注册地等）
2. 候选政策列表（从知识库检索回来）

【处理流程】
1. 提取企业关键特征
2. 逐条对比政策条件
3. 计算匹配度（完全匹配/部分匹配/不匹配）
4. 生成匹配报告

【输出格式】
{
  "enterprise_analysis": {企业关键特征},
  "matched_policies": [{政策名、匹配度、理由、缺失条件}],
  "total_score": 综合匹配评分,
  "recommendations": ["建议1", "建议2"]
}

【约束】
- 只基于知识库中的政策信息，不要编造政策
- 如果缺少必要信息，明确告知需要补充什么
- 匹配度评估要客观，不要过度乐观

5. 工具调用（Tool Use）

如果Agent需要调用工具，要在Prompt中定义工具的使用方式：

你拥有以下工具：
1. search_policy(query): 搜索政策知识库
2. get_enterprise_info(id): 获取企业详细信息
3. calculate_match(enterprise, policy): 计算匹配度

使用工具时，请先说明为什么使用这个工具，以及期望得到什么信息。

关键心得： Prompt设定Agent行为时，越具体越好。不要写"请认真分析"，要写"对比企业营收是否超过政策要求的门槛"。而且需要多次迭代调优，我做了大概5-6版才稳定下来。

204. 资源受限，只有一个24G显存的卡，如何对一个70B的模型进行全参微调？

回答：

这是一个很现实的问题。坦白说，单卡24G显存对70B模型做全参微调基本不可能，因为70B模型仅参数加载就需要约140GB（FP16）或70GB（INT4）。但我们可以通过一些技术手段来近似实现，或者说在有限资源下做有效微调。

实际可行的方案：

方案一：QLoRA（最推荐，我在法律助手项目中用的方案）

显存占用估算：
- 70B模型INT4量化加载：~35GB → 还不够
- QLoRA + 4bit量化 + 梯度检查点：约20-22GB → 勉强够
- QLoRA + 4bit + 梯度检查点 + 小batch_size(1)：约18-20GB → 可行

具体配置：

model: Qwen3-32B  # 实际我们用的是32B，70B可以类似配置
quantization: 4bit  # bitsandbytes NF4
lora_r: 16
lora_alpha: 32
lora_dropout: 0.1
batch_size: 1
gradient_accumulation_steps: 4
gradient_checkpointing: true

方案二：模型并行 + 卸载（CPU Offloading）

如果必须全参微调，可以：

  • 使用 DeepSpeed ZeRO-3：将模型参数分布到CPU和GPU
  • 但训练速度会非常慢，因为CPU-GPU传输是瓶颈
  • 一个batch可能需要几十秒

方案三：更务实的选择——换模型

24G显存更适合的模型选择：

7B 模型：全参微调没问题
13B 模型：可以用LoRA微调
32B 模型：QLoRA勉强可行
70B 模型：QLoRA + 4bit + 所有优化手段，极限情况

我的实际经验：

在法律助手项目中，我们用的是 Qwen3-32B + QLoRA，单卡24G显存（RTX 3090）完全跑得起来。配置如下：

  • 4bit量化（NF4）
  • LoRA rank=16，target_modules=全部linear层
  • batch_size=1，gradient_accumulation_steps=8
  • 启用梯度检查点
  • 混合精度训练（bf16）

训练效率：约3-5秒/step，一个epoch（2000条数据）大概2-3小时。

如果非要训70B模型，我的建议：

  1. 先用QLoRA + 4bit量化，这是最省显存的方式
  2. 开启gradient_checkpointing + CPU offloading
  3. batch_size设为1，gradient_accumulation_steps加大
  4. 做好心理准备，训练速度会非常慢
  5. 更实际的做法：租用云GPU（A100 80G），或者用多卡分布式训练

总结： 24G卡训70B全参几乎不可行，但用QLoRA做高效微调是完全可行的。我建议根据实际需求选择更合适的模型大小，而不是盲目追求大模型。

205. 这个协作机制是LangGraph自带的还是你自己写的

回答：

两者结合——核心机制用LangGraph自带的，但业务逻辑和定制化部分是我自己实现的。

LangGraph自带的部分：

1. 状态管理（StateGraph）

LangGraph提供了StateGraph这个核心数据结构，用来管理Agent之间的状态流转。我直接用了这个框架：

from langgraph.graph import StateGraph, State

class AgentState(State):
    enterprise_info: dict
    matched_policies: list
    analysis_result: dict
    final_report: str

2. 节点和边的定义（Node/Edge）

LangGraph的节点（Node）和边（Edge）机制是现成的，我只需要定义节点函数和连接关系：

workflow = StateGraph(AgentState)

# 定义节点
workflow.add_node("info_collector", collect_enterprise_info)
workflow.add_node("policy_matcher", match_policies)
workflow.add_node("report_generator", generate_report)

# 定义边
workflow.add_edge("info_collector", "policy_matcher")
workflow.add_edge("policy_matcher", "report_generator")

3. 条件路由（ConditionalEdge）

条件判断的路由也是LangGraph自带的：

workflow.add_conditional_edges(
    "policy_matcher",
    should_ask_for_more_info,  # 自定义判断函数
    {
        "continue": "report_generator",
        "ask_more": "info_collector"  # 信息不足时回退
    }
)

我自己写的部分：

1. Agent的协作逻辑

每个Agent节点内部的业务逻辑是我自己实现的：

  • 信息采集Agent：调用企业信息API，整合多源数据，通过OpenAI的function calling来解析
  • 政策匹配Agent：结合Neo4j图查询和向量检索，实现混合检索策略
  • 报告生成Agent：整合匹配结果，生成结构化报告

2. 裁决机制（仲裁逻辑）

当多个Agent给出不同结论时，我写了一个仲裁模块：

  • 投票机制：相同结论数最多者胜出
  • 置信度加权：结合每个Agent的置信度评分
  • 人工介入阈值：当置信度低于0.6时，自动转人工

3. 持久化策略

LangGraph有基础的持久化层，但我根据自己的需求做了扩展：

  • 会话状态存到Redis，支持分布式部署
  • 长期记忆存到Milvus向量库，基于语义相似度做检索
  • 中间结果存到MySQL，方便回溯和排查

4. 监控和日志

LangGraph没有自带完善的监控，我加了一套：

  • 每个节点的执行耗时打点到Prometheus
  • 每一步的状态变化记录到日志
  • 异常情况自动告警

总结： LangGraph解决的是"Agent之间的通信和状态流转"这个通用问题，我写的部分解决的是"具体业务怎么做"这个特定问题。两者结合，既利用了框架的稳定性，又保留了业务灵活性。

206. 这两个项目你遇到的最大的困难是什么，如何解决的？

回答：

两个项目遇到的最大困难不同，我分别说一下。

法律助手项目——最大困难：PDF解析质量不稳定

问题描述：
法律文档格式极其复杂，有页眉页脚、表格、图片、手写批注、多栏排版等。用MinerU解析时，经常出现：

  • 表格内容错乱，单元格对应不上
  • 图片和文字分离，上下文丢失
  • 页眉页脚混入正文，影响切片质量

解决过程：

第一步：定位问题
我分析了200份解析失败的文档，归纳出几类问题：

问题类型 占比 原因
表格解析错乱 35% 复杂表格（合并单元格、跨页）
图文分离 25% 图片嵌入在段落中间
页眉页脚干扰 20% 页眉与正文语义相关
手写批注 15% 批注覆盖原文
其他 5% 编码问题、扫描件质量

第二步：分层治理

  1. 预处理层：在MinerU解析之前，先用OpenCV检测页眉页脚区域，提前裁剪掉
  2. 解析层：调优MinerU的参数，针对法律文档格式做定制化配置
  3. 后处理层：写了一套规则引擎，对解析结果做后处理修复
    • 表格修复：通过行列检测算法，重建表格结构
    • 图文关联：根据位置信息，将图片和附近文本关联
    • 连续性检测：段落断裂时自动合并

第三步：持续优化

法条召回率从68%提升到了94%，合规正确率从72%提升到了91%。这个优化过程持续了大概两周。

政策补贴系统——最大困难：多Agent协作的一致性问题

问题描述：
多个Agent各自分析企业信息，经常得出不一致的结论。比如：

  • 信息采集Agent说企业员工数500人，政策匹配Agent说需要看最新数据
  • 不同Agent对同一政策的理解不一致
  • 其中一个Agent出错，后续结果全错

解决过程：

1. 引入共享状态层
把所有Agent的中间结果集中到一个统一的状态管理器中，每个Agent操作前先读取最新状态，避免"各自为政"。

2. 增加裁决机制
当多个Agent结论不一致时：

  • 按Agent的置信度加权投票
  • 高置信度Agent的结论优先级更高
  • 仍不一致时，触发人工介入

3. 增强容错
每个Agent都有超时机制和重试逻辑：

  • 超时后自动回退到上一个稳定状态
  • 连续失败3次后告警并转人工

4. 建立评估集
创建了200+测试用例，覆盖各种企业场景，每次修改后自动回归测试，确保不会出现回归问题。

最终效果： 企业匹配准确率达到92%以上，匹配响应时间小于1.5秒。

207. LangGraph中持久化层的作用？

回答：

持久化层（Persistence Layer）在LangGraph中是一个非常重要的组件，它解决了Agent运行过程中的状态保存和恢复问题。

核心作用：

1. 状态持久化（State Persistence）

Agent在运行过程中会产生大量中间状态——各Agent的输入输出、决策步骤、工具调用结果等。持久化层把这些状态保存下来，而不是只存在内存中。这样：

  • Agent运行到一半崩溃了，重启后可以从断点恢复
  • 可以回看Agent的决策过程，方便调试和排查

2. 会话管理（Session Management）

在多轮交互场景中，持久化层负责管理会话上下文：

  • 每个会话有独立的ID
  • 保存历史对话记录
  • 支持会话的暂停、恢复、回溯

3. 断点续跑（Resumability）

这是最实用的功能。比如政策补贴系统中，匹配Agent需要查询多个政策库，可能耗时较长。如果中途网络中断，持久化层可以：

  • 保存已经完成的工作
  • 恢复时跳过错过的步骤
  • 避免重复计算

4. 并发控制（Concurrency Control）

多个用户的Agent同时运行时，持久化层保证：

  • 每个用户的会话隔离
  • 状态读写不冲突
  • 数据一致性

在政策补贴系统中的具体应用：

# 配置持久化层
from langgraph.checkpoint import MemorySaver
from langgraph.checkpoint.sqlite import SqliteSaver

# 使用SQLite做持久化（生产环境可以用PostgreSQL）
checkpointer = SqliteSaver.from_conn_string("checkpoints.db")

# 将持久化层注入到workflow
app = workflow.compile(checkpointer=checkpointer)

# 运行Agent时，指定会话ID
config = {"configurable": {"thread_id": "session_123"}}
result = app.invoke(input_data, config=config)

# 恢复会话
result = app.invoke(new_input, config=config)  # 自动从上次状态继续

持久化层存储的内容：

存储内容 说明 示例
节点状态 每个Agent节点的输出 info_collector的输出结果
图状态 整个工作流的全局状态 企业信息+匹配结果+报告
执行历史 每一步的执行记录 执行顺序、耗时、是否成功
检查点 可恢复的断点 异常中断时的状态快照

选择持久化方案时我的考虑：

方案 适用场景 优缺点
MemorySaver 开发调试 速度快，但不持久，重启丢失
SqliteSaver 单机部署 简单可靠，适合小规模
PostgresSaver 生产环境 分布式，支持高并发
RedisSaver 高并发场景 速度快，但有数据丢失风险

总结： 持久化层让Agent从"一次性的脚本"变成了"可管理、可恢复、可追踪的工作流"，在生产环境中必不可少。

208. 持久化层的分类？

回答：

LangGraph的持久化层可以从两个维度来分类——按存储介质和按作用范围。

一、按存储介质分类

1. 内存型（In-Memory）

from langgraph.checkpoint import MemorySaver
saver = MemorySaver()
  • 特点：速度快，数据存在内存中
  • 缺点：进程重启后数据丢失
  • 适用场景：开发调试、测试环境

2. 文件型（File-based）

from langgraph.checkpoint.sqlite import SqliteSaver
saver = SqliteSaver.from_conn_string("checkpoints.db")
  • 特点：持久化到本地文件，简单可靠
  • 缺点：不适合分布式部署
  • 适用场景：单机部署、小规模应用

3. 数据库型（Database）

from langgraph.checkpoint.postgres import PostgresSaver
saver = PostgresSaver.from_conn_string("postgresql://user:pass@host/db")
  • 特点：支持分布式、高并发、数据安全
  • 缺点：需要额外维护数据库
  • 适用场景：生产环境、多用户并发

4. 缓存型（Cache-based）

from langgraph.checkpoint.redis import RedisSaver
saver = RedisSaver.from_redis_client(redis_client)
  • 特点：极快读写速度，支持过期策略
  • 缺点：数据有丢失风险（除非配置持久化）
  • 适用场景：高并发、低延迟要求

二、按作用范围分类

1. 会话级持久化（Session Level）

每个会话（thread_id）独立存储状态：

  • 不同用户的会话互不干扰
  • 支持多轮对话
  • 可以按会话ID查询历史

2. 工作流级持久化（Workflow Level）

保存整个工作流的执行轨迹：

  • 记录了从开始到结束的完整路径
  • 可以回放debug
  • 支持断点续跑

3. 节点级持久化（Node Level）

每个节点（Agent）的输出单独保存：

  • 可以查看单个Agent的执行结果
  • 定位问题更精确
  • 支持部分回滚

三、按功能特性分类

1. 基础持久化（Base Checkpoint）

只保存状态快照：

  • 简单可靠
  • 但不支持高级功能

2. 时间旅行持久化（Time Travel）

支持回溯到任意历史节点：

  • 可以查看Agent在任意时刻的状态
  • 支持"what if"分析
  • 适合调试复杂工作流

3. 异步持久化（Async Checkpoint）

支持异步写入，不阻塞主流程：

  • 性能更好
  • 适合高吞吐场景
  • 但最终一致性需要处理

在实际项目中如何选择：

开发环境 → MemorySaver（简单快速）
单机部署 → SqliteSaver（可靠够用）
生产环境 → PostgresSaver（分布式+安全）
高并发 → RedisSaver（性能优先）

我的选择： 政策补贴系统用的 PostgresSaver + RedisSaver 的组合。Postgres存持久化数据和历史记录，Redis做热缓存加速状态读取。

209. LangGraph还有什么持久化策略？

回答：

除了前面提到的基础持久化方案，LangGraph还有一些更高级的持久化策略，适合不同的业务场景。

1. 自定义持久化（Custom Checkpointer）

如果内置方案不能满足需求，可以实现Checkpointer接口：

from langgraph.checkpoint import BaseCheckpointSaver

class CustomSaver(BaseCheckpointSaver):
    def put(self, config, checkpoint, metadata):
        # 自定义写入逻辑
        my_storage.save(checkpoint)
    
    def get(self, config):
        # 自定义读取逻辑
        return my_storage.load(config)
    
    def list(self, config, filter=None, before=None, limit=None):
        # 自定义查询逻辑
        return my_storage.query(config, filter, limit)

2. 增量持久化（Incremental Checkpointing）

每次只保存变化的部分，而不是全量快照：

  • 节省存储空间
  • 减少写入时间
  • 适合状态变化频繁但每次变化量小的场景

3. 压缩持久化（Compressed Checkpointing）

对保存的状态做压缩处理：

  • 使用gzip/zlib压缩大状态
  • 减少存储成本
  • 适合状态中包含大量文本或长上下文的场景

4. 分片持久化（Sharded Checkpointing）

把状态按key分片存储到不同的存储节点：

  • 支持水平扩展
  • 避免单点瓶颈
  • 适合超大规模并发

5. 版本化持久化（Versioned Checkpointing）

每次状态变化都保存版本号：

v1 → v2 → v3 → v4
  • 支持版本回退
  • 可以对比不同版本的状态差异
  • 方便审计和追溯

6. TTL自动过期策略

结合Redis或MongoDB的TTL功能：

  • 设置状态过期时间（如7天）
  • 自动清理过期状态
  • 减少存储压力

7. 混合持久化策略（Hybrid Strategy）

这其实是我在政策补贴系统中实际用的方案：

热数据（当前会话）：Redis
温数据（近7天）：PostgreSQL
冷数据（7天以上）：对象存储（S3/MinIO）

各层的作用：

  • Redis层：处理高并发的状态读写，毫秒级响应
  • PostgreSQL层：存储完整的会话历史，支持复杂查询
  • 对象存储层：归档历史会话，低成本存储

8. 按需加载策略（Lazy Loading）

不是所有状态都一次性加载到内存：

  • 加载当前节点需要的状态
  • 其他状态按需加载
  • 减少内存占用

实际应用场景举例：

场景一：长对话的断点续传
法律助手项目中，用户可能在一个对话中问几十个问题。使用增量持久化，每次只保存新问题和回答，而不是整个对话历史。

场景二：多用户并发
政策补贴系统可能有多个用户同时使用。使用分片持久化，把不同用户的会话分到不同的存储节点。

场景三：调试和审计
使用版本化持久化，可以回溯Agent的每一步决策，方便排查问题。

总结： 选择持久化策略时，要根据业务场景来权衡。没有万能的方案，但可以组合使用多种策略来满足不同需求。

210. 稠密检索和稀疏检索的区别？

回答：

这是一个非常关键的检索问题。在现代RAG系统中，稠密检索和稀疏检索是两种主流的检索方式，它们各有优劣，互补使用效果最好。

一、核心区别

维度 稠密检索（Dense Retrieval） 稀疏检索（Sparse Retrieval）
表示方式 用密集向量表示（如768维浮点数） 用稀疏向量表示（高维但大部分为0）
代表方法 向量嵌入（Embedding） BM25、TF-IDF
匹配方式 语义匹配 关键词匹配
计算方式 向量相似度（余弦/点积） 词频统计+逆文档频率
对同义词的处理 能识别"轿车"和"汽车"是同类 无法识别，需要精确匹配
对专业术语 需要训练/微调 自然支持精确匹配
冷启动 需要训练Embedding模型 不需要训练，直接用统计方法

二、具体实现

稀疏检索（BM25）

# 基于词频统计
"法律助手提供法律咨询" → {
  "法律": 2, "助手": 1, "提供": 1, "咨询": 1
}
  • 优点：简单、快速、可解释、精确匹配
  • 缺点：无法处理语义相似、同义词问题

稠密检索（Embedding）

# 基于语义向量
"法律助手提供法律咨询" → [0.12, -0.34, 0.56, ..., 0.78]  # 768维向量
  • 优点：语义理解能力强、支持同义词、跨语言
  • 缺点：需要训练模型、计算量大、"黑盒"不可解释

三、各自的问题

稠密检索的痛点：

  • 领域偏差：通用Embedding模型在专业领域（法律、医疗）效果差
  • 低频词问题：罕见的专业术语，向量表示可能不准确
  • 无法精确匹配：检索"民法典第123条"和"民法典第124条"语义相近，但完全是两回事

稀疏检索的痛点：

  • 语义鸿沟：用户问"打官司"但文档写的是"诉讼"，匹配不上
  • 同义词问题：无法理解"公司"和"企业"是一个意思
  • 长文档劣势：长的文档词频高，但未必更相关

四、在项目中的实际应用——混合检索

在法律助手项目中，我用了混合检索（Hybrid Search），结合两者的优势：

# 混合检索策略
# 1. 稀疏检索（BM25）→ 精确匹配
# 2. 稠密检索（Embedding）→ 语义匹配
# 3. 融合（RRF/加权融合）

def hybrid_search(query, top_k=10):
    # 稀疏检索
    sparse_results = bm25_search(query, top_k=20)
    
    # 稠密检索
    dense_results = dense_search(query, top_k=20)
    
    # RRF融合
    combined = reciprocal_rank_fusion(
        sparse_results, 
        dense_results, 
        k=60  # RRF参数
    )
    
    return combined[:top_k]

融合策略：

融合方法 说明 适用场景
RRF（倒数排名融合） 按排名位置加权融合 通用场景
分数加权 按相似度分数线性融合 分数可比较时
级联检索 先BM25粗筛，再Embedding精排 性能优先

效果： 混合检索后，法条召回率从68%提升到94%，提升非常明显。特别是对于法律条款这种需要精确匹配的场景，BM25保证了精确匹配不丢，Embedding保证了语义相关的也召回。

五、总结

场景 推荐方案
精确匹配（法律条款、ID、代码） 稀疏检索为主
语义理解（问答、对话） 稠密检索为主
专业领域（法律、医疗、金融） 混合检索
资源受限 稀疏检索（无需GPU）
效果优先 混合检索+重排序

我的建议： 不要二选一，混合检索才是RAG系统的最佳实践。在法律助手项目中，我深有体会——只靠Embedding，很多精确匹配的条款会漏掉；只靠BM25，语义相关的内容又检索不到。两者结合，效果最好。
