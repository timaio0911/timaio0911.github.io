161. 你怎么用llamaindex做混合检索？

回答：

在法律助手项目中，我使用LlamaIndex来构建混合检索系统，它提供了非常便捷的抽象层。

混合检索的核心思路：

混合检索是将关键词检索和向量检索结合，取两者之长。LlamaIndex提供了内置的混合检索器，使用起来非常方便。

具体实现方式：

首先，我创建了两个索引：

  • 向量索引：使用MilvusVectorStore，将法律文档进行Embedding后存储
  • 关键词索引：使用BM25Retriever，建立倒排索引

然后，使用LlamaIndex的QueryFusionRetriever将两者融合。它支持多种融合策略，我选择的是相对分数融合（Relative Score Fusion），这种方式会将两种检索器的分数归一化后合并。

实际配置：

在法律助手中，我的配置是：

  • 向量检索返回Top-10
  • 关键词检索返回Top-10
  • 融合后保留Top-10
  • 最后交给Reranker重排序，输出Top-5

效果对比：

相比单一的向量检索，混合检索的法条召回率从85%提升到了92%。特别是对于包含精确法律术语的查询，关键词检索能补充向量检索的不足。

为什么选择LlamaIndex：

LlamaIndex的优势在于它封装了很多复杂细节，提供了统一的接口。我不需要自己实现BM25算法，也不需要手动处理分数融合，直接调用现成的组件就行。这大大提高了开发效率。

162. 我想知道你搭建整个知识图谱的完整详细过程

回答：

在政策补贴项目中，我搭建了企业政策补贴知识图谱，包含8类实体、12种关系、500+政策、3000+条件节点。完整过程如下：

第一步：需求分析和本体设计

首先要明确知识图谱要解决什么问题。在政策补贴场景中，核心需求是：给定企业信息，能快速找到匹配的补贴政策。

基于这个需求，我设计了本体（Ontology）：

  • 实体类型：企业、政策、行业、地区、补贴类型、申请条件、资质要求、主管部门
  • 关系类型：企业-属于->行业，政策-适用于->行业，政策-包含->申请条件，企业-满足->申请条件等

第二步：数据收集和结构化

从政府网站、政策文件中收集补贴政策数据。每份政策需要提取：

  • 政策名称、发布部门、发布时间
  • 适用行业、适用地区
  • 申请条件（可能有多个）
  • 补贴金额、申请流程

这个过程我结合了规则提取和大模型抽取。对于结构化程度高的政策文件用规则，对于非结构化的用Qwen-plus进行信息抽取。

第三步：实体识别和关系抽取

使用NLP技术从文本中识别实体和关系：

  • 实体识别：使用命名实体识别（NER）模型，结合法律领域的词典
  • 关系抽取：使用大模型进行关系分类，判断实体之间的关系类型

第四步：知识存储

使用Neo4j作为图数据库，将实体和关系导入。Neo4j的Cypher查询语言非常适合图谱的查询和遍历。

第五步：知识融合和消歧

不同来源的数据可能存在冲突或重复，需要进行融合：

  • 实体对齐：将同一实体的不同表述合并
  • 关系消歧：解决关系冲突
  • 冲突检测：发现矛盾的信息并人工确认

第六步：图谱应用

在政策匹配流程中，当用户输入企业信息后，系统会在图谱中进行游走，找到企业满足的所有条件，然后匹配包含这些条件的政策。相比传统的关键词匹配，图谱游走能更好地处理复杂的条件组合逻辑。

通过这套知识图谱，企业匹配准确率达到了92%以上，响应时间控制在1.5秒以内。

163. 一个项目的时间周期比较紧张，然后又遇到了问题，作为专业的AI工程师你会怎么去做（不结合项目，只要方案）

回答：

这是AI项目中非常常见的情况，我的处理思路是"快速定位、最小代价、分层解决"。

第一步：快速评估问题影响

首先要判断问题的严重程度：

  • 是否阻塞核心功能？
  • 影响范围有多大？
  • 是否有临时绕过方案？

根据评估结果，决定处理优先级。如果是阻塞性问题，必须立即解决；如果是边缘问题，可以记录后继续推进。

第二步：缩小问题范围

快速定位问题根源：

  • 是数据问题？（数据质量、数据缺失）
  • 是模型问题？（效果不达标、推理错误）
  • 是工程问题？（接口异常、性能瓶颈）
  • 是流程问题？（上下游不匹配）

通过日志、监控、测试快速缩小排查范围。

第三步：选择最小代价方案

时间紧张时，不要追求完美方案，而是选择"够用"的方案：

  • 数据问题：优先补充关键数据，边缘数据可以后续处理
  • 模型问题：考虑Prompt优化、Reranker调整等快速见效的方案
  • 工程问题：先用临时方案保证功能可用，后续再优化架构

第四步：并行处理

如果问题复杂，可以将任务拆分并行处理：

  • 一边排查问题，一边准备备选方案
  • 一边修复当前问题，一边预防类似问题

第五步：建立反馈循环

修复后要快速验证效果，并收集反馈：

  • 部署后立即监控关键指标
  • 收集用户反馈
  • 准备回滚方案

总结：

核心原则是"先保上线，再优化"。在时间压力下，AI工程师需要有快速决策和权衡的能力，不能陷入追求完美的陷阱。

164. rag的数据集是结构化还是非结构化

回答：

在法律助手项目中，RAG的数据集主要是非结构化数据，但也包含部分结构化数据。

非结构化数据：

这是RAG系统的主要数据来源，包括：

  • 法律法规全文（如《劳动法》《劳动合同法》）
  • 司法解释文本
  • 典型案例判决书
  • 法律文书模板

这些数据的特点是自由文本形式，没有固定的字段和格式。

结构化数据：

也有一部分结构化数据，主要用于精确查询：

  • 法律条文索引（法律名称、条款编号）
  • 案例元数据（案号、审判法院、判决日期）
  • 文书模板字段（模板名称、适用场景）

为什么需要混合：

纯非结构化数据的RAG存在局限：

  • 无法进行精确的条件筛选（比如"查找2023年发布的司法解释"）
  • 结果可能包含大量噪声
  • 对于特定格式的查询效果不好

所以在我的系统中，采用的是"结构化筛选 + 非结构化检索"的混合方案：

  1. 先通过MySQL进行结构化筛选（法律名称、发布时间等）
  2. 再通过Milvus进行语义检索
  3. 最后合并结果并重排序

这样既能保证精确查询的准确性，又能发挥语义检索的召回能力。

数据预处理：

对于非结构化数据，需要进行切片处理。我会根据法律文本的特点，以"条"为单位进行切分，同时保留上下文信息（法律名称、章节标题等），确保每个切片都是完整、可理解的。

165. rag构建怎么划分chunk

回答：

切片策略是RAG系统的核心环节，直接影响检索质量。在法律助手中，我的切片策略经过了多轮优化。

基本原则：

切片要满足三个条件：

  1. 语义完整性：每个切片表达一个完整的意思
  2. 适度长度：不能太短（缺乏上下文）也不能太长（引入噪声）
  3. 可检索性：切片内容要能被有效检索

法律文本的切片策略：

针对法律文本的特殊性，我采用"层级切片"策略：

第一层：以"条"为基本单位。法律条文通常以"第X条"开头，这是天然的语义边界。

第二层：处理长条款。如果单条内容超过512 tokens，会进一步按"款"进行拆分。比如"第X条"下有多个款项，会拆成多个切片。

第三层：保留上下文信息。每个切片都会附加元数据：

  • 法律名称（如"劳动合同法"）
  • 章节标题（如"第三章 劳动合同的解除和终止"）
  • 条款编号（如"第四十七条"）

切片大小选择：

我设置的切片参数是：

  • 最小切片：50 tokens（避免过短片段）
  • 最大切片：512 tokens（避免上下文过长）
  • 重叠：50 tokens（保持上下文连续性）

这个参数是通过实验确定的。太小会导致信息碎片化，太大会引入噪声。

效果验证：

通过这套切片策略，法条召回率从68%提升到了94%。特别是对于复杂的法律问题，能够准确定位到相关条款，而不是返回大段无关内容。

迭代优化：

切片策略需要持续优化。我会定期分析检索失败的case，看是否是切片边界不合理导致的，然后调整切片规则。

166. 是否了解非串行的多agent架构

回答：

了解。非串行的多Agent架构是指多个Agent可以并行执行、相互协作，而不是简单的线性调用。

串行 vs 非串行：

串行架构：Agent A → Agent B → Agent C，依次执行，后面的Agent必须等前面的完成。

非串行架构：多个Agent可以同时执行，或者根据条件动态路由。

常见的非串行架构：

1. 并行架构（Fan-out/Fan-in）

多个Agent并行处理不同子任务，最后汇总结果。比如在政策补贴系统中，可以同时调用：

  • Agent A：查询企业基本信息
  • Agent B：查询行业相关政策
  • Agent C：查询地区相关政策

三个Agent并行执行，最后将结果合并。

2. 动态路由架构

根据输入内容，动态选择不同的Agent处理。比如：

  • 如果用户问法律问题，路由到法律专家Agent
  • 如果用户问政策问题，路由到政策专家Agent
  • 如果用户问程序问题，路由到技术支持Agent

3. 协作架构

多个Agent相互对话，共同完成任务。比如一个Agent负责生成方案，另一个Agent负责审核，通过多轮对话达成共识。

在政策补贴项目中的实践：

我在政策补贴系统中使用了LangGraph构建非串行架构。当用户输入企业信息后：

  1. 路由Agent判断需要哪些信息
  2. 并行调用企业画像Agent、政策检索Agent、条件验证Agent
  3. 汇总Agent将结果合并，生成最终答案

这种非串行架构相比串行执行，响应时间缩短了约40%，同时提高了系统的并发处理能力。

167. 处理两万条数据，想要模型回答一下结果，多进程快还是多线程快

回答：

这个问题需要根据具体的任务类型来判断。

多进程 vs 多线程的本质区别：

多线程：共享内存，适合I/O密集型任务。Python由于GIL（全局解释器锁）的存在，多线程无法实现真正的并行计算。

多进程：独立内存，适合CPU密集型任务。每个进程有独立的Python解释器，可以充分利用多核CPU。

对于大模型推理场景：

处理两万条数据需要调用大模型，这属于I/O密集型任务（等待网络请求返回），所以：

多线程更快

原因：

  1. 大模型推理主要时间花在网络等待上，而不是本地计算
  2. 多线程可以同时发起多个请求，充分利用等待时间
  3. 内存开销小，可以创建大量线程

实际方案：

在法律助手项目中，我处理类似批量任务时，使用的是异步IO（asyncio）+ 信号量控制并发数。

具体做法：

  • 使用aiohttp发起异步HTTP请求
  • 设置并发数为50（根据API限制调整）
  • 使用信号量控制并发，避免请求过多被限流

性能对比：

在我测试中，处理两万条数据：

  • 串行执行：约3小时
  • 多线程（50并发）：约20分钟
  • 多进程（50进程）：约25分钟（有进程创建开销）

注意事项：

  1. 并发数不是越高越好，需要考虑API的QPS限制
  2. 需要处理异常重试，避免个别请求失败导致整体中断
  3. 需要有进度监控，了解执行状态

总结：

对于大模型推理这种I/O密集型任务，多线程（或异步IO）比多进程更快。但如果任务包含大量本地计算（如数据预处理），则多进程可能更优。

168. 多agent有什么嵌入时间么

回答：

多Agent系统的延迟（嵌入时间）主要来自几个方面：

1. Agent调度开销

每次调用Agent都有固定的调度开销，包括：

  • 状态序列化和反序列化
  • 消息传递
  • 上下文加载

在LangGraph中，这个开销通常在毫秒级别。

2. 大模型推理时间

这是最主要的延迟来源。每个Agent调用大模型进行推理，通常需要几百毫秒到几秒。

在政策补贴系统中，单次大模型调用平均需要300-500毫秒。

3. 工具调用时间

Agent调用外部工具（如数据库查询、API调用）也需要时间。

比如查询Milvus向量库通常需要50-100毫秒，查询Neo4j图数据库需要30-80毫秒。

4. 网络传输时间

如果Agent分布在不同服务器上，网络传输也会增加延迟。

优化策略：

1. 并行执行

对于独立的Agent任务，可以并行执行，减少总延迟。比如同时调用三个Agent，总时间等于最慢的那个，而不是三者之和。

2. 缓存机制

对于重复查询，使用Redis缓存结果，避免重复计算。

在法律助手中，我设置了查询缓存，相同问题的响应时间从500毫秒降低到50毫秒。

3. 流式输出

采用流式输出，用户可以边看边等待，降低感知延迟。

4. 预计算

对于可以预计算的结果，提前计算并缓存。

实际数据：

在政策补贴系统中，完整的多Agent流程（3个Agent协作）平均响应时间为1.5秒以内，其中：

  • Agent调度：约50毫秒
  • 大模型推理：约800毫秒
  • 工具调用：约200毫秒
  • 网络传输：约100毫秒
  • 其他：约350毫秒

通过优化，响应时间控制在1.5秒以内，用户体验是可以接受的。

169. 你了解什么agent架构，举例几个

回答：

我了解多种Agent架构，根据不同的应用场景选择合适的架构。

1. ReAct架构

这是最经典的Agent架构，结合推理（Reasoning）和行动（Acting）。

工作流程：思考 → 行动 → 观察 → 思考 → …

适用于需要多步推理和工具调用的场景。在法律助手中，用户提问后，Agent会先思考需要查询什么，然后调用检索工具，观察结果，再决定是否需要继续查询。

2. Plan-and-Execute架构

先制定计划，再执行。

工作流程：规划阶段生成任务列表 → 执行阶段依次完成 → 汇总结果

适用于复杂任务需要拆解的场景。比如政策补贴匹配，先规划需要收集哪些信息，然后逐步收集和验证。

3. 多Agent协作架构

多个Agent分工协作。

常见模式：

  • 主从模式：一个主Agent协调多个子Agent
  • 对等模式：Agent之间平等协作
  • 分层模式：不同层级的Agent负责不同抽象层次的任务

在政策补贴系统中，我使用的是主从模式，主Agent负责任务分配和结果汇总，子Agent负责具体的查询和验证。

4. 反思架构（Reflection）

Agent会反思自己的输出，进行自我修正。

工作流程：生成 → 评估 → 修正 → 生成

适用于对质量要求高的场景。比如法律文书生成，先生成初稿，然后自我审查，发现不合规的地方进行修正。

5. 人机协作架构

Agent和人类用户交互协作。

工作流程：Agent执行 → 遇到不确定 → 请求人类确认 → 继续执行

适用于需要人类判断的场景。在法律咨询中，对于风险较高的建议，Agent会请求用户确认后再给出最终答案。

在项目中的选择：

我在两个项目中使用了不同的架构：

  • 法律助手：ReAct架构 + 反思机制，保证答案质量
  • 政策补贴系统：多Agent协作架构，处理复杂的匹配逻辑

选择架构时，主要考虑任务复杂度、质量要求、响应时间要求等因素。

170. 你怎么保证你用ai生成的代码符合生产规范呢，不论什么ai工具（claude code，cursor）

回答：

这是一个非常重要的问题。AI生成的代码确实需要严格的验证流程，我在项目中建立了一套完整的质量保证体系。

第一步：明确规范要求

在使用AI生成代码前，首先要明确生产规范：

  • 代码风格规范（PEP8、类型注解等）
  • 安全规范（输入验证、SQL注入防护等）
  • 性能规范（内存使用、响应时间等）
  • 测试规范（单元测试覆盖率、集成测试等）

把这些规范写成Prompt的一部分，让AI生成代码时遵循。

第二步：代码审查

AI生成的代码必须经过人工审查：

  • 逻辑正确性：检查业务逻辑是否正确
  • 边界条件：检查异常处理、边界情况
  • 安全性：检查是否有安全漏洞
  • 可维护性：检查代码是否清晰易懂

我在项目中会要求团队成员对AI生成的代码进行Code Review，不直接使用。

第三步：自动化测试

AI生成的代码必须有配套的测试：

  • 单元测试：测试函数级别的正确性
  • 集成测试：测试模块之间的交互
  • 端到端测试：测试完整的业务流程

在法律助手中，我设置了CI/CD流水线，每次代码提交都会自动运行测试，确保质量。

第四步：静态分析

使用工具进行静态代码分析：

  • Lint工具：检查代码风格
  • 类型检查：使用mypy检查类型错误
  • 安全扫描：检查常见安全漏洞

这些工具可以自动化运行，发现问题及时反馈。

第五步：逐步验证

不要一次性生成大量代码，而是分步骤验证：

  • 先生成核心逻辑，验证正确
  • 再生成辅助功能，逐步完善
  • 每一步都要测试通过后再进行下一步

实际案例：

在法律助手中，我使用AI生成了一个检索模块的代码。按照上述流程：

  1. 先明确检索模块的接口规范
  2. AI生成初版代码
  3. 人工审查发现几个边界条件问题
  4. 修改后补充单元测试
  5. 测试通过后才集成到项目中

通过这套流程，AI生成的代码质量得到了保证，生产环境没有出现因为AI代码导致的严重问题。

总结：

核心原则是"AI生成 + 人工把关 + 自动化验证"。AI可以提高效率，但不能替代工程师的判断和责任。
