面试模拟 - 第七组（61-70题）

基于简历项目经历，模拟面试回答

61. 词向量化用的什么模型?

回答：

在我的项目中，词向量化主要用的是阿里的 text-embedding-v3 模型。

选择原因：

第一，text-embedding-v3是专门为中文场景优化的模型，在中文语义理解上效果非常好，这对于法律助手和政策补贴系统这类中文为主的场景非常关键。

第二，它支持变长输入，最大支持8192个token，能够处理较长的法律条文和政策文档，不需要做过多的截断处理。

第三，和Qwen系列模型同属阿里生态，兼容性好，调用方便，延迟低。

在项目中的应用：

在法律助手项目中，我用text-embedding-v3对法律条文进行向量化，存储到Milvus向量数据库中。用户查询时，先将查询文本向量化，再做相似度检索。整个流程是：用户提问 -> text-embedding-v3向量化 -> Milvus检索 -> 返回Top-K结果。

补充说明：

除了text-embedding-v3，我也了解其他主流的embedding模型，比如OpenAI的text-embedding-ada-002、BGE系列、M3E等。选择text-embedding-v3主要是因为它在中文法律领域的表现和我的项目需求最匹配。

62. 状态的一致性如何处理？

回答：

状态一致性是多Agent系统中的核心问题，在我的政策补贴系统中，我主要通过以下几个方式来保证：

第一，使用LangGraph的状态管理机制：

LangGraph提供了内置的State对象，所有Agent共享同一个状态树。每个节点执行完后，通过返回值更新状态，LangGraph会自动保证状态的原子性更新。

第二，设计清晰的状态Schema：

我用Pydantic定义了严格的状态数据结构，包括企业信息、匹配结果、置信度等字段。这样可以确保每个Agent写入的数据格式一致，避免状态混乱。

第三，引入检查点机制：

LangGraph支持checkpoint，我在关键节点设置检查点，比如信息收集完成后、匹配完成后各保存一次状态。这样即使某个节点出错，也可以从检查点恢复，而不是从头开始。

第四，异步操作的处理：

由于FastAPI是异步框架，多个Agent可能并发执行。我使用asyncio的锁机制来保护共享状态，确保同一时间只有一个Agent在修改关键状态。

实际效果：

通过这些措施，我的系统能够处理复杂的多轮交互，企业匹配准确率达到92%以上，没有出现过状态不一致导致的错误匹配。

63. 意图识别怎么处理的？

回答：

意图识别是对话系统的第一步，在我的项目中主要用大模型来做，具体方案如下：

在政策补贴系统中的实现：

我设计了一个专门的意图识别Agent，使用Qwen-plus作为底层模型。通过精心设计的Prompt，让模型从用户输入中提取关键意图，比如"查询补贴政策"、“匹配企业资质”、"申请流程咨询"等。

Prompt设计要点：

我采用了Few-shot的方式，在Prompt中给出几个意图分类的示例，让模型学习分类标准。同时定义了输出格式为JSON，包含intent（意图）、confidence（置信度）、entities（实体）三个字段。

置信度阈值机制：

当模型返回的置信度低于0.7时，我会让Agent主动追问用户，确认真实意图。比如用户说"我想了解一下"，系统会追问"您是想了解补贴政策内容，还是想了解申请流程呢？"

在法律助手中的实现：

法律助手的意图识别相对简单，主要是区分"法条查询"、“案例分析”、"合规咨询"三类。我用关键词匹配做初筛，再用大模型做精筛，这样既快又准。

效果：

意图识别准确率达到95%以上，有效避免了后续流程的误判。

64. 假设你做一个金融分析助手项目中的节点怎么设计的？

回答：

如果做金融分析助手，我会参考我在政策补贴系统中的多Agent架构，设计以下核心节点：

第一，用户交互节点：

负责接收用户问题，进行意图识别和实体提取。比如识别出用户想"分析某公司财报"、"对比行业数据"等意图。

第二，数据采集节点：

根据用户需求，从不同数据源获取信息。金融数据可能来自Wind、东方财富、公司公告等。这个节点需要设计多个子Agent，分别对接不同数据源。

第三，数据清洗节点：

金融数据格式多样，有表格、PDF、网页等。这个节点负责统一格式、处理缺失值、异常值检测等。

第四，分析计算节点：

核心分析逻辑，包括财务指标计算（ROE、PE、现金流等）、趋势分析、同行业对比等。可以用预定义的分析模板，也可以让大模型生成分析代码。

第五，风险评估节点：

基于分析结果，给出风险提示和投资建议。需要结合监管政策、市场情绪等多维度信息。

第六，报告生成节点：

将分析结果整理成结构化报告，可以用图表、表格等形式呈现。

状态设计：

我会用一个中心化的State对象存储所有中间结果，包括原始数据、清洗后数据、分析结论、风险评级等，确保各节点之间的数据流转清晰。

65. 怎么避免路由死循环，陷入死循环该怎么办？

回答：

路由死循环是Agent系统中的常见问题，我在政策补贴系统中遇到过并解决了这个问题。

预防措施：

第一，设置最大跳转次数：

我在LangGraph中设置了全局的max_steps参数，比如最多允许10次节点跳转。超过这个次数强制进入终止节点，返回当前最优结果。

第二，状态标记机制：

每次Agent执行后，会在状态中标记已访问的节点。路由逻辑会检查目标节点是否已访问过，避免重复进入同一节点。

第三，设计清晰的退出条件：

每个节点都有明确的完成条件，比如信息收集Agent必须拿到完整的企业信息才能进入下一阶段，否则只能追问或退出。

陷入死循环后的处理：

第一，超时检测：

设置单个节点的最大执行时间，比如30秒。超时后强制中断，进入降级流程。

第二，兜底返回：

如果检测到死循环，系统会返回当前已收集到的最佳结果，并提示用户"信息不足，建议补充以下内容"。

第三，日志告警：

记录死循环的详细日志，包括触发条件、节点路径等，方便后续优化路由逻辑。

实际案例：

在政策补贴系统中，企业信息收集Agent曾因为用户回答模糊而反复追问。我加入了"最多追问3次"的限制，并在第3次追问后给出默认选项让用户选择，有效避免了死循环。

66. react怎么跳出闭环？

回答：

ReAct（Reasoning + Acting）模式是Agent的核心工作方式，跳出闭环需要从机制设计上解决。

ReAct的基本循环：

思考（Thought）-> 行动（Action）-> 观察（Observation）-> 再思考… 这个循环如果没有终止条件，确实会陷入死循环。

跳出闭环的策略：

第一，设置最大推理轮次：

我在实现中设置了max_iterations参数，比如最多允许5轮思考-行动循环。达到上限后，Agent必须基于当前信息给出最终回答。

第二，设计明确的终止信号：

当Agent的Thought中包含"我已经获得足够信息"、"可以回答用户问题"等关键词时，强制结束循环。也可以用大模型判断当前信息是否充足。

第三，引入置信度评估：

每轮循环后评估当前答案的置信度，如果置信度超过阈值（比如0.85），提前结束循环。

第四，超时机制：

设置整体执行的超时时间，比如60秒。超时后强制返回当前最佳答案。

在项目中的应用：

在法律助手项目中，ReAct模式用于法条检索。Agent会思考用户问题涉及哪些法律领域，然后调用检索工具，观察检索结果，再决定是否需要调整检索策略。我设置了最多3轮检索，3轮后必须给出答案，避免无限循环。

67. FastAPI异步具体是如何实现的

回答：

FastAPI的异步实现基于Python的asyncio框架和ASGI协议，我在项目中大量使用了异步特性。

核心实现原理：

第一，事件循环机制：

FastAPI底层使用uvicorn作为ASGI服务器，uvicorn会启动一个事件循环（Event Loop）。当遇到await关键字时，事件循环会挂起当前协程，去执行其他任务，等IO操作完成后恢复执行。

第二，协程（Coroutine）：

用async def定义的函数是协程函数，调用时不会立即执行，而是返回一个协程对象。只有await时才会真正执行。这样可以让IO密集型任务（如数据库查询、网络请求）不阻塞主线程。

第三，依赖注入的异步支持：

FastAPI的Depends支持异步依赖，比如数据库连接池、Redis客户端等都可以用异步方式注入。

在项目中的应用：

在政策补贴系统中，我用异步处理并发请求。比如同时调用Milvus查询和Neo4j查询时，用asyncio.gather并行执行，响应时间从串行的200ms降到并行的120ms左右。

代码示例：

async def get_policy_info(query: str):
    async with aiohttp.ClientSession() as session:
        milvus_task = search_milvus(query)
        neo4j_task = search_neo4j(query)
        results = await asyncio.gather(milvus_task, neo4j_task)
    return merge_results(results)

性能提升：

通过异步优化，系统QPS从50提升到200+，能够支持更多并发用户。

68. 介绍一下MySQL的开窗函数？

回答：

开窗函数（Window Function）是MySQL 8.0引入的重要特性，用于在不改变行数的情况下进行聚合计算。

核心概念：

开窗函数和GROUP BY的区别在于，GROUP BY会将多行合并为一行，而开窗函数保留所有原始行，在每行上计算聚合值。

常见开窗函数：

ROW_NUMBER()： 行号函数，给每行分配唯一的序号。比如按成绩排名：
ROW_NUMBER() OVER (ORDER BY score DESC) as rank

RANK()： 排名函数，相同值排名相同，但会跳过后续名次。比如两个第1名，下一个是第3名。

DENSE_RANK()： 密集排名，相同值排名相同，不跳过名次。两个第1名，下一个是第2名。

SUM/AVG/COUNT + OVER： 累计或滑动聚合。比如计算累计销售额：
SUM(amount) OVER (ORDER BY date) as cumulative_sales

PARTITION BY： 分区子句，按某个字段分组后计算。比如每个部门内部排名：
ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC)

在项目中的应用：

虽然我的项目主要用Redis做缓存，但在数据统计分析时会用到开窗函数。比如分析政策匹配成功率时，用ROW_NUMBER找出每个企业匹配度最高的政策；用SUM OVER计算累计匹配数量等。

69. MySQL和PostgreSQL的区别是什么？

回答：

MySQL和PostgreSQL是两个主流的关系型数据库，各有特点：

语法差异：

MySQL用反引号`包裹字段名，PostgreSQL用双引号"；MySQL的自增用AUTO_INCREMENT，PostgreSQL用SERIAL或IDENTITY；MySQL的LIMIT语法直接用LIMIT，PostgreSQL也支持但还可以用FETCH FIRST。

数据类型：

PostgreSQL支持更丰富的数据类型，比如数组、JSONB（二进制JSON，查询更快）、范围类型、几何类型等。MySQL的JSON支持相对较弱。

事务和锁：

PostgreSQL对事务支持更严格，默认隔离级别更高。MySQL的InnoDB引擎也支持事务，但某些场景下锁粒度不如PostgreSQL细。

扩展性：

PostgreSQL支持自定义函数、存储过程、触发器等更强大，适合复杂业务逻辑。MySQL在这方面相对简单。

性能：

MySQL在简单查询、高并发读场景下性能更好；PostgreSQL在复杂查询、大数据量分析场景下更有优势。

在我的项目中的选择：

我选择MySQL主要是因为政策补贴系统的查询相对简单，主要是单表查询和简单关联，MySQL的性能足够。而且MySQL的生态更成熟，运维工具更多。但如果后续要做复杂的统计分析，可能会考虑PostgreSQL。

70. Redis数据类型？

回答：

Redis支持五种基本数据类型，我在项目中都有使用：

String（字符串）：

最简单的类型，可以存储字符串、整数、浮点数。我在项目中用于缓存热点数据，比如用户会话信息、验证码、API限流计数等。支持原子性的incr操作，非常适合计数场景。

List（列表）：

双向链表结构，支持左右插入弹出。我用于实现消息队列，比如政策更新通知队列。LPUSH生产消息，RPOP消费消息，简单高效。

Hash（哈希）：

键值对集合，适合存储对象。我在项目中存储企业信息，比如hash key是"company:123"，field有"name"、“industry”、"scale"等。比String存储JSON更节省内存，也支持单个field的更新。

Set（集合）：

无序不重复集合，支持交集、并集、差集操作。我用于存储标签、去重场景。比如存储某个政策适用的行业标签，用SINTER可以快速找出两个政策的共同适用行业。

Sorted Set（有序集合）：

每个元素关联一个分数，按分数排序。我在项目中用于实现排行榜、优先级队列。比如政策匹配结果按相似度排序，用ZADD添加，ZREVRANGE获取Top-N。

补充：

Redis 5.0还引入了Stream类型，适合更专业的消息队列场景，但我目前项目中用List就够了。
