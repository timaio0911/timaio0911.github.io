面试模拟 - 第九组（81-90题）

基于简历项目经历，模拟面试回答

81. 知识图谱怎么和rag配合

回答：

知识图谱和RAG的配合本质上是"结构化知识"和"非结构化检索"的互补。

配合方式主要有三种：

1. 知识图谱增强检索（GraphRAG）
在政策补贴系统中，我们用Neo4j构建了包含8类实体、12种关系、500+政策、3000+条件节点的政策图谱。当用户提问"哪些企业可以申请研发补贴"时，传统RAG可能只检索到零散的政策条款，而知识图谱可以从"研发补贴"这个节点出发，沿着"申请条件"关系找到"高新技术企业认定"、"研发费用占比"等关联节点，再把这些结构化信息作为上下文补充给RAG。

2. 图谱提供实体关系用于查询改写
用户问"我们公司能拿什么补贴"，系统先从图谱中查询该企业的画像信息（行业、规模、资质），然后把查询改写成更精确的检索query，召回率从68%提升到94%。

3. 图谱做答案验证
RAG生成答案后，用图谱中的实体关系做交叉验证，确保答案中的政策条件、金额等信息与图谱一致，合规正确率从72%提升到91%。

82. 模型如果出现幻觉，为什么？怎么处理？

回答：

幻觉的根本原因是模型在"不确定"时仍然生成看似合理的回答，而不是说"我不知道"。

产生幻觉的典型场景：

  • 知识库没有覆盖的问题，模型会"脑补"
  • 检索到了相关但不精确的内容，模型过度推断
  • 多轮对话中上下文冲突，模型混淆信息

我们的处理方案（法律助手项目）：

1. 检索置信度阈值
设置相似度阈值0.7，低于这个分数的检索结果不传给模型，而是触发"知识库未覆盖"的兜底回复。

2. 答案溯源机制
每个回答必须标注引用的法条编号，如果模型无法给出具体来源，系统会提示"该回答仅供参考，建议查阅原文"。

3. 事实一致性校验
用另一个轻量模型对生成答案做二次校验，检查答案中的关键信息（金额、日期、条件）是否与检索到的原文一致。

4. 用户反馈闭环
上线后监控用户对答案的"有用/无用"反馈，持续优化检索策略和prompt。

这套方案实施后，实际幻觉率降低了约40%。

83. 你的多agent是什么架构？我看着像是固定的流程，那为什么不使用langchain？

回答：

我们用的是LangGraph实现的有状态图架构，不是LangChain的线性链。

架构设计：
政策补贴系统包含政策检索Agent、企业画像Agent、条件匹配Agent、报告生成Agent四个核心节点，通过LangGraph的状态图管理流转。

为什么不用LangChain而用LangGraph：

对比维度 LangChain LangGraph
执行模式 线性链式 状态图，支持分支和循环
状态管理 无内置状态 内置checkpoint，支持中断恢复
条件路由 需要自定义 原生支持条件边
人工介入 难以实现 支持interrupt_before节点

具体优势体现：

政策补贴匹配需要根据企业资质动态决定下一步——如果企业缺少高新技术认定，需要先走"资质预审"分支；如果已有认定，直接进入"条件匹配"。这种动态路由用LangGraph的条件边天然支持，用LangChain需要大量自定义逻辑。

另外，我们的流程涉及人工审核节点（政策解读确认），LangGraph支持在特定节点中断等待人工输入，完成后自动恢复，这对合规性审核场景很关键。

84. 你在rag开发中一定遇到了问题，是什么，怎么解决的？

回答：

确实遇到不少问题，印象最深的是切片策略导致的召回率瓶颈。

问题描述：
法律条文有很强的结构层级（编→章→节→条→款→项），最初用固定512token切片，导致：

  • 一个完整的法条被切成2-3个片段，检索到片段但缺失上下文
  • 召回率只有68%，很多问题检索不到相关法条

排查过程：

  1. 分析bad case，发现80%的失败case都与切片边界有关
  2. 对比不同切片大小（256/512/1024），发现都不理想

解决方案：
采用语义切片+层级切片混合策略：

  • 先按法条的自然边界（条、款）做一级切片
  • 对于超长条款，再用滑动窗口做二级切片，窗口有重叠
  • 保留层级元数据（编→章→节→条），检索时可以向上聚合上下文

效果：
法条召回率从68%提升到94%，这个优化是我们项目最重要的技术突破之一。

85. 多智能体开发遇到的难点有哪些？

回答：

难点一：状态一致性
多个Agent共享状态时，容易出现数据竞争。比如政策检索Agent和企业画像Agent同时更新"匹配条件"字段，会导致数据覆盖。

解决方案：用LangGraph的checkpoint机制，每次状态变更都序列化到Redis，Agent启动时加载最新状态。

难点二：上下文膨胀
Agent之间传递的上下文会越来越大，特别是包含检索结果时，容易超过模型的上下文窗口。

解决方案：设计上下文压缩节点，在Agent之间传递时做摘要压缩，只保留关键信息。

难点三：错误传播
上游Agent的错误会传递给下游。比如政策检索Agent返回了错误的政策编号，条件匹配Agent会基于错误信息做判断。

解决方案：每个Agent节点后加一个校验节点，检查输出格式和关键字段，异常时触发重试或人工介入。

难点四：调试困难
分布式Agent的日志分散，出问题时难以定位。

解决方案：用LangGraph的trace功能，记录每个节点的输入输出和执行时间，出问题时可以完整回放。

86. 你项目中向量化模型如何选择的？

回答：

我们用的是阿里的text-embedding-v3模型。

选择理由：

考量维度 具体情况
中文效果 在中文法律文本上效果最好，MTEB中文榜单排名靠前
维度 1024维，平衡了效果和存储成本
价格 比OpenAI的embedding便宜，且支持国内调用
延迟 平均响应50ms内，满足实时检索需求

选型过程：

  1. 调研了OpenAI text-embedding-3、智源BGE、阿里text-embedding-v3三个模型
  2. 用500条法律问题做benchmark，对比top-5召回率
  3. text-embedding-v3在法律领域召回率最高（94% vs BGE 91% vs OpenAI 89%）

实际使用：

  • 向量维度：1024
  • 存储：Milvus，使用IVF_FLAT索引
  • 批量入库：支持异步批量向量化，单次处理1000条文档

87. 短文本和长文本检索效果不好怎么优化？

回答：

短文本问题： 用户query太短（如"补贴"），语义信息不足，向量检索效果差。

优化方案：

  1. Query扩展：用大模型对短query做意图扩展，“补贴"→"企业可以申请的政策补贴有哪些，申请条件是什么”
  2. 混合检索：短query时提高BM25关键词检索的权重，长query时提高向量检索权重
  3. 标签检索：给知识库打标签，短query先匹配标签，缩小检索范围

长文本问题： 用户输入长段落，向量检索会丢失细节。

优化方案：

  1. 分块检索：长文本切成多个语义段，分别检索再合并结果
  2. 关键句提取：用LLM从长文本中提取关键句作为检索query
  3. 多粒度索引：同一文档建立句子级、段落级、文档级三层索引

实际效果：
优化后，短文本（<10字）召回率从45%提升到78%，长文本（>500字）召回率从62%提升到85%。

88. agent的设计模式是什么，有哪些？

回答：

常见的Agent设计模式有以下几种：

1. ReAct模式（推理+行动）
最经典的模式，Agent交替进行"思考"和"行动"。思考阶段分析问题，行动阶段调用工具，观察结果后再思考。我们法律助手的法律咨询功能就是这个模式。

2. Plan-and-Execute模式
先制定计划，再逐步执行。适合复杂任务分解。政策补贴系统的报告生成就是这个模式——先规划报告结构，再逐章节生成。

3. 反思模式（Reflection）
Agent生成答案后，再用另一个Agent审视答案质量，发现问题后修正。我们用在答案质量校验上。

4. 多Agent协作模式
多个专业Agent分工协作。政策补贴系统就是这个模式——政策检索、企业画像、条件匹配各由专门Agent负责。

5. 人机协作模式
关键节点引入人工审核。政策解读确认环节就是人工介入点。

选择依据：

  • 简单问答：ReAct
  • 复杂任务：Plan-and-Execute
  • 高质量要求：Reflection
  • 专业分工：多Agent协作
  • 合规场景：人机协作

89. langgraph怎么对中间状态进行绑定

回答：

LangGraph通过StateGraph和Checkpoint机制管理中间状态。

状态定义：
python class AgentState(TypedDict): messages: list current_step: str intermediate_results: dict

绑定方式：

1. 节点函数绑定
每个节点函数的第一个参数就是state，可以直接读写。比如政策检索节点从state读取用户query，检索完成后把结果写回state的intermediate_results字段。

2. Checkpoint持久化
在compile时配置checkpoint，状态会自动持久化到Redis。这样即使某个节点执行失败，也可以从checkpoint恢复，而不是从头开始。

3. 人工介入绑定
用interrupt_before或interrupt_after在特定节点暂停，等待人工输入后恢复。政策解读确认环节就是用这个机制。

实际应用：
政策补贴系统中，条件匹配节点会把中间匹配结果存入状态，如果后续节点发现匹配失败，可以回溯到中间状态重新计算，而不是从头开始。这大大提高了系统的容错能力。

90. 记忆这个功能是怎么实现的，长短期是怎么实现的？

回答：

短期记忆实现：

  • 存储位置：内存中的对话历史列表
  • 生命周期：单次会话，会话结束清空
  • 实现方式：维护一个messages列表，每次交互追加用户输入和AI回复
  • 容量限制：保留最近20轮对话，超出时摘要压缩

长期记忆实现：

  • 存储位置：Redis + Milvus
  • 生命周期：持久化，跨会话保留
  • 实现方式：
    1. 关键信息提取：用LLM从对话中提取关键实体、偏好、结论
    2. 向量化存储：关键信息向量化后存入Milvus
    3. 检索召回：新会话开始时，检索与当前问题相关的历史记忆

政策补贴系统中的具体应用：

记忆类型 存储 用途
对话历史 Redis 保持当前会话连贯性
企业画像 Neo4j 跨会话保留企业资质信息
匹配记录 Milvus 避免重复推荐已匹配政策

关键设计：

  • 短期记忆容量有限，只保留必要上下文
  • 长期记忆要定期清理过期信息，避免噪音干扰
  • 敏感信息脱敏后才存入长期记忆
