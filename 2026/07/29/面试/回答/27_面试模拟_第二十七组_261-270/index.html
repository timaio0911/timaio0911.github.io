面试模拟 - 第二十七组（261-270题）

基于简历项目经历，模拟面试回答

261. 选择子智能体的流程是什么

回答：

在我做的政策补贴智能匹配系统中，子智能体的选择流程是一个基于意图识别和任务拆分的路由决策过程，大概分三步走：

第一步：意图识别与任务解析。 当用户提问进来，先由入口的Supervisor Agent对问题进行理解，判断用户想做什么——是要查企业能申报什么补贴、还是想了解某个政策的申报条件、还是需要补全企业资料。这一步决定了后续需要调度哪些子智能体。

第二步：路由分发。 根据意图，Supervisor从注册的子智能体列表中选出合适的候选集。我们系统里注册了企业画像采集Agent、政策匹配Agent、条件审核Agent、材料生成Agent等几个子智能体。Supervisor会看当前任务的依赖关系——比如政策匹配必须先等企业画像采集完成，才能进行。

第三步：动态编排执行。 选好子智能体后，Supervisor通过LangGraph的StateGraph编排执行顺序。有些子智能体是串行的（因为依赖前一个的输出），有些是可以并行跑的（比如同时采集企业数据和政策数据）。执行过程中如果某个子智能体返回的状态异常，Supervisor会判断是重试、跳过还是终止整个流程。

举个例子： 用户说"我们公司是深圳的科技型中小企业，能申报什么补贴"，Supervisor先识别这是政策匹配需求，然后同时调度企业画像Agent（去采集这家企业的行业、规模、资质等信息）和政策检索Agent（去知识库搜深圳科技型中小企业相关的政策），等两个结果都回来后，再交给条件审核Agent做匹配计算。

262. 某个用户的画像是怎么存储的

回答：

这里说的"用户画像"在我政策补贴项目中，其实指的是企业画像，因为我们的用户是企业而不是个人。企业画像的存储我用了分层存储的策略：

第一层：结构化数据存在Neo4j图数据库。 企业的基本信息（名称、行业、成立时间、注册资金、经营状态等）作为节点属性，企业与政策、企业与资质之间的关系作为边。比如"深圳XX科技公司"是一个节点，通过"所属行业"边关联到"软件和信息技术服务业"节点，通过"可申报"边关联到"深圳市科技型中小企业认定"政策节点。用图存的好处是查询企业的关联信息非常快，做关系推理也方便。

第二层：非结构化/半结构化数据存在向量数据库（Milvus）。 企业的历史申报记录、审计报告、补充说明材料等文本类数据，切片后做embedding存入Milvus。当需要查"这家企业过去有没有申报过类似项目"时，通过向量相似度检索。

第三层：缓存层用Redis。 对于高频访问的企业画像数据（比如企业的基本信息、行业标签这些不常变化的字段），会缓存到Redis里，设置TTL自动过期，避免每次都要查图数据库。

更新机制： 企业画像不是一次性写死的。我们有一个企业画像采集Agent，会定期从企业填写的表单、上传的资质文件、以及第三方公开数据中更新画像信息，增量写入Neo4j和Milvus，同时失效Redis中对应的缓存。

263. rank模型得分是怎么算的

回答：

你说的是重排序（Rerank）环节的得分吧？在我法律助手项目中，检索完知识库后有一个重排序步骤，它的得分计算逻辑是这样的：

背景： 第一次检索（用BM25+向量混合检索）会召回Top-K个候选切片，比如Top-30。但这里面可能有些切片和问题相关性不高，需要用重排序模型重新打分，挑出最相关的Top-5或Top-3给大模型生成答案。

得分计算方式： 我们用的是基于交叉编码器（Cross-Encoder）的重排序模型，它的核心思路是把问题和候选切片拼接成一个序列[CLS]问题[SEP]切片[SEP]，然后通过Transformer编码，输出一个0到1之间的相关性分数。分数越高，说明和问题的相关性越强。

具体来说：

  • 输入是（问题，候选切片）的pair对
  • 模型会综合语义匹配、关键词匹配、上下文一致性等因素给出得分
  • 这个得分是有判别力的，不像向量检索的余弦相似度那样只是一个距离度量，Cross-Encoder直接建模了问题和切片之间的交互关系

我们为什么需要它？ 在项目初期，只用向量检索时，发现有些切片虽然语义上"接近"但实际不相关。比如用户问"劳动合同纠纷的诉讼时效"，向量检索可能召回"劳动合同法第几条"的切片，但真正需要的是"诉讼时效"相关的法条。加了重排序后，法条召回率从68%提升到了94%，合规正确率从72%提升到了91%。

264. LangGraph中a节点到b节点回溯机制怎么实现

回答：

这个问题问得挺细的。在LangGraph中，节点的回溯机制本质上是通过图的状态（State）管理和条件边（Conditional Edge） 来实现的，而不是像传统编程那样有"goto"或"throw"之类的跳转指令。

具体实现方式：

在LangGraph中，节点之间的跳转是通过边的定义来控制的。节点A处理完当前状态后，会返回一个状态更新，然后由边的路由函数决定下一个节点是B还是C或者回溯到A自己。

回溯场景的两种实现：

场景一：简单的条件回溯。 比如节点A做数据校验，如果校验失败，需要回到上一个节点重新处理。这时候在定义边的时候，给A和B之间加一个conditional edge，路由函数根据A输出的状态（比如一个"success"字段）来决定是走到B还是回到A自身（或A之前的节点）。

# 伪代码思路
graph.add_conditional_edges("节点A", router, {
    "success": "节点B",   # 成功就往前走
    "retry": "节点A",     # 失败就回溯到A重试
    "fallback": "节点C"   # 或者走兜底节点
})

场景二：多层回溯（带状态恢复）。 更复杂的情况是，A→B→C，在C发现数据有问题，需要回退到A重新处理某些上下文。这时候我们的做法是：在State中维护一个历史栈，记录每个节点处理后的状态快照。当C触发回溯时，把State中的done标志位重置，并通过conditional edge指定回退目标节点。LangGraph的StateGraph天然支持这种通过状态驱动的流程控制。

我在项目中的实际应用： 政策补贴系统中，企业画像采集Agent可能采集到不完整的数据（比如企业的纳税信息缺失），这时候条件审核Agent会触发回溯，让企业画像采集Agent重新去获取缺失的数据，而不是直接报错终止流程。

265. 用户需要查询的实际场景是怎样的，收益率如何用智能体体现出来

回答：

用户查询的实际场景： 以我的政策补贴项目为例，用户查询的场景非常典型。比如一个中小企业老板，他登录系统后问：“我们公司是做软件开发的，在深圳两年了，有10来个员工，去年营收500万左右，能申请什么补贴？”

这个查询看似简单，背后涉及多个步骤：要先理解企业画像（行业、规模、地域、营收等），然后匹配政策库中符合条件的政策，还要审核每个政策的申报条件是否满足，最后生成一个可申报的清单。

收益率如何用智能体体现：

这个问题我觉得可以理解为：如何让智能体理解并处理"收益率"这类数值化的指标场景。在政策补贴场景中，虽然没有直接的"收益率"概念，但类似的数值判断逻辑我们在条件审核Agent中做过：

第一，数值提取与标准化。 用户说"年营收500万左右"，Agent需要从自然语言中提取出"营收 ≈ 500万"这个数值，并标准化为统一的单位（万元），方便和数据库中的政策条件做比较。

第二，条件匹配中的数值计算。 比如某政策要求"上年度营收增长率不低于15%"，Agent需要先拿到企业上一年和今年的营收数据，计算出增长率，再判断是否满足条件。这个计算过程是由Agent调用一个数值计算工具完成的，而不是让大模型自己算（大模型算数值容易出错）。

第三，结果的可视化呈现。 匹配结果不是简单罗列，而是让Agent根据企业的收益率情况和政策申报成功率，给出一个优先级排序，告诉用户"这个政策你符合条件，申报成功率很高，建议优先申报"。

266. 查询到了数据之后，通过工作流编排还是用AI/RAG搜出来

回答：

这个问题问的是两种技术路线的选择，我的回答是：两者结合，各自负责擅长的部分。

工作流编排（LangGraph）负责流程控制： 当查询比较复杂，需要多个步骤、多个Agent协作时，用工作流编排来管理整体的执行流程。比如政策补贴项目中的"查询匹配政策"这个需求，流程是：企业画像采集→政策检索→条件审核→材料生成→结果汇总。这个流程的编排、状态管理、异常处理、节点间的数据传递，都是通过LangGraph的工作流来控制的。

AI/RAG负责知识检索和生成： 在具体某个节点内部的"查询知识"这一步，用的是RAG。比如政策检索Agent需要去政策知识库中查某个行业有什么政策，这时候就用BM25+向量检索+重排序的RAG流程来找到最相关的政策切片。

一个更具体的例子： 用户问"我们公司是高新企业，在深圳，能申报什么补贴？"

  1. 工作流编排启动 → 进入"政策匹配"流程
  2. 企业画像Agent（工作流中的节点）→ 去数据库查企业信息
  3. 政策检索Agent（工作流中的节点）→ 内部用RAG搜政策知识库，找到"深圳高新企业补贴"相关条目
  4. 条件审核Agent（工作流中的节点）→ 把企业画像和检索到的政策条件做对比
  5. 结果汇总Agent（工作流中的节点）→ 生成最终的回答

所以我的结论是： 工作流编排决定了"谁来做、按什么顺序做、做错了怎么办"，RAG解决了"知识从哪里来、怎么找到最相关的信息"。两者缺一不可，不是二选一的关系。

267. 跨页表格没有合并如何识别

回答：

这个问题在法律助手项目中遇到过。很多法律文档（比如判决书、法规条文）中的表格会跨页，PDF解析时如果没有做特殊处理，跨页的表格会被拆成两个独立的表格，导致数据丢失或错乱。

我们的处理方式：

第一，用MinerU做底层解析。 MinerU本身对PDF的布局分析做得比较好，能识别出哪些区域是表格、哪些是正文。但它对跨页表格的合并能力有限，需要上层做额外处理。

第二，跨页表格合并的算法逻辑：

  1. 检测表格连续性： 在解析完所有页面后，遍历所有识别出的表格对象。如果上一页末尾有一个表格，下一页开头也有一个表格，且它们的列结构一致（列数相同、列标题语义匹配），就认为可能是同一个表格被跨页拆分了。

  2. 上下文判断： 光看列结构还不够，还需要看表格的序号和标题。如果上一页的表格末尾有"续上表"或"续表"等标识，或者下一页的表格标题和上一页相同，就确认是跨页表格。

  3. 合并策略： 确认后，将下一页的表格行追加到上一页表格的末尾，合并成一个完整的表格对象，同时删除下一页的表格头（只有第一页保留表头）。

第三，兜底方案： 如果自动合并失败（比如PDF格式过于复杂），我们会在表格对象中打一个"跨页"标签，在后端处理时，把相邻页面的表格作为候选合并对，让审核人员手动确认。

最终效果： 通过这套处理，我们项目中的表格解析完整率达到了95%以上，对法律文档中的结构化数据提取起到了关键作用。

268. 不同节点写一个key是否冲突

回答：

在LangGraph中，不同节点写入同一个key不会直接冲突，但需要理解LangGraph的状态管理机制才能正确使用。

LangGraph的状态更新机制：

LangGraph的State是一个TypedDict或Pydantic模型，每个节点执行完后会返回一个字典，这个字典的内容会被合并（merge）到全局State中。默认的合并策略是覆盖（overwrite）——如果节点A和节点B都写入了State中的同一个key，那么后执行的节点会覆盖先执行的节点在该key上的值。

但这不是简单地"覆盖"就完事了，有几种情况：

情况一：有意覆盖，合理。 比如节点A初始化了一个"临时结果"字段，节点B基于节点A的输出做了进一步处理，然后把更新后的结果写回同一个key。这是常见的设计模式，没问题。

情况二：无意的覆盖，容易出bug。 如果两个节点各写各的，但恰好用了同一个key名，后执行的节点会把前一个的处理结果冲掉。比如节点A写了一个"result"表示政策检索结果，节点B也写了一个"result"表示条件审核结果，节点B就会把节点A的结果覆盖掉。

避免冲突的做法：

  1. 命名规范： 每个节点在State中拥有自己的命名空间，比如 policy_search_result、condition_check_result、material_generation_result，而不是共用 result 这种模糊的key。

  2. 使用Reducer： LangGraph允许自定义Reducer来控制合并行为。如果确实需要多个节点往同一个key追加数据（比如所有节点都把各自的日志写入一个log_list），可以用add作为Reducer，这样每次写入都是追加而不是覆盖。

  3. 显式依赖： 在定义边的时候，明确指定节点之间的依赖关系，确保不会出现两个节点同时对同一个key做写操作但预期不一致的情况。

我项目中的实践： 在政策补贴系统中，State定义就很清晰，每个Agent的输出都用独立的字段名，比如 enterprise_profile、matched_policies、eligibility_results，从设计上避免了冲突。

269. YOLO怎么部署的

回答：

YOLO（You Only Look Once）在项目中的部署，我是用来做文档图像中的目标检测的，比如识别法律文档中的印章、签名、二维码等元素。部署方式分几个层面：

第一，模型选择与导出。 我们用的是YOLOv8的官方预训练模型，在自建的文档元素数据集上做了微调。训练完成后，把PyTorch模型导出为ONNX格式，这样在推理时不需要依赖PyTorch环境，部署更轻量。

第二，容器化部署。 模型以ONNX格式打包进Docker镜像中，配合FastAPI提供服务。推理服务暴露一个HTTP接口，接收图片URL或Base64编码的图片，返回检测到的目标类别和坐标框。整个镜像控制在300MB左右，比带PyTorch的镜像小很多。

第三，与主系统的集成。 YOLO推理服务是作为法律助手项目中的一个独立微服务运行的，不是嵌在主服务中。主服务（FastAPI）在处理PDF解析流程时，如果检测到文档中包含图片或印章区域，就调用YOLO服务的接口去做检测，再把检测结果返回给主流程做后续处理。

第四，部署配置：

  • 推理设备：CPU（因为我们的场景对实时性要求不高，OCR和检测走离线批量处理）
  • 并发策略：用Gunicorn + Uvicorn管理多进程，每个进程加载一次模型，支持并行推理
  • 如果后续需要GPU加速，架构上已经预留了切换GPU的支持

总结： 就是"微调→导出ONNX→Docker打包→FastAPI服务化→主系统调用"这条链路，相对标准但很实用。

270. 性能优化你做过什么？

回答：

在两个项目中，我做了不少性能优化的工作，主要集中在几个方面：

一、RAG检索性能优化（法律助手项目）

  • 混合检索+重排序管道： 先用BM25做关键词检索（毫秒级），同时用向量检索做语义召回，两者取并集后再用重排序模型精排。相比只用向量检索，响应速度提升了60%以上。
  • 缓存策略： 对高频法条查询结果做Redis缓存，设置TTL，命中率大概在30%左右，直接跳过了检索流程。
  • 索引优化： Milvus中用的IVF_FLAT索引，配合合适的nlist参数，在召回率和检索速度之间取了平衡。

二、API响应优化（两个项目都有）

  • 异步化： 整个后端基于FastAPI + asyncio，IO密集型操作（数据库查询、向量检索、大模型调用）都用异步，不会阻塞工作线程。
  • 连接池： Milvus、Redis、Neo4j都配置了连接池，避免频繁创建和销毁连接的开销。
  • 响应压缩： 对返回给前端的JSON数据启用Gzip压缩，减少了约70%的传输体积。

三、数据处理流水线优化

  • 批量处理： PDF解析和知识库构建过程中，不是来一个文档处理一个，而是攒一批文档后批量处理，减少模型加载和卸载的开销。
  • 并行处理： 用asyncio.gather让多个不依赖的步骤并行执行，比如同时解析PDF的不同页面，同时调用多个embedding模型做向量化。

四、大模型调用优化

  • 流式输出： 前端使用SSE流式接收大模型输出，用户不需要等到完整结果生成就能看到内容，体验上"感觉"快了很多。
  • Prompt压缩： 对长上下文做摘要压缩后再传给大模型，减少了token消耗和延迟。

量化成果： 检索响应速度提升了60%以上，企业匹配响应时间控制在1.5秒以内，离线可用率达到了100%。
