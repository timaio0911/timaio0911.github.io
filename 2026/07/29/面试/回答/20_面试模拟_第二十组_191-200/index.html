191. 讲讲python垃圾回收机制

回答：

Python的垃圾回收机制主要基于引用计数，辅以标记-清除和分代回收来处理循环引用问题。

一、引用计数（核心机制）

Python中每个对象都有一个引用计数，记录有多少个引用指向它。

对象被创建时，引用计数为1
被其他变量引用时，计数+1
引用被删除或超出作用域时，计数-1
计数为0时，内存立即被回收

引用计数增加的情况：

  • 对象被赋值给变量
  • 对象被添加到列表、字典等容器
  • 对象作为参数传递给函数

引用计数减少的情况：

  • 变量被del删除
  • 变量被重新赋值
  • 对象从容器中移除
  • 函数执行完毕，局部变量超出作用域

优点： 实时性高，对象不再被引用时立即回收，不会累积垃圾。

缺点： 维护引用计数有额外开销，且无法处理循环引用。

二、标记-清除（解决循环引用）

对于容器对象（list、dict、class等），如果存在循环引用，引用计数会失效：

a = []
b = []
a.append(b)  # b的引用计数+1
b.append(a)  # a的引用计数+1
del a
del b  # 引用计数都不为0，无法回收

标记-清除机制会：

  1. 标记阶段：从根对象（全局变量、调用栈等）出发，遍历所有对象，标记可达的对象
  2. 清除阶段：遍历所有对象，回收未被标记的对象

三、分代回收（优化性能）

基于"大部分对象存活时间很短"的观察，将对象分为三代：

代级 对象 回收频率
第0代 新创建的对象 频繁（如每分配一定次数触发）
第1代 经过1次回收仍存活的对象 较少
第2代 经过2次回收仍存活的对象 最少

为什么需要分代： 每次全量垃圾回收需要遍历所有对象，开销很大。分代回收让大部分回收只处理第0代对象，效率更高。

四、gc模块的使用

Python提供了gc模块，可以手动控制垃圾回收：

import gc

# 关闭自动垃圾回收（不推荐，了解即可）
gc.disable()

# 手动触发垃圾回收
gc.collect()

# 查看垃圾回收统计
gc.get_stats()

# 查看无法回收的对象
gc.garbage

五、常见的内存泄漏场景

在项目开发中，我遇到过的内存泄漏场景：

  1. 全局变量持有大对象

    # 错误：全局变量持有大对象，永远不会被回收
cache = []
def process(data):
    cache.append(data)  # 数据越积越多

  2. 循环引用且定义了__del__方法
    如果对象定义了__del__方法，垃圾回收器无法处理循环引用，会导致内存泄漏。

  3. 闭包中引用大对象

    def outer():
    large_data = [0] * 10000000
    def inner():
        return large_data[0]  # large_data被闭包引用，无法回收
    return inner

在项目中的应用：

在法律助手系统中，我们处理大量法律文档，内存管理非常重要。我做了以下优化：

  1. 使用生成器处理大文件，而不是一次性加载到内存
  2. 定期清理缓存，通过Redis设置TTL自动过期，避免内存累积
  3. 使用weakref处理缓存场景，避免因缓存导致对象无法回收
  4. 监控内存使用，在Docker容器中设置内存限制，超过阈值自动重启

总结： Python的垃圾回收机制整体是"自动的"，但理解其原理有助于写出更高效、更安全的代码。在AI项目中，由于经常处理大量数据，内存管理尤为重要。

192. unsloth框架和llm-factory

回答：

Unsloth和LLaMA-Factory都是当前流行的LLM微调框架，我在法律助手项目中都有调研和使用经验。

一、Unsloth

定位： 专注于训练速度优化和显存节省的微调框架。

核心特点：

  1. 极致优化：通过自定义内核和算子优化，相比标准训练能节省50%以上的显存，训练速度提升2-5倍
  2. 支持QLoRA：对QLoRA有深度优化，4bit量化后训练效果保持较好
  3. 简化API：API设计简洁，几行代码就能完成配置
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="Qwen3-32B",
    max_seq_length=4096,
    load_in_4bit=True,  # 4bit量化
)

model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
)

适用场景：

  • 资源受限的环境（单卡24G显存）
  • 需要快速迭代验证的场景
  • 对训练速度有较高要求的场景

二、LLaMA-Factory

定位： 功能全面的微调平台，支持多种训练方法和模型架构。

核心特点：

  1. 支持多种训练方法：全参微调、LoRA、QLoRA、Prefix Tuning、P-Tuning等
  2. 支持多种模型架构：LLaMA、Qwen、DeepSeek、ChatGLM等主流模型
  3. 丰富的训练配置：支持SFT、DPO、PPO、KTO等多种训练范式
  4. Web UI界面：提供可视化操作界面，方便不熟悉命令行的用户

适用场景：

  • 需要对比多种训练方法的场景
  • 需要进行DPO/PPO等对齐训练的团队
  • 需要完整训练流程管理（数据管理、训练监控、模型评估）

三、两者对比

维度 Unsloth LLaMA-Factory
核心优势 训练速度优化 功能全面、灵活
训练速度 极快（优化2-5倍） 标准速度
显存占用 极低（优化50%+） 标准
支持训练方法 LoRA、QLoRA为主 全参、LoRA、QLoRA、DPO、PPO等
支持模型 主流模型 最全面
学习曲线 低 中等
自定义程度 中等 高
Web UI 无 有

四、在法律助手项目中的选择

在法律助手项目中，我最终选择了Unsloth进行QLoRA微调，原因如下：

  1. 资源限制：我们只有一张24G显存的卡，需要微调Qwen3-32B模型，Unsloth的显存优化能让我们在有限的资源下完成训练
  2. 训练目标明确：我们只需要做SFT（监督微调），不需要DPO/PPO等复杂对齐训练
  3. 迭代速度快：项目周期紧，Unsloth的训练速度提升让我们能更快地迭代

实际效果：

  • 使用Unsloth + QLoRA，在24G显存上成功微调了Qwen3-32B
  • 相比标准训练，显存节省了约31.7G
  • 训练速度提升了约2倍
  • 微调后的模型在法律问答任务上准确率提升了约15%

总结： 如果资源受限、追求训练速度，选Unsloth；如果需要完整的训练平台、多种训练方法对比，选LLaMA-Factory。两者不冲突，也可以先用Unsloth快速验证，再迁移到LLaMA-Factory进行正式训练。

193. 目前最前沿的模型的网络结构，都有哪些层？

回答：

当前最前沿的大语言模型（如GPT-4、Qwen3、DeepSeek等）都基于Transformer架构，核心网络结构包括以下层：

一、输入层

输入文本 → Tokenizer → Token IDs → Embedding层

  1. Tokenizer：将文本转换为token序列

    • BPE（字节对编码）：GPT系列使用
    • SentencePiece：Qwen、LLaMA使用
    • 词表大小通常在32K-256K之间

  2. Token Embedding：将每个token映射为高维向量

    • 维度通常为4096-8192（取决于模型规模）
    • 训练过程中学习每个token的语义表示

  3. Position Embedding：注入位置信息

    • RoPE（旋转位置编码）：当前主流，Qwen、LLaMA、DeepSeek都使用
    • 优点：支持外推，处理长文本效果好
    • 替代了早期的绝对位置编码和Sinusoidal编码

二、Transformer核心层（堆叠N层）

每个Transformer层包含：

1. 层归一化（LayerNorm/RMSNorm）

输入 → LayerNorm → 注意力 → 残差连接 → LayerNorm → FFN → 残差连接
  • RMSNorm：当前主流，相比LayerNorm计算量更小
  • Pre-Norm：在注意力之前做归一化，训练更稳定
  • Qwen和LLaMA都使用Pre-RMSNorm

2. 多头注意力机制（Multi-Head Attention）

输入 → Q/K/V线性投影 → 拆分为多头的Q/K/V → 注意力计算 → 多头拼接 → 输出投影

关键组件：

  • QKV投影：将输入映射为Query、Key、Value三个矩阵
  • 注意力计算：Attention(Q,K,V) = softmax(QK^T/√d)V
  • 多头机制：将注意力拆分为多个头，每个头关注不同的语义模式
  • 输出投影：将多头结果拼接并映射回原始维度

当前主流变体：

  • GQA（分组查询注意力）：DeepSeek、Qwen使用，减少KV Cache，提升推理效率
  • MLA（多头潜在注意力）：DeepSeek V2/V3使用，进一步压缩KV Cache

3. 前馈神经网络（FFN）

FFN(x) = activation(xW₁ + b₁)W₂ + b₂

当前主流变体：

  • SwiGLU：Qwen、LLaMA使用，效果优于ReLU和GELU
  • 激活函数：SiLU（SwiGLU的激活函数）
  • 中间维度：通常是隐藏维度的2.5-4倍

4. 残差连接

每个子层（注意力、FFN）后都有残差连接：

output = LayerNorm(input + sublayer(input))

作用是缓解梯度消失，让深层网络训练更稳定。

三、输出层

最后一层Transformer输出 → LayerNorm → LM Head → Softmax → 预测下一个token
  • LM Head：通常与Token Embedding共享权重（Weight Tying）
  • Softmax：将logits转换为概率分布
  • 输出：每个token的概率分布，选择概率最高的token生成

四、当前最前沿模型的特殊设计

1. DeepSeek V3/R1

  • 使用MoE（混合专家）架构，多个专家网络，每次只激活部分专家
  • 使用MLA（多头潜在注意力），大幅减少KV Cache
  • 总参数量671B，但每次推理只激活约37B参数

2. Qwen3

  • 使用GQA，平衡推理效率和模型质量
  • SwiGLU激活函数
  • 支持超长上下文（128K tokens）

3. LLaMA 3

  • 使用GQA
  • 更大的词表（128K tokens）
  • 在训练数据质量上做了大量优化

五、层数配置参考

模型规模 层数 隐藏维度 注意力头数

32B (Qwen3) 64 5120 40

在项目中的实际意义：

在法律助手项目中，我选择Qwen3-32B，其网络结构特点是：

  • 64层Transformer，足够处理复杂的法律推理
  • RoPE位置编码，支持长法律文档
  • GQA机制，推理效率高，适合生产环境
  • 配合QLoRA微调，在有限资源下完成领域适配

总结： 当前主流模型架构的核心是Transformer，但每一层都有多种优化变体。理解这些层的设计原理，有助于在实际项目中做更好的模型选型和调优。

194. 为什么这里要用多agent的模式？

回答：

这个问题很好，我结合政策补贴项目的实际经验来说明为什么选择多Agent模式，而不是用单Agent或传统程序实现。

当时的场景：

企业政策补贴匹配系统需要处理以下任务：

  1. 采集企业多维度信息（工商、财务、知识产权）
  2. 解析政策文本，提取结构化条件
  3. 将企业信息与政策条件逐条比对
  4. 综合评估匹配度，给出建议
  5. 生成可读的申报指引

为什么不用单Agent？

尝试过，但遇到三个问题：

问题一：Context太乱

单个Agent需要同时处理"企业信息采集"、“政策解析”、“条件匹配”、"决策判断"等多个任务，所有信息都混在一个上下文里。

单Agent的Context：
[企业工商信息][企业财务数据][政策A全文][政策B全文][政策C全文]
[匹配结果A][匹配结果B][匹配结果C][综合评估][行动建议]

当上下文超过模型窗口时，关键信息可能被截断，而且不同任务的信息互相干扰。

问题二：指令冲突

单Agent的system prompt需要同时包含：

  • “你要采集企业信息，调用API获取数据”
  • “你要解析政策文本，提取条件”
  • “你要进行匹配判断”
  • “你要生成最终回答”

这些指令混在一起，模型容易混淆优先级，导致某个任务执行不好。

问题三：调试困难

当结果出错时，很难定位是哪个环节的问题。是企业信息采集错了？政策解析错了？还是匹配判断错了？

为什么用多Agent？

原因一：职责分离，每个Agent专注一件事

Agent 职责 输入 输出
企业画像Agent 采集企业信息 企业名称 结构化企业信息
政策解析Agent 解析政策文本 政策文档 结构化条件列表
条件匹配Agent 逐条比对 企业信息+条件列表 匹配结果
匹配决策Agent 综合评估 匹配结果 评分+建议
生成Agent 格式化输出 评估结果 自然语言回答

每个Agent只需要理解和处理自己的任务，Prompt简洁清晰，不会互相干扰。

原因二：可并行执行，提升效率

企业画像Agent内部的三个子任务（工商、财务、知识产权）可以并行执行，政策解析Agent也独立运行，整体响应时间大幅缩短。

单Agent：串行处理，总耗时5秒
多Agent：企业画像(1.5s并行) + 政策解析(2s并行) → 匹配(1s) → 决策(0.5s) → 生成(1s)
总耗时：约3.5秒，比单Agent快30%

原因三：可独立测试和优化

每个Agent可以独立测试，定位问题更精准：

  • 企业画像Agent输出不对 → 检查数据采集逻辑
  • 条件匹配Agent输出不对 → 检查匹配规则
  • 匹配决策Agent输出不对 → 检查评分标准

原因四：支持灵活扩展

新增功能时，不需要修改现有Agent，只需要新增Agent：

  • 新增"风险提示Agent" → 在匹配结果后增加风险分析
  • 新增"材料清单Agent" → 在生成回答时附带申请材料清单

原因五：容错性更好

某个Agent出错不会影响其他Agent：

  • 如果企业画像Agent超时，匹配决策Agent可以基于已有信息做判断
  • 如果政策解析Agent出错，可以单独重试，不需要重新执行整个流程

什么时候用多Agent，什么时候用单Agent？

场景 推荐模式 原因
简单问答、知识检索 单Agent 不需要复杂分工
复杂业务流程、多步骤推理 多Agent 分工明确，易于管理
需要并行处理 多Agent 提升效率
流程固定、变化少 传统程序（非Agent） 更稳定、更可控
需要灵活决策、动态调整 多Agent 自主决策能力强

总结： 选择多Agent不是跟风，而是因为我确实遇到了单Agent解决不了的问题。在政策补贴系统中，多Agent模式让系统更清晰、更高效、更易于维护。关键是要判断场景是否真的需要多Agent，不要为了用而用。

195. 单页儿童绘本场景，说一句话生成单页图片文本声音等，用户输入【我不希望我的孩子第一次上幼儿园很紧张】，怎么落地

回答：

这个场景很有意思，虽然我简历上的项目主要是法律和政策领域，但从技术架构角度，我可以给出一个落地方案。

整体架构设计：

用户输入 → 理解层 → 创意层 → 生成层 → 组装层 → 输出

一、理解层：解析用户意图

用户输入"我不希望我的孩子第一次上幼儿园很紧张"，需要提取：

用户意图：安抚孩子情绪，减轻入园焦虑
核心主题：克服分离焦虑、适应新环境
情感基调：温馨、鼓励、安全感
目标用户：3-6岁儿童

实现方式： 使用大模型进行意图分类和情感分析，提取关键要素。

二、创意层：生成故事框架

根据用户输入，生成绘本的完整故事框架：

标题：小兔子的幼儿园冒险

分页设计（每页对应一句话生成）：
第1页：小兔子跳跳不想去幼儿园，躲在妈妈后面
第2页：跳跳看到别的小朋友在玩滑梯，有点好奇
第3页：老师温柔地牵起跳跳的手，带他认识新朋友
第4页：跳跳和其他小朋友一起画画、做手工
第5页：放学了，跳跳开心地告诉妈妈今天学了好多东西

实现方式： 大模型根据用户输入生成故事脚本，包含每页的文字描述、情感定位和画面描述。

三、生成层：多模态生成

1. 图片生成

使用Stable Diffusion或DALL·E生成绘本风格的插画：

prompt: "A cute bunny rabbit hiding behind its mother, looking at a colorful kindergarten, children playing on slides, warm watercolor illustration style, children's book, soft colors"

风格控制：

  • 统一的美术风格（水彩、蜡笔、卡通）
  • 一致的角色形象（小兔子角色保持一致）
  • 温馨明亮的色调

2. 文本生成

为每页生成简短、押韵、适合朗读的文字：

第1页文字：
"小兔子跳跳，不想去学校，
躲在妈妈身后，偷偷地瞧一瞧。"

3. 语音生成

使用TTS（如CosyVoice或Fish Speech）生成配音：

  • 选择温暖、舒缓的儿童故事语音风格
  • 控制语速适中（儿童能听清楚）
  • 添加背景音乐（轻柔的钢琴曲）

四、组装层：整合输出

将图片、文字、语音整合为最终输出：

最终输出格式：
┌─────────────────────────────────────┐
│  [图片]  小兔子在幼儿园门口         │
│                                     │
│  "小兔子跳跳，不想去学校，          │
│   躲在妈妈身后，偷偷地瞧一瞧。"     │
│                                     │
│  🔊 播放语音（自动朗读）            │
│  🎵 背景音乐：轻柔钢琴曲            │

196. 针对于给小朋友的ai生成系统，应该会有内容限制，该怎么判断输入是否是小孩，怎么评测输出内容？

回答：

这是一个非常关键的合规和安全性问题。针对儿童AI系统，内容安全是第一优先级，需要从输入和输出两个维度做多层防护。

一、判断输入是否是小孩

方法一：用户注册信息（最可靠）

在注册时强制要求输入年龄信息：

  • 表单填写出生日期
  • 使用家长账号创建子账号
  • 通过手机号验证家长身份

优点： 最准确，可控性强
缺点： 用户可能虚报年龄

方法二：行为模式分析

通过用户的行为模式判断：

  • 打字速度：儿童打字速度明显慢于成人
  • 输入内容复杂度：儿童输入词汇量有限，句子结构简单
  • 交互时长：儿童注意力时间短，交互时长通常较短
  • 点击位置：儿童点击的精准度较低

实现方式： 收集用户交互数据，训练一个简单的分类模型。

方法三：语言特征分析

通过用户的输入文本判断：

  • 词汇复杂度：儿童使用的词汇有限
  • 语法结构：儿童句子通常较短，结构简单
  • 拼写错误：儿童拼写错误率较高
  • 表情符号使用：儿童使用表情符号的频率和类型不同

方法四：互动验证

设计无感的验证机制：

  • 在对话中嵌入"猜谜题"或"简单数学题"，判断作答能力
  • 如果回答正确率符合成人水平，标记为疑似成人用户
  • 如果回答比较简单，标记为儿童用户

综合判断策略：

用户输入 → 多维度判断
├── 注册信息（权重40%）
├── 行为特征（权重30%）
├── 语言特征（权重20%）
└── 互动验证（权重10%）
    ↓
综合评分 → 判断是否为儿童用户

二、输出内容评测

评测维度一：内容安全性

安全审核规则：
1. ❌ 暴力内容：打斗、伤害、武器
2. ❌ 恐怖内容：鬼怪、恐怖场景
3. ❌ 不当内容：性暗示、成人话题
4. ❌ 诱导内容：诱导分享个人信息
5. ❌ 负面情绪：过度消极、绝望
6. ✅ 积极内容：友情、勇气、分享
7. ✅ 教育内容：知识、技能、习惯
8. ✅ 情感内容：爱、关怀、安全感

实现方式： 使用大模型进行内容审核，输出安全评分。

评测维度二：适龄性

不同年龄段的儿童理解能力不同：

年龄段 词汇要求 句子长度 抽象概念 主题
3-4岁 300-500常用词 5-8字 极少 日常、家庭
5-6岁 1000-1500词 10-15字 少量 友情、学校
7-8岁 2000-3000词 15-25字 基础 道德、科学

评测维度三：价值观审核

确保内容符合正确的价值观导向：

  • 不歧视性别、种族、地域
  • 不鼓励攀比、炫耀
  • 不传递错误的知识
  • 强调分享、合作、尊重

评测维度四：阅读体验

  • 句子是否朗朗上口（适合朗读）
  • 是否有韵律感（适合儿童记忆）
  • 图片是否色彩鲜明、内容清晰
  • 是否有互动元素（提问、游戏）

三、自动化评测流程

生成内容 → 多层评测

第1层：规则过滤（快速）
├── 敏感词匹配
├── URL检测
├── 个人信息检测
└── 暴力恐怖内容检测

第2层：AI审核（较慢但全面）
├── 大模型综合评估
├── 安全性评分（0-100）
├── 适龄性评分（0-100）
└── 价值观评分（0-100）

第3层：人工抽检（兜底）
├── 随机抽取5%的内容
├── 由人工审核员复核
└── 定期更新审核规则

决策：
如果任何维度评分低于阈值 → 拦截，不输出
如果所有维度评分高于阈值 → 通过，输出

四、实际项目中的落地建议

  1. 宁可漏判，不能误判：在儿童内容安全上，保守比激进好
  2. 多层审核，逐级校验：规则过滤快，AI审核准，人工抽检保底
  3. 建立反馈机制：用户和家长可以对内容进行举报，不断完善审核规则
  4. 定期更新规则：随着政策变化和语言演化，审核规则需要持续更新
  5. 透明披露：告知家长内容的生成方式和审核机制，建立信任

总结： 儿童AI系统的内容安全是一个系统工程，需要从输入判断、内容审核、输出评测三个环节全面把控。虽然我目前做的项目不是儿童领域，但这些安全设计思路是通用的，在AI应用中都需要考虑。

优点： 风险最小化
缺点： 部署时间较长，需要有流量控制能力

198. 讲讲线性回归，岭回归，拉索回归的区别？

回答：

这三种回归方法都是监督学习中的线性模型，核心区别在于正则化策略不同，用于解决过拟合和特征选择问题。

一、线性回归（Linear Regression）

原理： 寻找一条直线（或超平面）来拟合数据，使得预测值与真实值之间的误差平方和最小。

目标函数：min(Σ(yi - ŷi)²)

其中ŷi = w₁x₁ + w₂x₂ + … + wₙxₙ + b

特点：

  • 没有正则化项
  • 对异常值敏感
  • 当特征之间存在多重共线性时，系数不稳定
  • 容易过拟合，尤其是特征数量多时

二、岭回归（Ridge Regression）

原理： 在线性回归的基础上，加入L2正则化项，惩罚系数的大小。

目标函数：min(Σ(yi - ŷi)² + λΣwj²)

L2正则化的效果：

  • 让所有系数都变小，但不会变为0
  • 相当于给每个特征都分配一定的权重，即使相关性不高
  • 能有效缓解多重共线性问题

特点：

  • 系数收缩但不为零
  • 适合特征都相关、需要保留所有特征的场景
  • 超参数λ控制正则化强度，λ越大，系数越小

三、拉索回归（Lasso Regression）

原理： 在线性回归的基础上，加入L1正则化项。

目标函数：min(Σ(yi - ŷi)² + λΣ|wj|)

L1正则化的效果：

  • 让一些系数变为0，实现特征选择
  • 相当于自动判断哪些特征重要，不重要的直接去掉
  • 产生稀疏解

特点：

  • 系数可以变为0，实现自动特征选择
  • 适合特征多、大部分特征不重要的场景
  • 当特征间高度相关时，Lasso会随机选择其中一个

四、三者的对比

维度 线性回归 岭回归 拉索回归
正则化 无 L2 L1
系数 无约束 收缩但不为零 可以为零
特征选择 不支持 不支持 支持
处理多重共线性 差 好 较好
适用场景 特征少、数据干净 特征多但都相关 特征多且大部分无用
计算复杂度 低 低 较高（需要迭代求解）

五、数学角度的理解

从几何角度理解三者的区别：

线性回归：无约束，系数可以任意大
岭回归：系数被限制在一个圆内（L2约束）
拉索回归：系数被限制在一个菱形内（L1约束）

菱形有尖角，所以Lasso更容易让系数落在坐标轴上，即系数为0。

六、在项目中的应用场景

虽然我工作中主要做AI应用，但统计学知识在数据分析和特征工程中也有应用：

在法律助手项目中：

  • 在做文档相关性分析时，需要用线性模型评估不同特征（关键词匹配度、语义相似度、文档长度等）对最终检索结果的影响
  • 岭回归可以用来处理特征之间的相关性，分析哪些特征对检索效果贡献最大
  • Lasso回归可以帮助选择最有区分力的特征，减少嵌入向量的维度

在政策补贴系统中：

  • 分析企业特征（营收、人员、行业等）与匹配成功率的关联
  • 使用岭回归处理特征间的多重共线性（如营收和利润高度相关）
  • 使用Lasso选择最重要的企业特征，简化企业画像模型

七、如何选择

情况 选择
特征少（<10），数据干净 线性回归
特征多，都重要 岭回归
特征多，大部分不重要 拉索回归
不确定，想要更好的效果 Elastic Net（结合L1和L2）

总结： 三种回归方法的核心区别在于正则化策略。线性回归是基础，岭回归解决过拟合，拉索回归解决特征选择。在实际应用中，我通常先用Lasso做特征选择，再用岭回归做最终模型。

199. 有三类数据，其中一类数据比较少怎么解决？

回答：

数据不平衡是机器学习中常见的问题，在AI项目中也经常遇到。我从数据层面、算法层面和评估层面给出解决方案。

一、数据层面（重采样）

1. 过采样（Oversampling）

增加少数类样本的数量：

随机过采样： 简单复制少数类样本

  • 优点：简单
  • 缺点：容易过拟合，因为复制样本没有新信息

SMOTE（合成少数类过采样）： 在少数类样本之间插值生成新样本

  • 在少数类样本的K近邻之间随机生成新样本
  • 比简单复制效果好，能引入多样性
  • 缺点是可能生成不合理的数据（特征边界模糊）

ADASYN： 自适应合成采样，对更难学习的样本生成更多合成数据

2. 欠采样（Undersampling）

减少多数类样本的数量：

随机欠采样： 随机删除多数类样本

  • 优点：简单，减少数据量
  • 缺点：可能丢失重要信息

Tomek Links： 删除多数类中与少数类边界模糊的样本

  • 能清理边界噪声，让分类边界更清晰

Edited Nearest Neighbors： 删除K近邻中大多数与自身类别不同的样本

3. 混合采样

结合过采样和欠采样：

对于三类数据 A/B/C：
- A类：10000条（多数）
- B类：5000条（中等）
- C类：500条（少数）

策略：
1. 对C类过采样：使用SMOTE增加到5000条
2. 对A类欠采样：随机减少到5000条
3. 最终三类各5000条，平衡

二、算法层面

1. 调整类别权重

在损失函数中为少数类分配更高的权重：

# 在模型训练时设置类别权重
from sklearn.utils.class_weight import compute_class_weight

weights = compute_class_weight('balanced', classes=[0, 1, 2], y=y_train)
# 权重：多数类权重小，少数类权重大

2. 使用对不平衡数据鲁棒的算法

  • 决策树/随机森林：通过调整class_weight参数，天然支持不平衡数据
  • XGBoost/LightGBM：支持scale_pos_weight参数，对少数类更关注
  • 异常检测算法：如果少数类数量极少，可以将问题转化为异常检测（Isolation Forest、One-Class SVM）

3. 集成学习方法

EasyEnsemble： 多次欠采样多数类，每次训练一个模型，集成多个模型的结果

BalanceCascade： 逐步训练，每次训练后移除已正确分类的多数类样本

三、评估层面

在不平衡数据上，不能单纯用准确率（Accuracy）评估，因为全部预测为多数类也能获得很高的准确率。

应该使用的指标：

指标 说明 适用场景
精确率（Precision） 预测为少数类中，真正是少数类的比例 关注误报（FP）的场景
召回率（Recall） 真正的少数类中，被正确识别出的比例 关注漏报（FN）的场景
F1-Score 精确率和召回率的调和平均 需要平衡两者的场景
AUC-ROC 模型区分正负类的能力 二分类场景
Macro-F1 对每个类计算F1再平均 多分类不平衡场景
混淆矩阵 直观展示每类的预测情况 通用

四、生成式方法（适合AI项目）

在AI项目中，还可以用大模型生成少数类的样本：

# 使用大模型生成数据
prompt = """
以下是少数类样本的几个例子：
{examples}

请根据这些例子的特征，生成5个新的、合理的样本，
保持类别特征一致，但内容要有变化。
"""

优点： 生成的样本多样性好，比SMOTE更合理
缺点： 成本高，需要人工审核生成质量

五、实际项目中的选择策略

少数类占比 推荐方案 原因
> 20% 调整类别权重 简单有效，不需要改变数据
5%-20% SMOTE过采样 增加样本多样性，效果好
1%-5% 混合采样 过采样+欠采样结合
< 1% 异常检测 数量太少，不适合分类任务

在法律助手项目中的实际应用：

在法律文档分类中，我们遇到过"典型案例"类别数据很少的问题（只有几十条，其他类别有几千条）。

我的处理方案：

  1. 先用SMOTE过采样，将典型案例增加到200条
  2. 调整类别权重，在损失函数中给典型案例更高的权重
  3. 使用F1-score评估，而不是准确率
  4. 人工扩充：从法律网站上手动收集了50条典型案例

最终典型案例的召回率从原来的30%提升到了70%以上。

总结： 数据不平衡没有银弹，需要根据数据量、不平衡程度和业务需求综合选择方案。通常我会先尝试调整类别权重（最简单），如果效果不好再加过采样，最后考虑生成式方法。

200. 软件工程和大模型应用开发各有什么侧重点

回答：

这个问题很有深度，我在两个项目中都有深刻体会。软件工程和大模型应用开发虽然都是"开发"，但思维方式和侧重点差异很大。

一、核心定位差异

软件工程（Software Engineering）

  • 目标是构建确定性系统
  • 输入相同，输出必然相同
  • 行为由代码精确控制
  • 错误可重现、可调试

大模型应用开发（LLM Application Development）

  • 目标是构建概率性系统
  • 输入相同，输出可能不同（温度参数影响）
  • 行为由模型+Prompt共同决定
  • 错误可能无法重现

二、具体差异对比

维度 软件工程 大模型应用开发
确定性 高 低（输出有随机性）
测试方法 单元测试可以验证所有分支 需要统计评估（准确率、召回率）
调试方式 断点、日志、堆栈跟踪 Prompt调试、输出分析、链路追踪
错误处理 try-catch精确捕获 重试、降级、兜底策略
性能优化 算法复杂度、数据库索引 模型大小、推理速度、缓存策略
版本管理 代码版本控制 代码+模型+Prompt+数据版本控制
部署方式 编译/打包/部署 模型部署+服务部署（通常需要GPU）
监控指标 错误率、响应时间、吞吐量 生成质量、幻觉率、用户满意度

三、在项目中体验到的三个关键差异

差异一：测试方式完全不同

软件工程：

def add(a, b):
    return a + b

def test_add():
    assert add(1, 2) == 3  # 确定性，每次测试结果一样

大模型应用：

def generate_answer(query):
    response = llm.invoke(query)
    return response

def test_generate():
    result = generate_answer("What is RAG?")
    # 不能直接assert，因为每次输出可能不同
    # 需要用统计方法评估
    assert "retrieval" in result.lower()  # 检查关键词
    assert len(result) > 50  # 检查长度

差异二：错误处理策略不同

软件工程： 精确捕获异常，错误类型明确

大模型应用： 需要多层兜底策略

大模型应用的错误处理：
第1层：重试机制（模型偶发错误）
第2层：降级方案（用简单模型代替复杂模型）
第3层：缓存兜底（返回之前相似的答案）
第4层：人工转接（复杂问题转人工客服）

差异三：质量评估体系不同

软件工程： 功能是否实现看测试用例是否通过

大模型应用： 质量是多维度的，需要综合评估

大模型质量评估体系：
├── 忠实度：回答是否基于检索内容
├── 相关性：回答是否与问题相关
├── 完整性：回答是否覆盖所有要点
├── 安全性：回答是否包含不当内容
├── 一致性：同一问题的回答是否逻辑一致
└── 用户体验：回答是否清晰、易懂

四、大模型应用开发需要额外关注的方面

1. Prompt工程

Prompt是"新的代码"，需要版本管理、测试和优化：

  • 开发环境和生产环境使用不同的Prompt
  • Prompt修改需要走代码审查流程
  • 使用Prompt模板管理，避免硬编码

2. 模型评估

需要建立完整的评估体系：

  • 测试集：200+问题，覆盖各种场景
  • 评估指标：忠实度、准确率、召回率
  • 自动评估+人工抽检

3. 成本控制

大模型API调用成本高，需要优化：

  • 缓存策略：减少重复调用
  • 模型选择：简单问题用小模型，复杂问题用大模型
  • Token优化：控制输入输出长度

4. 安全与合规

大模型应用有特殊的风险：

  • 幻觉控制：确保回答基于事实
  • 内容安全：防止不当内容生成
  • 数据隐私：用户数据不能用于模型训练

五、两者结合的最佳实践

在政策补贴系统中，我采用了"软件工程+大模型"的混合架构：

软件工程部分（确定性）：
├── 企业信息采集（API调用，接口稳定）
├── 数据存储（MySQL、Milvus、Neo4j）
├── 权限管理（用户认证、角色控制）
├── 任务调度（定时任务、消息队列）
└── 监控告警（Prometheus、Grafana）

大模型部分（概率性）：
├── 意图识别（理解用户意图）
├── 政策解析（提取结构化条件）
├── 匹配决策（综合判断是否匹配）
├── 回答生成（生成自然语言回答）
└── 结果优化（润色、格式化）

六、总结

应该用软件工程思维的地方 应该用大模型思维的地方
系统架构设计 Prompt设计
数据存储和访问 模型选型和调优
API接口设计 评估指标设计
部署和运维 成本优化
权限和安全 幻觉控制

我的经验： 不要用软件工程的确定性思维去要求大模型，也不要用大模型的概率性思维去设计底层系统。两者结合，用软件工程构建稳定可靠的底层框架，用大模型处理复杂、灵活的智能任务。
