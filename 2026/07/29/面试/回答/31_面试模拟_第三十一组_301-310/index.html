面试模拟 - 第三十一组（301-310题）

基于简历项目经历，模拟面试回答

301. 上下文怎么传递的

回答：

这个问题我分两个场景来回答：一个是RAG场景中的上下文传递，另一个是Agent场景中的上下文传递。

RAG场景：

在法律助手项目中，上下文的传递主要分三个阶段：

  1. 用户输入阶段： 用户的问题本身携带了最直接的上下文。但用户的问题往往是口语化的，比如"我要离婚怎么分财产"，所以我们需要先做Query Rewrite，把口语化问题转成法律检索表达，同时保留原始事实。这个改写后的query就是第一个上下文载体。

  2. 检索阶段： 检索出来的chunks本身携带了语义上下文。我们做了多路召回——Milvus语义检索召回相似度高的chunks，MySQL精确检索召回匹配法条编号的chunks，两者合并后传给Reranker。这里上下文就是"带权重的候选chunks集合"。

  3. 生成阶段： 把Top-K的chunks拼接到Prompt中，加上原始问题，形成完整的上下文输入给大模型。这里有个关键点——我们做了上下文压缩，不是把所有chunks一股脑塞进去，而是通过Reranker筛选出最相关的3-5条，避免上下文窗口被噪声淹没。

Agent场景（政策补贴项目）：

在LangGraph工作流中，上下文是通过全局State传递的。我们定义了一个TypedDict作为State：

class PolicyMatchState(TypedDict):
    user_query: str
    enterprise_profile: dict
    matched_policies: list
    eligibility_results: list
    flow_status: str

每个Agent节点读取State中自己需要的字段，处理后更新State中的对应字段。比如企业画像Agent写enterprise_profile，政策检索Agent读它并写matched_policies。这样上下文就在各个节点间自然流转，而且每个节点只关心自己需要的部分，互不干扰。

302. 有很多工具，如何设计精准找到

回答：

在我们政策补贴系统中，涉及的工具确实不少——企业画像查询、政策检索、条件匹配、材料生成、短信通知、文件上传等等。如果工具多了，让Agent精准找到正确的工具，核心在于工具注册机制和路由策略。

一、工具注册时的描述质量是关键

每个工具注册时，除了名称和参数schema，最关键的是描述（description）。这个描述直接影响大模型能不能正确选择工具。我们的做法是：

  • 描述要具体： 不是写"查询政策"，而是"根据企业所属行业、地区、规模等条件，查询匹配的国家/地方补贴政策，返回政策列表"
  • 包含使用场景： 在描述中写明"当用户询问有什么补贴可以申请时，调用此工具"
  • 参数示例： 在参数描述中给出示例值，比如"industry: ‘制造业’, region: ‘广东省’"

二、工具分类和命名规范

我们把工具按功能域分组，命名带前缀，方便Agent理解：

  • policy_*：政策相关工具
  • enterprise_*：企业画像相关工具
  • notification_*：通知相关工具
  • document_*：文档生成相关工具

三、路由Agent做初筛

在LangGraph中，我们设计了一个路由Agent，它的职责是：先理解用户意图，然后判断应该进入哪个子流程。比如用户问"我们公司能申请什么补贴"，路由Agent判断这是一个政策匹配请求，就导向政策匹配子流程，而不是去调用企业画像入库工具。

四、工具数量控制

如果工具超过一定数量（比如20+），我们会做分层工具设计：

  • 顶层：路由Agent只暴露少数几个"大工具"（子流程）
  • 底层：每个子流程内部再管理自己的细粒度工具

这样每个Agent面对的候选工具列表控制在10个以内，大模型选择的准确率明显更高。

303. 怎么控制召回的多少

回答：

在法律助手项目中，控制召回数量是一个需要精细调节的问题——召回太少可能漏掉关键法条，召回太多又会引入噪声、增加延迟和成本。我主要从几个维度来控制：

一、Top-K参数控制

最直接的方式是设置Top-K值。我们根据测试结果，把语义检索的Top-K设为20，精确检索的Top-K设为10，合并后交给Reranker。Reranker重排后再取Top-5作为最终输入给大模型。

二、相似度阈值过滤

单纯靠Top-K不够，因为如果所有候选的相似度都很低，说明检索本身就没找到好东西。我们设了一个相似度阈值（0.65左右），低于这个阈值的chunks直接丢弃，不参与后续重排。这样能避免"矮子里拔将军"的问题。

三、多路召回的合并策略

我们做了多路召回——语义检索（Milvus）和关键词检索（MySQL）。两路召回的结果合并时，用**RRF（Reciprocal Rank Fusion）**算法做加权融合。具体是给每个chunk算一个融合分：score = 1/(k + rank_semantic) + 1/(k + rank_keyword)。这样在两个排名中都靠前的chunk优先级更高，同时控制最终进入重排阶段的总数不超过30个。

四、动态调整

不同类型的查询，最优的召回数量也不同。比如查"离婚财产分割"这种宽泛问题，需要多召一些（Top-30）；查"民法典第1046条"这种精确问题，Top-5就够了。我们在Query Rewrite阶段会加一个问题类型标签，根据标签动态调整召回参数。

304. 重排序的算法

回答：

在法律助手项目中，我们用的重排序（Reranker）不是自己做算法研发，而是基于开源的交叉编码器（Cross-Encoder）模型。具体来说：

一、Reranker的原理

Reranker和Bi-Encoder（向量检索用的那种）的核心区别在于交互方式：

  • Bi-Encoder： 把query和chunk分别编码成向量，计算余弦相似度。优点是快，适合大规模检索，但缺点是query和chunk之间没有交互，丢失了细粒度的匹配信息。
  • Cross-Encoder： 把query和chunk拼接成一个句子，输入到一个Transformer模型中进行联合编码，输出一个相关性分数。优点是精度高，缺点是慢，因为每对(query, chunk)都要过一次模型，所以只能用在粗排之后的精排阶段。

二、我们用的具体方案

粗排阶段（Milvus检索）：用text-embedding-v3做向量化，召回Top-20。
精排阶段（Reranker）：用开源的bge-reranker-v2-m3交叉编码器，对Top-20的候选chunks逐一打分，重新排序后取Top-5。

三、效果数据

加入Reranker后，Top-5的准确率提升了约15个百分点。具体来说，原来单纯靠向量检索，Top-5中可能还有1-2条不相关的结果；加上Reranker后，基本能做到Top-5中4-5条都和问题高度相关。

四、延迟优化

Reranker的瓶颈是计算速度。20个chunk过一遍交叉编码器大约需要200-300ms。我们做了两个优化：

  1. 并行推理： 允许多个(query, chunk)对同时推理，利用GPU的并行能力
  2. 缓存机制： 对高频query的rerank结果做Redis缓存，命中时直接返回

最终检索响应速度提升了60%以上，从原来的1.5秒降到了0.6秒左右。

305. 从你的工程实践你落实的Hermes落实在哪些方面

回答：

（注：这里我认为面试官问的是"Hermes"框架/工具链在实际工程中的落地，结合我的项目经验来回答。）

在政策补贴和企业法律助手两个项目中，我虽然不是Hermes框架的直接开发者，但在工程实践中确实落实了很多与Hermes理念一致的设计思路：

一、工具调用标准化（MCP/工具注册）

在政策补贴系统中，我们实现了类似Hermes的工具注册机制——每个工具都有清晰的名称、描述、参数schema和返回值定义。这其实就是在践行"工具即接口"的理念，让大模型能够通过结构化的描述精准调用工具。

二、多Agent协作与工作流编排

政策补贴系统用了LangGraph做多Agent编排，每个Agent有明确的职责边界，通过全局State进行数据传递。这和Hermes的Agent设计理念是相通的——Agent不是黑盒，而是可观测、可调试、可编排的工作流节点。

三、可观测性与日志

法律助手项目上线后，我们建立了完整的日志体系：记录每次用户查询→检索→重排→生成的完整链路，包括每个环节的耗时、召回结果、重排分数、最终答案。这些日志既用于监控，也用于后续的优化迭代，相当于Hermes强调的"可观测性"落地。

四、系统设计的模块化

两个项目都采用了模块化设计——RAG模块、Agent模块、知识图谱模块、缓存模块各司其职，通过API接口进行通信。这种松耦合的架构和Hermes的插件化设计理念是一致的。

306. Claude Code泄露代码你看了么，有没有印象深刻的点

回答：

我看过关于Claude Code使用过程中泄露代码的讨论，主要是说在Cline、Claude Code这些AI编程工具中，如果不注意配置，代码可能会被上传到第三方服务进行推理，导致敏感代码泄露。

我印象深刻的几点：

一、问题的本质

这不是Claude Code本身的安全漏洞，而是使用方式的问题。当你用AI编程工具时，你的代码会被发送到LLM服务商的服务器进行推理。如果代码涉及商业机密、核心算法、客户数据，确实存在泄露风险。

二、对工程实践的启示

这让我反思了自己在项目中的做法：

  1. 敏感信息隔离： 在法律助手项目中，我们处理的是法律条文和合同审查。这些数据虽然不涉及用户隐私，但合同内容本身是客户的商业信息。所以我们在设计时就把敏感数据脱敏作为了一环，不会把原始合同全文发给大模型，而是先做结构化提取，只传关键字段。

  2. 本地部署方案： 对于高敏感场景，我们预留了本地模型部署的方案。用Qwen3-32B做本地推理，数据不出服务器，从根本上杜绝泄露风险。

  3. API层安全控制： 在FastAPI接口层，我们加了一层请求审计，记录每次请求的完整参数和响应，异常时能追溯到具体是哪个环节出了问题。

三、我的看法

我觉得工具本身没有对错，关键是怎么用。对于AI编程工具，我会建议：

  • 涉及敏感代码时，用本地模型或私有化部署
  • 不要在Prompt中贴完整的敏感代码
  • 做好代码审查，AI生成的不直接上线
  • 公司层面建立AI工具使用规范

307. 接口交互有遇到堵塞问题么，怎么解决的

回答：

遇到过，而且在两个项目中都遇到过不同类型的堵塞问题。

一、大模型接口超时堵塞

在法律助手项目中，最初调用大模型API时用的是同步请求，遇到高并发时，一个慢请求会阻塞整个线程池，导致后续请求排队等待。

解决方案：

  • 改用异步非阻塞架构，FastAPI + asyncio + httpx.AsyncClient，所有IO操作都异步化
  • 给大模型调用设置合理的超时时间（我们设为30秒），超时后主动断开，避免无限等待
  • 引入熔断机制：连续3次超时后，熔断器打开，直接返回降级响应（“服务繁忙，请稍后重试”），避免雪崩

二、数据库连接池耗尽

在企业补贴系统中，多个Agent同时查询Neo4j知识图谱时，连接池被打满，导致新的查询排队等待。

解决方案：

  • 调大连接池上限（从默认的10调到50）
  • 增加连接池监控，当使用率超过80%时告警
  • 对耗时较长的查询做超时控制，比如图遍历超过5秒就中断

三、Redis缓存击穿

高频查询的缓存过期瞬间，大量请求同时打到数据库，导致数据库压力骤增。

解决方案：

  • 用互斥锁（SETNX）控制：只有一个请求去查数据库并重建缓存，其他请求等待
  • 缓存预热：系统启动时，把热点数据提前加载到缓存
  • 缓存过期时间加随机偏移，避免批量同时过期

四、前端请求堆积

在政策补贴系统中，用户上传企业材料时，如果文件较大（比如几十页的PDF），上传和解析会占用大量时间。

解决方案：

  • 改成异步任务队列：前端上传后立即返回"提交成功"，后端用Celery异步处理PDF解析和数据提取
  • 前端轮询任务状态，处理完成后展示结果
  • 加文件大小限制和格式校验，提前拦截不合规的请求

308. 有个请求到A服务器上，大模型在流式输出，用户想停止掉，请求可能发送到任意服务器，怎么保证请求发送到A服务器

回答：

这是一个典型的分布式系统中的请求路由和会话保持问题。在我们的法律助手项目中，确实遇到过类似的场景——用户发出了一个查询，大模型正在流式生成回答，用户发现回答不对想停止生成。

核心思路：建立基于会话ID的路由机制

一、会话粘滞（Session Stickiness）

最简单的方案是让同一个会话的请求始终路由到同一台服务器。我们在API网关层（Nginx/负载均衡器）配置了基于会话ID的哈希路由：

hash $cookie_session_id consistent;

这样同一个会话ID的请求，负载均衡器会始终转发到同一台后端服务器。

二、但光靠网关不够——也需要应用层配合

网关的粘滞策略不是100%可靠的（比如服务器重启、扩缩容、哈希冲突）。所以我们还做了应用层的兜底方案：

  1. 共享状态存储： 每个正在进行的流式输出任务，在Redis中注册一条记录：{session_id: server_id, task_id: started_at}
  2. 停止请求的处理流程：
    • 用户点"停止" → 请求到达任意服务器 → 服务器查Redis，找到该session对应的server_id
    • 如果就是自己，直接取消本地的流式任务
    • 如果是另一台服务器，通过内部RPC（gRPC或HTTP）向目标服务器发送取消指令
  3. 目标服务器收到取消指令后： 中断对应的流式生成任务，关闭SSE连接，释放资源

三、WebSocket方案（更优但改造成本大）

如果系统设计初期就考虑这个问题，用WebSocket是更优雅的方案——连接建立后就是长连接，不存在"请求发到哪台服务器"的问题。但我们当时系统已经基于HTTP SSE做了流式输出，所以采用了上面的Redis+RPC方案。

四、超时兜底

为了防止"停止请求"本身也丢失，我们还设置了一个最大生成时间（比如60秒），超过这个时间自动中断流式输出，返回已生成的部分结果。

309. 路由Agent如何设计

回答：

路由Agent是我们政策补贴系统中的核心组件。我详细说说设计思路。

一、路由Agent的职责

路由Agent不负责具体的业务逻辑，它的职责只有三个：

  1. 理解用户意图： 用户的问题到底是查政策、查企业信息、生成申报材料，还是咨询流程？
  2. 分发到正确的子流程： 根据意图，把控制权交给对应的子Agent或工作流
  3. 异常处理： 如果无法识别意图，或者识别结果置信度低，走兜底流程

二、设计要点

1. 意图分类

我们定义了几个核心意图类别：

  • policy_query：查政策
  • eligibility_check：检查是否符合条件
  • material_generation：生成申报材料
  • application_tracking：查询申报进度
  • general_chat：闲聊或咨询流程

路由Agent收到用户问题后，先通过LLM做意图分类，输出一个结构化的意图结果：

{
  "intent": "policy_query",
  "confidence": 0.92,
  "entities": {"industry": "制造业", "region": "广东省"}
}

2. 路由逻辑

在LangGraph中，我们通过条件边（Conditional Edge）实现路由：

def route_decision(state: PolicyMatchState) -> str:
    intent = state["classified_intent"]
    confidence = intent["confidence"]
    
    if confidence < 0.6:
        return "clarification_node"  # 置信度低，让用户澄清
    elif intent["intent"] == "policy_query":
        return "policy_retrieval_node"
    elif intent["intent"] == "eligibility_check":
        return "enterprise_profile_node"
    elif intent["intent"] == "material_generation":
        return "material_generation_node"
    else:
        return "general_chat_node"

3. 兜底和反馈

如果路由Agent判断错误，用户反馈"这不是我要找的"，我们会：

  • 记录这次误判，用于后续改进
  • 让用户重新描述问题
  • 定期分析误判案例，优化意图分类的Prompt

三、和RAG场景的对比

在法律助手项目中，路由逻辑更简单——问题进来后，先判断是精确法条查询还是语义检索。精确查询走MySQL的精确匹配，语义检索走Milvus向量检索，两者并行，最后合并结果。实际上这也是一种"轻量级路由"。

310. RAG召回率和准确率的区别

回答：

这是一个很基础但也很重要的问题。我结合法律助手项目的实际评测经验来说明。

一、概念区别

召回率（Recall） 衡量的是"应该召回的内容中，实际召回了多少"。公式是：召回率 = 相关且被召回的数量 / 所有相关文档的总数。

准确率（Precision） 衡量的是"召回来的内容中，有多少是真正相关的"。公式是：准确率 = 相关且被召回的数量 / 所有被召回的数量。

简单说：

  • 召回率高 = 该找到的都找到了，但可能混进来一些不相关的
  • 准确率高 = 找来的都很相关，但可能漏掉了一些

二、项目中的实际数据

在法律助手项目中，我们同时关注这两个指标：

指标 优化前 优化后
Top-5 召回率 68% 94%
Top-5 准确率 约60% 约85%

三、为什么需要同时关注

举个例子：用户问"离婚财产怎么分"，理想情况下应该召回婚姻法、民法典婚姻家庭编、司法解释等相关法条。

  • 如果只追求召回率：把Top-20甚至Top-50都拿来，相关法条基本都覆盖了，但里面会混入很多无关内容（比如合同法的条款），大模型生成的答案质量会下降，因为被噪声干扰了。
  • 如果只追求准确率：只保留相似度最高的1-2条，确实很精准，但如果关键法条因为表述差异没排到前面，就会漏掉，导致回答不完整甚至错误。

四、怎么平衡

我们通过Reranker重排序来平衡两者：

  1. 粗排阶段（Milvus检索）：优先保证高召回，Top-20尽可能覆盖所有相关法条
  2. 精排阶段（Reranker）：交叉编码器重新打分，取Top-5，保证高准确率

这样既不会漏掉关键法条，又不会让噪声干扰大模型生成。

五、一个容易被忽略的点

评测召回率和准确率时，标注数据的质量至关重要。我们在项目中专门花了大量时间做标注工作——找法律专业人士标注了500+组测试数据，每组标注了"这个问题应该召回哪些法条"，确保评测结果可信。没有好的标注数据，这两个指标都是空中楼阁。
