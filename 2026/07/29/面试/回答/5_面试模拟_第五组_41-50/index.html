41. Python迭代器和生成器的区别，使用场景有什么不同？

回答：

迭代器和生成器都是Python中实现惰性求值的机制，但层次不同：

迭代器 是一个实现了__iter__()和__next__()方法的对象，通过
ext()逐个获取元素，取完抛出StopIteration异常。任何实现了这两个方法的对象都是迭代器，比如列表的iter()返回的对象。

生成器 是一种特殊的迭代器，用yield关键字定义函数，每次调用
ext()时执行到yield暂停并返回值，下次从暂停处继续。生成器函数返回的就是生成器对象。

核心区别：

  • 生成器是迭代器的语法糖，写起来更简洁
  • 迭代器需要手动实现__next__，生成器用yield自动实现
  • 生成器只能遍历一次，迭代器可以重新创建

我在项目中的使用场景：

在法律助手项目中，处理大量PDF文档时会生成成千上万的切片。如果把所有切片一次性加载到内存，内存会爆。我用生成器来处理：定义一个chunk_generator()函数，用yield逐个返回切片，这样在构建知识库时可以边生成边入库，内存占用始终保持在可控范围内。

在政策补贴系统中，遍历知识图谱的节点时也用了生成器，因为图谱有500+政策节点和3000+条件节点，一次性遍历太慢，用生成器可以按需获取。

42. 魔术方法有哪些？

回答：

魔术方法（Magic Methods）是Python中以双下划线开头和结尾的特殊方法，也叫dunder方法，用于实现类的特殊行为。常用的有这几类：

对象创建和销毁：

  • init()：初始化方法，创建对象时调用
  • new()：真正创建对象的方法，在__init__之前
  • del()：对象被垃圾回收时调用

字符串表示：

  • str()：print()或str()时调用，给用户看的
  • repr()：交互式环境显示，给开发者看的，更正式

比较运算：

  • eq()、ne()、lt()、gt()等：实现==、!=、<、>等比较

算术运算：

  • add()、sub()、mul()等：实现+、-、*等运算

容器相关：

  • len()：len()函数调用
  • getitem()：下标访问obj[key]
  • setitem()：下标赋值obj[key] = value
  • contains()：in运算符
  • iter()、next()：迭代器协议

上下文管理：

  • enter()、exit()：with语句支持

我在项目中的应用：

在政策补贴系统中，我自定义了一个PolicyNode类表示知识图谱的节点，实现了__eq__和__hash__，这样可以把节点放入集合去重；实现了__str__方便日志打印节点信息；实现了__getitem__让节点可以像字典一样访问属性。

43. *args和**kwargs的用法的区别？

回答：

这两个都是Python函数定义时的可变参数语法，用于处理不确定数量的参数：

*args 收集位置参数，在函数内部是一个元组。比如def func(*args)，调用 unc(1, 2, 3)时，args就是(1, 2, 3)。

**kwargs 收集关键字参数，在函数内部是一个字典。比如def func(**kwargs)，调用 unc(a=1, b=2)时，kwargs就是{‘a’: 1, ‘b’: 2}。

使用顺序： 定义函数时必须按(普通参数, *args, 关键字参数, **kwargs)的顺序，否则语法错误。

解包用法：

  • unc(*list)：把列表解包成位置参数
  • unc(**dict)：把字典解包成关键字参数

我在项目中的应用：

在法律助手项目中，我封装了一个通用的search_knowledge_base()函数，用*args接收任意数量的查询关键词，用**kwargs接收过滤条件（如法律类别、时效性等）。这样调用时非常灵活：

python search_knowledge_base("劳动合同", "解除", category="劳动法", year=2024)

在政策补贴系统中，Agent调用工具时也用kwargs传递参数，因为不同工具需要的参数不同，用字典传递更灵活。

44. 微调的数据集该如何获得

回答：

微调数据集的获取是大模型微调的关键环节，我在法律助手项目中用的是QLoRA微调Qwen3-32B，数据来源主要有这几个渠道：

第一，从现有知识库抽取。 我们的法律知识库有大量法条、案例、司法解释，通过编写脚本从这些文档中抽取问答对。比如把法条作为上下文，让大模型生成对应的问题和标准答案，形成QA对。

第二，业务系统日志挖掘。 法律助手上线后积累了大量真实用户问答记录，筛选出用户点赞的高质量回答，经过人工审核后加入训练集。这种方式获得的数据最贴近真实场景。

第三，人工标注。 针对法律专业场景，邀请法务人员手动编写高质量的问答对。成本高但质量最好，主要用于关键场景的补充。

第四，数据增强。 对已有的问答对做改写，比如同义词替换、问题改写、答案重组，扩充数据量。

数据格式： 我们用的是Alpaca格式，包含instruction（指令）、input（输入）、output（输出）三个字段。最终构建了约5000条高质量法律问答数据。

数据质量把控：

  • 去重：去除重复和高度相似的样本
  • 过滤：过滤掉答案过短或明显错误的样本
  • 格式检查：确保JSON格式正确，字段完整
  • 多样性：确保覆盖不同法律领域，避免数据倾斜

最终效果是合规正确率从72%提升到91%，证明这套数据构建方案是有效的。

45. 部署推理引擎怎么做并发提升，外部的接口是什么

回答：

大模型推理的并发提升是工程化的重点，我在项目中用过几种方案：

推理框架层面：

vLLM 是目前最主流的高性能推理引擎，核心优势是PagedAttention技术，把KV Cache分页管理，避免内存碎片，大幅提升并发能力。我在法律助手中部署Qwen3-32B时用的就是vLLM，单卡可以支持10+并发请求。

具体优化手段：

第一，连续批处理（Continuous Batching）：不用等一个batch全部完成才处理下一个，而是有请求完成就立即插入新请求，GPU利用率大幅提升。

第二，KV Cache优化：vLLM的PagedAttention把KV Cache像操作系统内存一样分页，按需分配，避免预分配浪费。

第三，量化部署：用AWQ或GPTQ做4位量化，模型体积减小，推理速度提升，精度损失很小。我用QLoRA微调的模型就是4位量化版本。

外部接口：

推理引擎对外暴露的是OpenAI兼容的API接口，这是行业标准。接口路径通常是/v1/chat/completions，请求格式和OpenAI完全一致：

python POST /v1/chat/completions { "model": "qwen3-32b", "messages": [{"role": "user", "content": "..."}], "temperature": 0.7, "max_tokens": 2048 }

这样做的好处是代码层面可以无缝切换模型，比如从Qwen切换到DeepSeek，只需要改配置，代码不用动。我在法律助手和政策补贴系统中都是用这套接口标准，前端调用统一的FastAPI网关，网关再转发到推理引擎。

监控指标： 并发数、吞吐量（tokens/s）、首token延迟、平均延迟，这些都要监控，我用Prometheus+Grafana做监控看板。

46. 列举几个LangChain里的函数和类名

回答：

LangChain是我做RAG和Agent开发的核心框架，常用的函数和类有这些：

文档加载器（Document Loaders）：

  • PyPDFLoader：加载PDF文件
  • TextLoader：加载纯文本文件
  • DirectoryLoader：批量加载目录下的文件

文本分割（Text Splitters）：

  • RecursiveCharacterTextSplitter：递归字符分割，最常用，按段落、句子、字符逐级分割
  • CharacterTextSplitter：按单一分隔符分割

向量存储（Vector Stores）：

  • Milvus：我项目中用的向量数据库连接类
  • FAISS：Facebook开源的向量检索库，本地测试用

嵌入模型（Embeddings）：

  • OpenAIEmbeddings：调用OpenAI的embedding接口
  • HuggingFaceEmbeddings：加载本地的HuggingFace模型

链（Chains）：

  • ConversationalRetrievalChain：带对话历史的检索问答链
  • RetrievalQA：基础的检索问答链
  • LLMChain：最基础的LLM调用链

提示词模板（Prompt Templates）：

  • PromptTemplate：基础模板
  • ChatPromptTemplate：对话格式模板
  • FewShotPromptTemplate：少样本提示模板

Agent相关：

  • AgentExecutor：Agent执行器
  • create_react_agent：创建ReAct模式的Agent
  • Tool：定义Agent可用的工具

我在项目中的使用：

法律助手用RecursiveCharacterTextSplitter做文档切片，用Milvus存向量，用RetrievalQA构建检索链。政策补贴系统用LangGraph（LangChain的图扩展）构建多Agent工作流，节点用Tool定义，边用条件路由连接。

47. RAG检索的时候，流程是什么？会先检索标签么？检索完后会有多个切片，这个切片会有优先级么？

回答：

我在法律助手项目中实现的RAG检索流程是这样的：

完整流程：

第一步，查询理解：对用户问题做意图识别和关键词提取，判断是法律咨询还是案例查询，提取法律领域标签。

第二步，多路召回：同时执行向量检索（Milvus）和关键词检索（BM25），各自返回Top-30结果。

第三步，结果融合：用RRF（Reciprocal Rank Fusion）算法融合两路结果，去重后得到候选集。

第四步，重排序（Rerank）：用Cross-Encoder模型对候选集重新打分，取Top-5。

第五步，上下文组装：把Top-5切片按顺序拼接，加上提示词模板，发给大模型生成答案。

关于标签检索：

会先检索标签。我们在入库时给每个切片打了标签（法律类别、效力层级、时效性等）。用户查询时，先做标签匹配做初步过滤，缩小检索范围。比如用户问"劳动法相关问题"，先过滤出"劳动法"标签下的文档，再做向量检索，这样既快又准。

切片优先级：

有优先级，主要通过这几个维度排序：

第一，Rerank分数：重排序模型的打分是最重要的优先级指标，分数越高说明与问题越相关。

第二，标签匹配度：如果查询有明确的领域标签，标签完全匹配的切片优先级更高。

第三，时效性：新法规优先于旧法规，特别是法律领域，法规更新很频繁。

第四，权威性：法律效力层级高的（如法律>行政法规>部门规章）优先级更高。

最终返回给大模型的5个切片，是按照Rerank分数从高到低排列的，大模型会优先参考排在前面的内容。

48. 介绍一下你写的混合检索策略具体指什么？

回答：

混合检索是我在法律助手项目中为了解决单一检索方式的局限性而设计的策略，核心是向量检索+关键词检索+Rerank重排序的三阶段架构。

为什么需要混合检索：

单一向量检索的问题：对用户query的表述方式敏感，如果用户问"公司拖欠工资怎么办"，向量检索可能召回语义相似但不精确的内容，比如"工资支付周期"的相关法条，而不是"拖欠工资的法律责任"。

单一关键词检索的问题：依赖字面匹配，用户换个说法就检索不到。比如"解雇"和"辞退"是同义词，BM25可能只匹配一个。

我的混合检索策略：

第一阶段：向量检索（Milvus）

用text-embedding-v3模型把query向量化，在Milvus中做近似最近邻搜索，召回Top-30语义相似的切片。向量检索的优势是语义理解能力强，能捕获用户意图。

第二阶段：关键词检索（BM25）

用BM25算法做关键词匹配，同样召回Top-30。BM25的优势是精确匹配能力强，对专业术语、法条编号这类精确查询效果好。

第三阶段：RRF融合

用Reciprocal Rank Fusion算法融合两路结果。公式是score = 1/(k+rank)，k通常取60。两路都排在前面的文档会获得更高的融合分数，最终取Top-30。

第四阶段：Rerank精排

用Cross-Encoder模型（如bge-reranker-v2-m3）对融合后的30个切片重新打分。Cross-Encoder会把query和切片拼接后一起编码，能更精细地理解两者关系，最终取Top-5。

效果：

这套混合检索策略把法条召回率从68%提升到94%，检索响应速度提升60%以上。向量检索保证语义召回，关键词检索保证精确匹配，Rerank保证最终精度，三者互补。

49. 你是怎么结合知识图谱增加检索效率的？

回答：

在政策补贴系统中，知识图谱是核心组件，我用Neo4j存储了8类实体、12种关系、500+政策、3000+条件节点。知识图谱对检索效率的提升主要体现在这几个方面：

第一，结构化检索路径。

传统RAG是把文档切成chunk后暴力检索，缺乏结构。知识图谱把政策、企业、行业、补贴类型等实体和关系都结构化存储了。当用户问"新能源企业能申请哪些补贴"时，不需要遍历所有文档，而是沿着图谱路径：企业类型→新能源→关联政策→补贴类型，精准定位到相关节点。图谱游走比向量检索快得多，响应时间<1.5秒。

第二，多跳推理增强。

有些问题需要多步推理，比如"某制造业企业申请研发补贴需要满足什么条件"。知识图谱可以做多跳查询：企业→制造业→研发补贴→前置条件，把分散在不同政策文件中的条件节点串联起来。纯RAG很难做到这种结构化推理。

第三，上下文精准供给。

检索到相关节点后，我可以沿着图谱关系获取完整的上下文。比如检索到一个补贴政策节点，可以同时获取它的申请条件、适用行业、申报时间等关联节点，一次性提供给大模型，避免信息碎片化。

第四，标签辅助过滤。

图谱中每个节点都有丰富的属性标签（行业类别、政策层级、生效时间等）。用户查询时，先在图谱中做标签匹配和关系筛选，缩小检索范围，再做向量检索，这样既快又准。

实际效果：

企业匹配准确率从传统RAG的80%提升到92%以上，响应时间控制在1.5秒以内。知识图谱不是替代RAG，而是作为RAG的增强层，提供结构化的检索路径和精准的上下文。

50. 知识图谱的内容会影响RAG的检索么？

回答：

会的，知识图谱和RAG是互相影响、互相增强的关系。在政策补贴系统中，我具体做了这些设计：

图谱对RAG的正面影响：

第一，查询增强。 用户查询时，我会先在知识图谱中做实体识别和关系查询，把查询到的结构化信息补充到原始query中。比如用户问"高新技术企业补贴"，图谱会返回相关的政策节点、行业分类、申报条件等，把这些信息拼接到query里再做向量检索，召回的内容更精准。

第二，上下文丰富。 RAG检索到的chunk是独立的文本片段，缺乏关联信息。我会把chunk在图谱中对应的节点及其邻居节点信息一起提供给大模型，让模型看到更完整的上下文。

第三，结果排序调整。 如果某个chunk在图谱中有对应的实体节点，且该节点与查询意图高度相关，我会提升这个chunk在最终排序中的优先级。

图谱对RAG的潜在负面影响及应对：

信息冲突： 图谱中的结构化数据和文档中的非结构化数据可能有冲突。比如政策文档更新了，但图谱还是旧版本。解决方案是建立图谱和文档的版本同步机制，定期校验一致性。

过度依赖： 如果过度依赖图谱的结构化信息，可能会忽略文档中的一些细节和边缘案例。我的做法是图谱作为增强层，而不是替代层，最终还是以原始文档检索为主。

维护成本： 图谱需要持续维护，如果图谱质量下降，会影响RAG效果。我们建立了图谱质量监控机制，定期检查节点完整性、关系准确性。

总体来说， 知识图谱和RAG是互补的。图谱提供结构化路径和精准上下文，RAG提供灵活的语义检索。两者结合，企业匹配准确率达到92%以上，比单独用RAG提升了10多个百分点。
