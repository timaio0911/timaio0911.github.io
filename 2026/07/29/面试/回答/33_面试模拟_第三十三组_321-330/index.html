面试模拟 - 第三十三组（321-330题）

基于简历项目经历，模拟面试回答

321. Reranker的输入和输出是什么？一次重排多少候选、最终保留多少条、增加多少延迟、效果提升多少？

回答：

Reranker的输入和输出：

  • 输入： 一个query和一组候选chunks的pair对。每个pair是 (query, chunk_text) 的拼接。
  • 输出： 每个pair的相关性分数，通常是一个0-1之间的浮点数，分数越高表示越相关。

我们用的是bge-reranker-v2-m3这个交叉编码器模型。它内部把query和chunk拼接成一个句子，中间用[SEP]分隔，然后过一个Transformer编码器，最后用分类头输出一个相关性得分。

具体参数：

  • 重排候选数： 30个（从Milvus语义检索和MySQL精确检索两路召回合并后取Top-30）
  • 最终保留数： Top-5（得分最高的5条）
  • 增加延迟： 大约200-300ms（30个pair对过一遍交叉编码器的时间）
  • 效果提升： Top-5准确率提升了约15个百分点

为什么选30个候选？

我们测试过不同的候选数量：

  • 10个候选：Reranker很快（<100ms），但可能漏掉好的chunk
  • 30个候选：效果和速度的平衡点，200-300ms可接受
  • 50个候选：效果提升不明显（不到1%），但延迟翻倍到500ms+
  • 100个候选：延迟1秒以上，完全不划算

所以30个是经过测试选出的最优值。

延迟优化：

200-300ms的延迟虽然不是很大，但对用户体验来说还是能感知到的。我们做了两个优化：

  1. 并行推理： 30个pair对不是串行过模型，而是打包成一个batch并行推理，利用GPU的并行计算能力
  2. 缓存： 对高频query（比如"离婚财产怎么分"这种常见问题），把Reranker结果缓存到Redis，TTL设为1小时，命中时直接返回，延迟为0

322. 怎么判断RAG、Prompt或检索优化后效果真的变好了，而不是主观感觉更好？

回答：

这是一个非常关键的问题——没有客观评测，优化就是盲人摸象。在我们的项目中，建立了一套自动化评测体系，确保每次优化都有数据支撑。

一、评测数据集

首先，我们制作了一个标注好的评测数据集，包含：

  • 500+组测试问题
  • 每个问题标注了"应该召回哪些法条"（标准答案）
  • 每个问题标注了"期望的答案要点"

这些数据由法律专业人士标注，确保标准答案的权威性。

二、分层评测指标

第一层：检索质量评测（自动化）

指标 计算方法 说明
Top-5召回率 召回的5条chunks中，包含标准答案的比例 衡量"有没有漏掉关键法条"
Top-5准确率 召回的5条chunks中，真正相关的比例 衡量"召回来的东西对不对"
MRR（Mean Reciprocal Rank） 第一个正确答案出现在第几位的倒数的平均值 衡量"正确答案排得靠不靠前"

第二层：生成质量评测（自动化+人工）

  • 答案完整性： 用大模型（如GPT-4）作为裁判，打分判断答案是否覆盖了问题的所有要点
  • 答案准确性： 人工抽检，看答案是否和标准法条一致
  • 幻觉率： 答案中编造法条的比例

第三层：用户体验指标（线上）

  • 用户反馈率（点赞/点踩）
  • 回答采纳率（用户是否复制或引用了回答）
  • 平均对话轮数（一轮就解决 vs 需要追问）

三、A/B测试流程

每次优化（比如修改了切片策略、调整了Reranker参数），我们都会跑一遍A/B测试：

  1. 控制组：旧版本
  2. 实验组：新版本
  3. 用500个测试问题分别跑两遍
  4. 对比召回率、准确率、MRR等指标
  5. 如果实验组在所有指标上都优于控制组，且提升幅度超过误差范围（5%以上），才判定优化有效

四、一个真实的例子

有一次我们调整了切片策略——从固定200字切片改成按法律结构切片。上线前做了A/B测试：

  • 旧策略：召回率68%，准确率60%
  • 新策略：召回率82%，准确率73%

数据明确说明新策略更好，大家都没有争议。这就是"用数据说话，而不是感觉"。

323. Top-5召回率怎么计算？测试问题由谁提供、标准法律依据由谁标注，一道问题可以对应多少条依据？

回答：

一、Top-5召回率的计算方法

公式很简单：

Top-5召回率 = 系统返回的Top-5结果中，包含了标准答案中法条的数量 / 标准答案中所有法条的总数

举个例子：标准答案标注了某问题应该包含3条法条（民法典第1046条、第1047条、第1077条），系统返回的Top-5中包含了其中2条，那么召回率就是 2/3 ≈ 66.7%。

二、测试问题由谁提供

测试问题来自三个渠道：

  1. 真实用户对话记录： 从内部试用阶段收集的真实用户提问，这些是最有价值的，因为反映了真实的使用场景
  2. 法律专业人士设计： 请合作的律师朋友，根据他们的执业经验设计高频法律问题，覆盖民事、刑事、行政等领域
  3. 我们自己构造： 针对系统的边界情况构造测试用例，比如"复合问题"（同时问两个不相关的问题）、“模糊表述”（“那个法”）、“长尾问题”（非常冷门的法律领域）

三、标准答案由谁标注

标准答案由法律专业人士标注，我们和一位有执业经验的律师合作：

  • 律师对每个测试问题，标注出"应该引用哪些法条"
  • 标注时同时给出法条编号和具体条款内容
  • 标注完成后，由另一位法律从业者交叉验证，确保标注质量

四、一道问题对应多少条依据

这个没有固定值，取决于问题的复杂度：

  • 简单问题： 1-2条法条就够了。比如"离婚冷静期是多久"，只需要民法典第1077条
  • 中等复杂问题： 3-5条。比如"离婚财产怎么分"，需要婚姻法、民法典相关条款、司法解释
  • 复杂问题： 5-10条甚至更多。比如"公司拖欠工资如何维权"，涉及劳动合同法、劳动法、工资支付条例等多个法律文件

在我们的标注数据中，平均每个问题对应3-4条法条。但评测时我们不会把标准答案设得太死板——只要标注了3条，系统能召回2条就算合格，召回3条就算优秀。

324. 怎么控制法律大模型幻觉？仅靠Prompt和限制模型基于知识库回答是否足够，有没有数据证明效果？

回答：

一、幻觉是法律领域的致命问题

法律领域对准确性的要求极高——如果模型编造了一条不存在的法条，或者歪曲了法条原意，后果可能是灾难性的。所以控制幻觉是我们项目中的第一优先级。

二、我们的多层防线

第一层：Prompt约束（最基础，但不够）

Prompt中明确要求：“请基于以上检索到的法条内容回答，不要编造法条。如果检索到的法条不足以回答用户问题，请明确告知用户。”

但仅靠Prompt是不够的——大模型有"讨好用户"的倾向，即使Prompt说了不要编造，模型在不确定时仍然会尝试生成一个看起来合理的回答。

第二层：知识库约束（核心防线）

我们的核心策略是限制模型只能基于检索到的知识库内容回答。具体做法：

  • 在Prompt中只嵌入检索到的法条内容，不包含模型自身的法律知识
  • 输出格式要求：每条回答必须标注引用的法条编号
  • 如果用户问的问题和检索到的法条无关，模型必须回答"这个问题超出了我的知识库范围"

第三层：答案校验（自动化）

生成答案后，我们加了一个校验层：

  1. 提取答案中引用的所有法条编号
  2. 在知识库中查询这些法条是否存在
  3. 如果存在，对比答案中引用的内容和法条原文是否一致
  4. 如果不一致，触发告警，返回降级响应

第四层：人工抽检（定期）

每周抽取100条回答，由法律专业人士人工审核，统计幻觉率。

三、实际效果数据

经过四层防线，我们的幻觉率控制在了2%以下：

  • 优化前（仅靠Prompt）：幻觉率约15%
  • 加上知识库约束：降至5%
  • 加上答案校验：降至2%以下
  • 目前人工抽检的幻觉率约为1.5%

四、够不够？

坦率说，2%的幻觉率对于法律场景来说还是不够的。法律场景应该追求零幻觉。这也是我们目前还在努力的方向——通过更严格的校验规则、引入事实验证Agent、以及不断优化检索质量来进一步降低幻觉率。

325. 合同审查功能怎么评测？拿到一份合同后，怎么判断系统发现的风险是否准确、全面，是否存在漏检？

回答：

一、合同审查功能的评测体系

合同审查和法条检索不同，它更复杂——不是"找一个答案"，而是"找出一份合同中的所有风险点"。所以评测维度也更多。

二、评测方法

第一步：建立标准答案库

我们准备了50份测试合同，由专业律师对每份合同进行审查，标注出所有风险点，包括：

  • 风险所在的条款位置
  • 风险类型（如"违约责任不对等"、“管辖权约定不明确”）
  • 风险等级（高/中/低）
  • 建议修改方案

这份标准答案就是评测的"金标准"。

第二步：自动化评测指标

指标 计算方法 说明
风险检出率 系统发现的风险点 / 律师标注的总风险点 衡量"有没有漏检"
风险准确率 系统发现且正确的风险点 / 系统发现的总风险点 衡量"发现的准不准"
误报率 系统发现但实际不存在的风险点 / 系统发现的总风险点 衡量"有没有乱报"

第三步：详细评估

每一份合同，都会针对每个风险点做对比：

  • 律师标注了风险A，系统发现了 → 正确
  • 律师标注了风险A，系统没发现 → 漏检
  • 系统发现了风险B，律师认为不是风险 → 误报
  • 系统发现了风险C，律师也标注了 → 正确

第四步：人工复核

自动评测无法覆盖所有方面，比如"风险描述是否准确"、“建议是否合理”。所以还需要人工抽检：

  • 每月抽取10份合同，让律师对系统输出进行评分
  • 评分维度：风险识别完整度、风险描述准确度、修改建议质量

三、实际项目中的数据

在合同审查功能的MVP阶段，我们的评测结果是：

  • 风险检出率：约75%（还有25%的漏检需要改进）
  • 风险准确率：约85%
  • 误报率：约10%

主要漏检的情况是：合同中的隐含风险（比如"双方协商一致"这种表述，可能隐含了后续执行中的不确定性）比较难识别。

四、存在的挑战

合同审查的评测比法条检索更难，因为：

  1. 风险点没有标准答案——不同律师可能对同一份合同有不同的风险判断
  2. 合同多样性——劳动合同、买卖合同、租赁合同，风险点差异很大
  3. 上下文依赖——一个条款单独看没风险，但和另一个条款结合起来看就是风险

目前我们还在持续改进合同审查的准确率，目标是把检出率提升到90%以上。

326. 高、中、低风险怎么划分？项目中是否有专业律师参与标准制定和结果验收？

回答：

一、风险等级的划分标准

我们的风险等级划分，参考了法律实务中的通用标准，结合了合同审查的实际情况：

高风险：

  • 涉及合同核心条款的重大缺陷，一旦触发可能导致严重经济损失或法律后果
  • 比如：违约责任不对等（我方违约罚金极高，对方违约几乎无惩罚）、管辖权约定在对方所在地、无限连带责任担保
  • 这类风险必须修改，否则不能签约

中风险：

  • 存在明显的不利条款，但不足以导致合同无效或重大损失
  • 比如：付款条件苛刻但尚可接受、保密范围过宽、争议解决方式不明确
  • 建议争取修改，但实在无法修改也可以接受

低风险：

  • 存在一些表述不规范或微小瑕疵，但不影响合同执行
  • 比如：标点符号错误、条款编号不连续、引用法条编号有误
  • 能改就改，不改也没太大影响

二、专业律师的参与

是的，专业律师全程参与了标准制定和结果验收。

标准制定阶段：

  • 我们和一位有10年执业经验的律师合作，共同制定了风险等级的划分标准
  • 律师提供了50份真实合同的风险标注作为训练数据
  • 律师还帮我们梳理了常见的风险点类型，覆盖了合同领域的常见风险

验收阶段：

  • 每个版本上线前，律师会抽检10-20份合同，对系统输出进行评分
  • 律师会出具一份验收报告，包括：检出率、准确率、误报率、改进建议
  • 只有验收通过，才能上线

三、持续的校准

风险等级划分不是一成不变的。随着业务场景的变化，我们定期（每季度）和律师一起回顾和校准标准：

  • 哪些风险的等级需要调整
  • 是否有新的风险类型需要纳入
  • 是否有某些风险的实际损害程度和预期不符

327. 请介绍LangGraph工作流，包括主要节点、状态字段、条件路由、精确检索、语义检索、生成和校验之间的关系

回答：

政策补贴项目中的LangGraph工作流是整个系统的核心。我详细介绍一下它的设计。

一、整体架构

我们设计了一个多Agent协作的LangGraph工作流，包含6个主要节点，通过条件边连接，所有节点共享一个全局State。

二、状态字段（State）

class PolicyMatchState(TypedDict):
    # 输入
    user_query: str                    # 用户原始问题
    session_id: str                    # 会话ID，用于持久化
    
    # 中间结果
    enterprise_profile: dict           # 企业画像（行业、规模、地区、营收等）
    matched_policies: list             # 匹配的政策列表
    eligibility_results: list          # 条件审核结果
    generated_materials: list          # 申报材料生成结果
    
    # 控制流
    flow_status: str                   # 流程状态：初始化/进行中/完成/异常
    error_info: str                    # 异常信息
    retry_count: int                   # 重试次数

三、主要节点

1. 意图识别节点（Intent Recognition Node）

  • 职责：理解用户想要什么
  • 输出：intent（policy_query / eligibility_check / material_generation / general_chat）

2. 企业画像采集节点（Enterprise Profile Node）

  • 职责：采集企业的基本信息（行业、规模、地区、营收、员工数等）
  • 输入：user_query
  • 输出：enterprise_profile
  • 支持多轮对话补充信息（如果用户一次没说全）

3. 政策检索节点（Policy Retrieval Node）

  • 职责：根据企业画像，从知识图谱和向量库中检索匹配的政策
  • 内部又分为两个子路径：
    • 精确检索（MySQL+Neo4j）： 按行业、地区、规模等结构化条件精确匹配
    • 语义检索（Milvus）： 用企业画像描述做向量检索，发现语义相似的政策
  • 两路结果合并后输出

4. 条件审核节点（Eligibility Check Node）

  • 职责：逐条检查政策条件是否满足
  • 输入：enterprise_profile + matched_policies
  • 输出：eligibility_results（每条政策给出"符合/不符合/待确认"的判断）

5. 材料生成节点（Material Generation Node）

  • 职责：为符合条件的政策生成申报材料
  • 输入：eligibility_results
  • 输出：generated_materials

6. 结果生成节点（Result Generation Node）

  • 职责：汇总所有结果，生成最终的用户友好回答
  • 输入：前面所有节点的输出
  • 输出：最终答案

四、条件路由

def router(state: PolicyMatchState) -> str:
    """根据当前状态决定下一步走向哪个节点"""
    intent = state.get("intent", "")
    status = state["flow_status"]
    
    # 异常处理
    if status == "异常":
        return "error_handler"
    
    # 根据意图路由
    if intent == "policy_query":
        if not state["enterprise_profile"]:
            return "enterprise_profile_node"
        return "policy_retrieval_node"
    elif intent == "eligibility_check":
        return "enterprise_profile_node"  # 先采集企业信息
    else:
        return "general_chat_node"

五、精确检索和语义检索的关系

政策检索节点内部，精确检索和语义检索是并行执行的：

  • 精确检索：用SQL查Neo4j知识图谱，“行业=制造业 AND 地区=广东省 AND 规模=中型”
  • 语义检索：用向量检索查Milvus，“广东省制造业中型企业可申请的补贴政策”

两路结果通过RRF（Reciprocal Rank Fusion）融合，取Top-10进入条件审核环节。

六、生成和校验

生成环节（材料生成节点）之后，我们加了一个校验节点：

  • 检查生成的材料是否完整（是否覆盖了所有必填字段）
  • 检查生成的材料是否合规（是否引用了正确的政策条款）
  • 如果校验不通过，重新生成，最多重试3次

328. 为什么选择LangGraph，而不是简单的while循环加Function Calling？它在流程控制、调试和可观测性方面有什么价值？

回答：

这个问题问得好，也是我们团队在技术选型时认真讨论过的。

一、为什么不用"while循环+Function Calling"？

理论上，确实可以写一个简单的循环：

while True:
    result = llm_call(prompt, tools)
    if result.is_final_answer:
        break
    tool_result = execute_tool(result.tool_call)
    prompt += tool_result

这看起来简单直接，但实际项目中会遇到很多问题：

问题1：没有状态管理
多个Agent之间怎么共享数据？数据放在哪里？只能靠全局变量或者传参，随着流程变复杂，代码会迅速变成"意大利面条"。

问题2：控制流单一
循环是线性的，但真实的业务场景往往需要分支、并行、回溯。比如"如果企业信息不全，需要回退到企业画像采集节点重新采集"，用while循环实现这种逻辑非常别扭。

问题3：没有持久化
如果流程执行到一半，服务器重启了，所有中间状态就丢了，用户只能重新开始。

问题4：调试困难
每次循环都修改了同一个prompt变量，出了bug很难定位是哪个环节的问题。

二、LangGraph解决了这些问题

1. 流程控制（Control Flow）

LangGraph的图结构天然支持复杂的控制流：

  • 顺序执行： 节点A → 节点B（最基础的）
  • 条件分支： 根据State中的某个字段，走不同的路径
  • 并行执行： 多个节点同时执行
  • 循环回溯： 节点B发现数据不完整，可以回到节点A重新采集
  • 子图嵌套： 复杂节点内部可以再嵌套一个子图

这些在while循环中要么无法实现，要么实现起来极其复杂。

2. 调试（Debugging）

LangGraph提供了可视化调试能力：

  • 每次执行都会生成一个执行轨迹图，可以直观看到每个节点的执行顺序、耗时、状态变化
  • 每个节点的输入输出都可以单独查看
  • 出了bug，可以快速定位到是哪个节点出了问题

用一个实际例子来说：有一次政策检索节点返回了空结果，如果是while循环，我需要加大量日志；但在LangGraph中，我直接在可视化界面上看到"政策检索节点执行了，但输出是空列表"，然后去排查检索逻辑，30分钟就定位了问题。

3. 可观测性（Observability）

  • 每个节点的执行时间、输入输出、异常信息都可以自动记录
  • 支持断点续传：如果流程中断，可以从最后一个成功的节点恢复
  • 支持中间状态检查：在任意节点暂停，查看当前State

三、实际效果

在政策补贴项目中，因为用了LangGraph，我们：

  • 开发周期缩短了约30%（对比之前用while循环的尝试）
  • 线上bug率降低了约50%（因为状态管理更清晰，不容易出错）
  • 调试时间减少了约60%（可视化调试太方便了）

329. 用户断线后如何让任务继续执行并恢复输出？长对话中工具返回内容过多、上下文窗口不足和Prompt Cache失效时怎么处理？

回答：

一、用户断线后的任务恢复

我们的系统通过LangGraph的持久化层来实现断线恢复。

具体做法：

  1. 每个任务都有唯一Session ID： 用户发起请求时，系统生成一个session_id，这个ID贯穿整个任务生命周期
  2. State持久化到外部存储： LangGraph的State不是只存在内存中，而是通过StateSnapshot机制持久化到MySQL或Redis中。每个节点执行完毕后，State会被序列化保存
  3. 断线重连： 用户断线后重新连接，带上session_id，系统从持久化存储中读取最新的State，判断任务执行到哪里了，然后从中断点继续执行
  4. 前端轮询： 前端在用户断线重新连接后，轮询后端查询任务状态，拿到最终结果

实际效果： 用户即使断线了，任务在后台继续执行。重新连接后，用户看到的是"您的任务已完成，以下是结果"而不是"请重新开始"。

二、长对话中工具返回内容过多

在政策补贴项目中，工具返回内容过多的情况很常见，比如政策检索返回了20条政策，每条政策还有详细的条件描述，加起来可能超过5000字。

处理策略：

  1. 摘要压缩： 工具返回的内容不做全量传递，而是经过一个摘要Agent进行压缩。比如20条政策→压缩成每条100字的关键信息摘要
  2. 分层传递： 只传递最相关的Top-5，其余作为"备选"放在附件中，供大模型需要时查阅
  3. 结构化输出： 工具返回结果用JSON格式，大模型只读取关键字段（如政策名称、匹配度、核心条件），不读全文

三、上下文窗口不足

当对话轮数较多，或者单次工具返回内容过大，导致上下文窗口超出模型限制时：

处理策略：

  1. 滑动窗口： 只保留最近的N轮对话（我们设为5轮），更早的历史对话压缩成摘要
  2. 对话摘要： 每轮对话结束后，用一个独立的Agent生成该轮对话的摘要（200字以内），存到State中
  3. 关键信息保留： 即使压缩了历史对话，State中的关键字段（如enterprise_profile、matched_policies）不会丢失，因为它们不依赖对话历史，而是独立存储的
  4. 分页策略： 如果结果列表太长（比如20条政策），不一次性全部传入，而是分页传递，每页5条

四、Prompt Cache失效

Prompt Cache是LLM服务商提供的一种优化机制——如果Prompt的prefix部分相同，可以复用缓存，减少计算量。但一旦Prompt内容变了（比如拼接了不同的检索结果），缓存就失效了。

处理策略：

  1. Prefix固定： 把Prompt中不变的部分（系统指令、格式要求）和可变的部分（检索结果、历史对话）分开，系统指令部分尽量保持不变，提高缓存命中率
  2. 批量处理： 如果多个用户的检索结果有重叠（比如都查了同一条政策），对重叠部分做缓存
  3. 不在意失效： 坦率说，Prompt Cache失效不是我们最优先优化的问题，因为对我们来说，答案的准确性比响应速度更重要。如果缓存失效意味着模型能拿到最新的检索结果，那其实更好

330. 如果有8500万到1亿份裁判文书，如何完成数据清洗、结构化拆分、标签标注和质量校验，并降低大模型调用成本？

回答：

这是一个非常宏大的工程问题。8500万到1亿份裁判文书，意味着数据量在PB级别，传统的数据处理方法完全不可行。我谈谈我的设计思路：

一、数据清洗——分层处理

第一层：规则清洗（离线，低成本）

用Spark或Flink做大规模分布式处理，用规则过滤：

  • 去除空文档、重复文档（裁判文书网有大量重复数据）
  • 去除格式错误、编码错误的数据
  • 提取元数据：案号、法院名称、审判日期、案件类型、当事人信息
  • 这些规则清洗可以在数小时内完成，成本极低

第二层：模型清洗（在线，有成本但可控）

规则清洗后，用轻量级模型做进一步处理：

  • 用BERT-based的序列标注模型提取段落结构（事实、理由、判决等）
  • 用正则+规则识别实体（人名、公司名、金额、法条引用）
  • 这部分可以用小模型（如ALBERT、DistilBERT）在GPU集群上批量处理，成本可控

二、结构化拆分

裁判文书的格式相对统一——事实、理由、判决、案号、当事人等结构清晰。所以结构化拆分可以主要靠规则：

  1. 段落级拆分： 按"本院认为"、“经审理查明”、"判决如下"等标准段落标记拆分
  2. 句子级拆分： 用NLP工具（如LAC、PKUSeg）做句子分割
  3. 实体抽取： 用规则+词典抽取案号、金额、日期、法条引用等关键信息
  4. 向量化： 用text-embedding-v3对每个段落做向量化，存入Milvus

三、标签标注——主动学习（Active Learning）

1亿份文书不可能全部人工标注。采用主动学习策略：

  1. 用规则自动打标签（比如"盗窃罪"标签通过案由字段自动标注）
  2. 随机抽取5万份让法律专业人士标注
  3. 用这5万份训练一个分类模型
  4. 用模型对剩余的文书做预测，选出模型最不确定的10万份
  5. 让专业人士标注这10万份
  6. 更新模型，重复4-5步
  7. 迭代3-5轮后，模型精度足够，停止人工标注

这样只需要标注15-20万份，就能达到覆盖90%以上案件的标签效果。

四、质量校验

自动化校验：

  • 数据完整性校验：是否所有必填字段都已填充
  • 格式校验：是否符合结构化schema
  • 一致性校验：案号格式是否统一、日期是否合法

抽样校验：

  • 每天抽取0.1%的数据，用大模型做质量检查
  • 大模型检查：数据是否完整、结构是否正确、标签是否准确
  • 如果发现异常，触发告警，回溯修正

五、降低大模型调用成本

这是最需要精打细算的部分。我的策略是：

1. 用规则替代大模型（80%的成本都在这）

  • 结构化提取：用正则+规则替代大模型，准确率可达95%，成本几乎为零
  • 标签分类：用BERT-based分类模型替代大模型，成本是GPT-4的1/1000

2. 大模型只用在关键环节

  • 只在需要深度理解的地方用大模型，比如"案件争议焦点总结"
  • 而且用本地部署的小模型（如Qwen3-32B），而不是云端大模型

3. 批量处理+缓存

  • 相似文书批量处理，复用相同的结果
  • 常见案件类型的模板结果缓存，命中时直接返回

4. 成本估算

按1亿份文书计算：

  • 规则清洗：几乎零成本（用现有Spark集群）
  • 结构化提取：成本约5000元（用BERT模型，GPU集群跑一周）
  • 标签标注：成本约15万元（人工标注15万份，每份1元）
  • 大模型调用：仅用于抽样校验和质量检查，约200万次，成本约2万元

总计：约17.5万元，而不是用大模型处理全部1亿份的几千万元。
