211. 如果BERT输出5类，想将输出提到10类该怎么做

回答：

这个问题本质上是分类任务的类别数扩展。核心思路是调整模型的输出层，必要时进行微调。

最简单的做法——修改分类头：

BERT的架构可以拆成两部分：主干网络（Transformer Encoder） + 分类头（Classification Head）。分类头通常就是一个全连接层，输入是BERT的[CLS]向量，输出是类别数。

# 原始：5分类
classifier = nn.Linear(768, 5)

# 改为10分类
classifier = nn.Linear(768, 10)

但要注意几个问题：

1. 权重初始化

原来5类的权重不能直接复用，因为新增的5类没有对应权重。可以：

  • 随机初始化新类别的权重：最简单，但新类需要从零学起
  • 从同类初始化：如果新类别和旧类别语义相近，可以用旧类别的权重做初始化

2. 是否需要微调

场景 建议
新类别和旧类别相似 只训练分类头，不微调BERT
新类别差异较大 需要全模型微调（LoRA）
数据量很少 只训练分类头，冻结BERT

3. 数据准备

每新增一个类别，至少需要50-100条标注数据，否则训练不稳定。

4. 更灵活的方案——增加辅助分类器

如果不想动原来的模型，可以加一个独立的辅助分类器：

  • 主分类器：负责原来的5类
  • 辅助分类器：负责新增的5类
  • 最后合并结果

5. 从零训练 vs 增量训练

  • 从零训练：把分类头改成10类，用全部数据重新训练
  • 增量训练：保留原来的权重，只训练新类别的权重

增量训练更高效，但要注意灾难性遗忘——模型可能会忘记原来5类的分类能力。我一般会：

  1. 先冻结BERT，只训练分类头
  2. 用旧数据做replay（回放），防止遗忘
  3. 效果稳定后再解冻BERT做LoRA微调

总结： 改分类头本身很简单，难点在于新类别的数据准备和防止灾难性遗忘。

212. 语义感知是怎么实现的？

回答：

语义感知（Semantic Awareness）指的是让模型理解文本的真正含义，而不仅仅是字面匹配。在法律助手项目中，我做了不少语义感知相关的工作。

核心实现方式：

1. 基于Embedding的语义表示

这是最基础的方式。通过预训练模型（如BERT、text-embedding-v3）将文本转化为向量，语义相近的文本在向量空间中也相近：

# 使用text-embedding-v3
query = "打官司需要什么材料"
query_vec = embedding_model.encode(query)

# 语义相近的文档会被检索出来
doc1 = "诉讼需要准备的材料清单"  # 语义相近
doc2 = "打官司的流程和材料"      # 语义相近
doc3 = "今天的天气很好"          # 语义不相关

2. 法律助手项目中的语义感知实现

法律文档中，同一件事可能有多种表述。比如"劳动仲裁"和"劳动争议处理"指的是同一件事。我通过以下方式实现语义感知：

a. 语义切片（Semantic Chunking）

不是简单按字数切分，而是按语义边界切分：

  • 检测段落边界（换行、标题）
  • 检测句子边界（句号、分号）
  • 保持语义完整性（一个完整的法律条款不拆分）

b. 语义检索（Semantic Search）

将用户问题向量化，与知识库中的文档向量做相似度匹配：

  • 使用text-embedding-v3生成向量
  • 存入Milvus向量数据库
  • 检索时计算余弦相似度

c. 重排序（Rerank）

粗排后，用更精细的语义模型做二次排序：

  • 粗排：向量检索，召回top-50
  • 精排：交叉编码器（Cross-Encoder），对(query, doc)打分
  • 取top-5作为最终结果

3. 语义感知的难点和解决方案

难点 解决方案
同义词问题 使用大规模预训练模型，覆盖更多同义词
专业术语 在法律数据集上微调Embedding模型
长文本语义 分段编码+加权融合
歧义消解 结合上下文窗口做语义理解

4. 实际效果

在法律助手项目中，引入语义感知后：

  • 法条召回率从68%提升到94%
  • 用户用日常语言提问也能找到相关法律条款
  • 比如用户问"被公司辞退了怎么办"，能匹配到"劳动合同解除"相关条款

简单来说： 语义感知就是让模型从"看字"变成"懂意"，通过向量化+语义匹配+重排序的组合来实现。

213. OCR提取的图片和文字分块后加载到什么地方？

回答：

在法律助手项目中，我处理了大量含有图片的PDF文档。OCR提取的图片和文字分块后，需要根据不同的使用场景加载到不同的存储系统中。

整体架构：

OCR/MinerU解析
    │
    ├── 文字块 → 向量化 → Milvus（语义检索）
    │             ├── 结构化信息 → MySQL（存储元数据）
    │             └── 全文索引 → Elasticsearch（关键词检索）
    │
    └── 图片块 → 对象存储/MinIO（存储原始图片）
                  ├── 图片描述（Caption）→ 向量化 → Milvus
                  └── 图片元数据 → MySQL

详细说明：

1. 文字块

存储到Milvus（向量数据库）：

  • 每个文字块生成Embedding向量
  • 存储向量+文本内容+元数据
  • 用于语义检索
# 文字块存储结构
{
    "chunk_id": "doc_001_chunk_005",
    "doc_id": "doc_001",
    "text": "根据《中华人民共和国劳动合同法》第三十九条...",
    "embedding": [0.12, -0.34, ..., 0.78],  # 768维向量
    "metadata": {
        "page": 5,
        "source": "劳动法.pdf",
        "chunk_type": "paragraph"
    }
}

存储到MySQL（关系数据库）：

  • 文档元数据：文件名、上传时间、页数
  • 分块信息：每个块的起始位置、所属文档
  • 用于管理和查询

2. 图片块

存储到对象存储（MinIO/S3）：

  • 原始图片：保持高分辨率，用于后续分析
  • 图片缩略图：用于快速预览
  • 图片OCR结果：提取的文字内容

存储到Milvus（如果图片做了语义描述）：

  • 图片的Caption向量
  • 用于图文混合检索

3. 为什么这样设计？

存储系统 用途 为什么选它
Milvus 语义检索 向量检索速度快，支持10亿级规模
MySQL 元数据管理 结构化查询，支持复杂条件过滤
MinIO 图片存储 对象存储，成本低，扩展性好
ES（可选） 全文检索 关键词精确匹配，BM25算法

4. 加载顺序（用户查询时的流程）：

用户提问
    ↓
1. 在Milvus中做向量检索 → 召回相关文字块
    ↓
2. 根据文字块中的doc_id，查询MySQL获取文档元数据
    ↓
3. 如果涉及到图片，从MinIO加载对应图片
    ↓
4. 图文结合，送入大模型生成回答

5. 实际项目中的经验：

法律助手项目处理了上千份法律文档，图片和文字分块后：

  • 文字块约50万条，全量存入Milvus
  • 图片约2万张，存入MinIO
  • 查询响应时间：文字检索<100ms，图片加载<500ms

总结： 没有"一个地方存所有"的方案，而是根据数据特性和使用场景，选择最合适的存储系统。

214. 召回和重排阶段的区别？

回答：

召回（Retrieval）和重排（Rerank）是RAG系统中两个核心的阶段，它们目标和策略完全不同，但缺一不可。

一、核心区别

维度 召回阶段 重排阶段
目标 快速找出候选集 精确排序候选集
数量级 全量数据→top-50/100 top-50/100→top-5/10
速度要求 毫秒级，越快越好 可以稍慢，几百毫秒
精度要求 不能漏掉相关文档 排序要精准
模型 双编码器（Bi-Encoder） 交叉编码器（Cross-Encoder）
计算量 低（向量相似度计算） 高（需要模型推理）
可扩展性 好，支持千万级数据 差，只能处理小批量

二、法律助手项目中的具体实现

召回阶段：

# 1. 向量检索（Milvus）
# 用户问题 → 向量化 → 在Milvus中检索 → 返回top-50
# 耗时：约50ms

# 2. 混合检索（BM25 + 向量检索）
# 同时做关键词匹配和语义匹配
# 结果合并后取top-50
# 耗时：约80ms

召回策略： 宁可多召回一些不相关的，也不能漏掉相关的。所以我会把top_k设得比较大（50-100），确保高召回率。

重排阶段：

# 1. 交叉编码器打分
# 对(top-50)个候选文档，逐一和query做匹配打分
# 使用更精细的模型（如bge-reranker-v2）
# 耗时：约200-500ms

# 2. 按分数排序，取top-5
# 作为最终输入大模型的上下文

重排策略： 精度优先，计算量大所以只处理少量的候选文档。

三、为什么需要重排？

只有一个原因——向量检索的精度不够。

向量检索（双编码器）的缺点是：

  • query和doc各自独立编码，没有交互
  • 语义相近但实际不相关的文档可能分数很高
  • 比如"合同法"和"劳动合同法"语义相近，但内容完全不同

交叉编码器（重排模型）能让query和doc充分交互，打分更准确。

四、效果数据

在法律助手项目中：

阶段 召回率 准确率 耗时
仅召回 94% 40% 50ms
召回+重排 92% 85% 300ms

召回率稍微下降了一点（因为重排会筛掉一些），但准确率大幅提升，用户体验更好。

五、总结

召回 重排
比喻 海选 决赛
原则 宁滥勿缺 宁缺毋滥
评价指标 召回率 精确率

两者缺一不可： 没有召回，重排无米下锅；没有重排，召回的噪声太多，大模型会被干扰。

215. 介绍一下依赖注入？

回答：

依赖注入（Dependency Injection, DI）是一种设计模式，核心思想是：类不自己创建依赖对象，而是由外部传入。这能让代码更灵活、更易测试、更易维护。

一、通俗理解

假设你开一家餐厅：

❌ 没有依赖注入：
  厨师自己种菜、自己养猪、自己酿酒
  → 太累了，换菜单就要重新种菜

✅ 有依赖注入：
  厨师只管做菜，食材由供应商提供
  → 想换菜单，换供应商就行

二、代码示例

没有依赖注入：

class LegalAssistant:
    def __init__(self):
        self.llm = QwenLLM()  # 自己创建，写死了
        self.vector_store = MilvusStore()  # 自己创建，写死了
    
    def answer(self, query):
        context = self.vector_store.search(query)
        return self.llm.generate(query, context)

问题：想换LLM或换向量数据库，必须修改代码。

有依赖注入：

class LegalAssistant:
    def __init__(self, llm, vector_store):
        # 依赖从外部注入
        self.llm = llm
        self.vector_store = vector_store
    
    def answer(self, query):
        context = self.vector_store.search(query)
        return self.llm.generate(query, context)

# 使用
llm = QwenLLM()
vector_store = MilvusStore()
assistant = LegalAssistant(llm, vector_store)

# 想换，改注入的地方就行
llm = DeepSeekLLM()  # 换成DeepSeek
assistant = LegalAssistant(llm, vector_store)

三、在项目中的应用

法律助手项目中，我用依赖注入的地方：

# 1. LLM可以灵活切换
legal_assistant = LegalAssistant(
    llm=QwenPlusLLM(),  # 开发时用
    # llm=DeepSeekLLM(),  # 上线前切换
    vector_store=MilvusStore(),
    embedder=TextEmbeddingV3()
)

# 2. 测试时注入Mock
legal_assistant = LegalAssistant(
    llm=MockLLM(),  # 不调用真实API
    vector_store=MockVectorStore(),  # 使用内存中的数据
    embedder=MockEmbedder()
)

四、依赖注入的好处

好处 说明
解耦 类不依赖具体实现，只依赖接口
可测试 可以注入Mock对象，方便单元测试
灵活 切换实现只需要改一处
可维护 每个组件职责单一

五、FastAPI中的依赖注入

在政策补贴系统的后端中，我大量使用了FastAPI自带的DI：

from fastapi import Depends, FastAPI

app = FastAPI()

# 定义依赖
def get_vector_store():
    return MilvusStore()

def get_llm():
    return QwenLLM()

# 注入依赖
@app.post("/search")
async def search(
    query: str,
    vector_store: MilvusStore = Depends(get_vector_store),
    llm: QwenLLM = Depends(get_llm)
):
    context = vector_store.search(query)
    return llm.generate(query, context)

总结： 依赖注入不是什么高深的技术，就是**“把依赖从内部创建变成外部传入”**，让代码更灵活、更干净。

216. 讲讲深浅拷贝？

回答：

深浅拷贝是Python中对象复制的两种方式，核心区别在于嵌套对象的处理方式。

一、核心概念

浅拷贝（Shallow Copy）：

  • 复制对象本身，但不复制对象内部的子对象
  • 新旧对象共享内部的子对象
  • 修改子对象会影响两个对象

深拷贝（Deep Copy）：

  • 递归复制对象及所有子对象
  • 新旧对象完全独立
  • 修改任何部分都不影响对方

二、代码示例

import copy

# 原始对象
original = {
    "name": "法律助手",
    "modules": ["RAG", "Agent", "Search"]
}

# 浅拷贝
shallow = copy.copy(original)

# 深拷贝
deep = copy.deepcopy(original)

# 修改内部列表
shallow["modules"].append("OCR")

print(original["modules"])  # ['RAG', 'Agent', 'Search', 'OCR']  ← 被影响了
print(deep["modules"])      # ['RAG', 'Agent', 'Search']          ← 不受影响

# 修改外层元素
shallow["name"] = "政策助手"
print(original["name"])  # "法律助手"  ← 外层不受影响

三、在项目中的应用场景

法律助手项目中，我用深浅拷贝的场景：

浅拷贝的使用场景：

# 1. 配置共享
# 多个Agent共享同一个配置，配置不常变
base_config = {"model": "Qwen3", "temperature": 0.7, "top_k": 50}
agent1_config = copy.copy(base_config)
agent1_config["temperature"] = 0.5  # 修改不影响base_config
# 但注意：如果配置里有嵌套的dict，修改会互相影响

# 2. 状态快照 - 快速记录
current_state = {"step": "retrieval", "chunks": chunk_list}
snapshot = copy.copy(current_state)  # 快速记录，但chunks是共享的

深拷贝的使用场景：

# 1. 会话状态复制
# 每个用户的会话状态需要完全独立
session_state = {
    "user_info": {"name": "张三", "role": "律师"},
    "history": [{"role": "user", "content": "劳动法..."}],
    "cache": {"last_query": "...", "results": [...]}
}

# 复制给另一个用户，必须深拷贝，否则修改会互相影响
new_session = copy.deepcopy(session_state)

# 2. 配置模板
# 从模板创建配置，每个实例需要完全独立
config_template = {
    "model_params": {"lr": 1e-4, "batch_size": 8},
    "data_config": {"path": "/data", "augmentation": True}
}
experiment_config = copy.deepcopy(config_template)
experiment_config["model_params"]["lr"] = 5e-5  # 不影响模板

四、需要注意的问题

问题 说明
深拷贝性能 大对象深拷贝很慢，可能耗时几百毫秒
循环引用 深拷贝能处理，但可能无限递归
自定义对象 需要实现 __copy__ 和 __deepcopy__ 方法
不可变对象 int、str、tuple不需要深拷贝，它们本来就是不可变的

五、面试回答总结

维度 浅拷贝 深拷贝
复制层级 只复制一层 递归复制所有层
嵌套对象 共享引用 完全独立
性能 快 慢（大对象）
内存 少 多
使用场景 配置共享、状态快照 会话隔离、模板复制

217. NumPy的广播机制主要是做什么？

回答：

NumPy的广播（Broadcasting）机制解决的是不同形状数组之间的运算问题。它让形状不匹配的数组也能进行逐元素运算，而不用手动复制数据。

一、核心思想

广播机制的核心是：自动扩展小数组的维度，使其与大数组形状匹配，然后进行逐元素运算。

二、实际例子

import numpy as np

# 例1：标量 + 数组
arr = np.array([[1, 2, 3], [4, 5, 6]])
result = arr + 10  # 10被广播到和arr相同形状
# result: [[11, 12, 13], [14, 15, 16]]

# 例2：一维数组 + 二维数组
arr_2d = np.array([[1, 2, 3], [4, 5, 6]])
arr_1d = np.array([10, 20, 30])
result = arr_2d + arr_1d  # arr_1d被广播到两行
# result: [[11, 22, 33], [14, 25, 36]]

# 例3：列向量 + 行向量
col = np.array([[1], [2], [3]])  # shape: (3, 1)
row = np.array([10, 20, 30])    # shape: (3,)
result = col + row               # 都广播到 (3, 3)
# result: [[11, 21, 31], [12, 22, 32], [13, 23, 33]]

三、广播规则

从最后一个维度开始比较，满足以下条件之一即可广播：

  1. 维度大小相等
  2. 其中一个维度大小为1
  3. 其中一个维度缺失
# 规则演示
A shape:  (4, 3, 2)
B shape:     (3, 2)  → 自动在前面补1 → (1, 3, 2) → 广播到 (4, 3, 2)

四、在法律助手项目中的应用

1. 批量计算向量相似度

# 用户查询向量和所有文档向量的相似度计算
query_vec = np.array([0.1, 0.2, -0.3])   # shape: (3,)
doc_vectors = np.random.randn(10000, 3)   # shape: (10000, 3)

# 广播机制：query_vec自动广播到 (10000, 3)
similarities = np.dot(doc_vectors, query_vec)  # shape: (10000,)

2. 批量归一化

# 批量对Embedding向量做L2归一化
embeddings = np.random.randn(1000, 768)   # 1000个768维向量
norms = np.linalg.norm(embeddings, axis=1, keepdims=True)  # shape: (1000, 1)
normalized = embeddings / norms  # 广播：norms从(1000, 1)广播到(1000, 768)

五、不广播会怎样？

没有广播机制，你需要手动写循环：

# 没有广播
result = np.zeros_like(arr_2d)
for i in range(arr_2d.shape[0]):
    result[i] = arr_2d[i] + arr_1d

# 有广播，一行搞定
result = arr_2d + arr_1d

性能差异巨大：C语言实现的广播比Python循环快几十倍。

总结： 广播机制让我们能用简洁的代码做高效的数组运算，是NumPy最实用的特性之一。

218. PyTorch支持广播么？

回答：

支持。 PyTorch的广播机制和NumPy基本一致，遵循相同的规则。

一、PyTorch中的广播

import torch

# 标量广播
a = torch.tensor([[1, 2], [3, 4]])
b = 5
c = a + b  # 5被广播到和a相同形状
# c: [[6, 7], [8, 9]]

# 维度广播
a = torch.randn(3, 1, 5)  # shape: (3, 1, 5)
b = torch.randn(1, 4, 1)  # shape: (1, 4, 1)
c = a + b                  # 结果: (3, 4, 5)

二、和NumPy广播的区别

维度 NumPy PyTorch
规则 完全相同 完全相同
内存 返回新数组 返回新张量
性能 C实现 CUDA加速（GPU）
梯度 不支持 支持自动求导

三、PyTorch广播的注意事项

1. 广播不兼容时会报错

a = torch.randn(3, 5)
b = torch.randn(4, 3)  # 最后一个维度不匹配
# c = a + b  # RuntimeError: 形状不兼容

2. 广播和张量操作的结合

在模型训练中，广播经常出现：

# 批量计算损失
predictions = torch.randn(32, 10)  # 32个样本，10个类别
targets = torch.randint(0, 10, (32,))  # 32个标签

# 广播在loss函数中自动发生
loss = nn.CrossEntropyLoss()(predictions, targets)

# 在注意力机制中
scores = torch.matmul(query, key.transpose(-2, -1))  # 矩阵乘法
weights = torch.softmax(scores, dim=-1)  # 广播
output = torch.matmul(weights, value)

3. 显存优化

广播在GPU上执行，不会额外占用显存（因为广播是"虚拟的"——不复制数据）：

# 下面的操作不会额外占用显存
batch_size, seq_len, hidden = 32, 128, 768
x = torch.randn(batch_size, seq_len, hidden)
bias = torch.randn(hidden)  # 广播到(batch_size, seq_len, hidden)

y = x + bias  # bias是广播的，不复制数据

四、在项目中的实际应用

政策补贴系统中，计算企业匹配度时的广播：

# 批量计算企业和政策的匹配得分
enterprise_features = torch.randn(1, 64)     # 1个企业，64维特征
policy_features = torch.randn(500, 64)       # 500个政策

# 广播：enterprise_features自动广播到(500, 64)
scores = torch.matmul(policy_features, enterprise_features.T)
# scores shape: (500, 1) → 每个政策的匹配得分

五、总结

  • PyTorch完全支持广播，规则和NumPy一致
  • 在GPU上广播效率极高，不会额外占用显存
  • 但要注意形状不兼容时会报错，需要提前确认
  • 在模型构建、损失计算、批量处理中都会用到

219. 介绍一下前向传播和反向传播？

回答：

前向传播和反向传播是神经网络训练的两个核心步骤，一个是"做题"，一个是"改错"。

一、前向传播（Forward Propagation）——做题

数据从输入层开始，逐层向前计算，最终得到输出结果。

以法律助手的QLoRA微调为例：

# 简化的前向传播过程
输入: "法律条款第XXX条是什么内容？" → 文本向量化
    ↓
Embedding层 → 将token转为向量 [batch, seq_len, hidden]
    ↓
Transformer层 × N → 逐层计算注意力
    ↓
输出层 → 预测下一个token的概率分布
    ↓
损失计算 → 比较预测结果和真实结果

前向传播中发生了什么？

  • 每一层接收上一层的输出
  • 乘以权重（W），加上偏置（b），经过激活函数
  • 最终得到预测结果

二、反向传播（Backward Propagation）——改错

根据预测结果和真实结果的差异（损失），从输出层向输入层反向传播梯度，更新参数。

# 反向传播的流程
损失函数: 预测结果和真实结果的差距
    ↓
计算梯度 → 对每个参数求偏导（链式法则）
    ↓
从输出层 → 隐藏层 → 输入层，逐层计算梯度
    ↓
参数更新 → W_new = W_old - lr × gradient

三、关键概念

1. 链式法则（Chain Rule）

反向传播的核心数学原理：

如果 y = f(g(x))，则 dy/dx = df/dg × dg/dx

在神经网络中：
损失L对参数W的梯度 = dL/dy × dy/dz × dz/dW

2. 梯度（Gradient）

梯度告诉我们应该往哪个方向调整参数，才能让损失变小：

  • 梯度为正：参数增大，损失增大 → 应该减小参数
  • 梯度为负：参数增大，损失减小 → 应该增大参数

四、在QLoRA微调中的实际应用

# 法律助手项目中，微调过程
for batch in dataloader:
    # 1. 前向传播
    outputs = model(batch["input_ids"])  # 预测结果
    loss = loss_fn(outputs, batch["labels"])  # 计算损失
    
    # 2. 反向传播
    loss.backward()  # 计算梯度（只对LoRA参数）
    
    # 3. 参数更新
    optimizer.step()  # 更新LoRA参数
    optimizer.zero_grad()  # 清零梯度

五、为什么需要反向传播？

如果不使用反向传播，直接计算梯度，需要对每个参数都做一次前向传播，计算量是O(n)（n为参数量）。而反向传播通过链式法则，一次前向+一次反向就能计算出所有梯度，计算量是O(1)。

直观对比：

方法 计算量 适用场景
数值微分 O(n) 小模型验证
反向传播 O(1) 大规模模型训练

六、总结

阶段 方向 做什么 类比
前向传播 输入→输出 计算预测结果 学生做题
反向传播 输出→输入 计算梯度更新参数 老师批改订正

两者交替进行，直到模型收敛。在法律助手项目中，我训练了约3个epoch，每次迭代都包含这两个步骤。

220. 某个MySQL数据库中有一个schema，来了一个查询query，怎么区分它是要查询哪张表？

回答：

这个问题考察的是SQL解析和查询路由的能力。在数据库层面，可以从以下几个角度来区分。

一、从SQL语句本身分析

1. 解析SQL中的FROM子句

最直接的方法：SQL语句中明确指定了表名。

-- 明确指定表
SELECT * FROM users WHERE id = 1;        → 查询users表
SELECT name FROM orders WHERE status = 1; → 查询orders表

-- JOIN多表
SELECT u.name, o.order_id 
FROM users u JOIN orders o ON u.id = o.user_id;  → 涉及users和orders两张表

2. 解析SQL语法树

使用SQL解析器（如sqlparse、sqlglot）将SQL解析成语法树，然后提取表名：

import sqlparse

query = "SELECT name, age FROM users WHERE status = 'active'"
parsed = sqlparse.parse(query)[0]

# 提取FROM子句中的表名
from_clause = parsed.token_matching.find(["FROM"])
table_name = from_clause[0].get_real_name()  # "users"

二、在政策补贴系统中的应用

在政策补贴系统中，后端API需要根据不同的查询类型，路由到不同的数据源：

from sqlglot import parse_one

def route_query(query: str) -> dict:
    """解析SQL并路由到对应的数据源"""
    tree = parse_one(query)
    table_name = tree.find("from").expressions[0].table
    
    # 根据表名路由
    if table_name == "enterprises":
        return {
            "datasource": "mysql_enterprise",
            "table": "enterprises",
            "cache": True
        }
    elif table_name == "policies":
        return {
            "datasource": "neo4j",  # 政策数据在图数据库
            "table": "policies",
            "cache": True
        }
    elif table_name == "matches":
        return {
            "datasource": "mysql_main",
            "table": "policy_matches",
            "cache": False
        }

三、如果查询没有明确指定表名？

在一些简单场景中，用户可能只传了查询条件，没有表名：

# 用户输入：{"name": "张三", "status": "active"}
# 需要根据上下文推断表名

def infer_table(query_params: dict, context: str):
    """根据查询参数和上下文推断表名"""
    # 根据字段名推断
    if "enterprise_name" in query_params:
        return "enterprises"
    if "policy_name" in query_params:
        return "policies"
    
    # 根据上下文
    if context == "企业查询":
        return "enterprises"
    elif context == "政策匹配":
        return "policies"
    
    # 默认路由
    return "unknown"

四、更高级的做法——查询路由中间件

class QueryRouter:
    """SQL查询路由中间件"""
    
    def __init__(self):
        self.routes = {
            "enterprises": {
                "datasource": "mysql_enterprise",
                "parser": EnterpriseParser(),
                "validator": EnterpriseValidator()
            },
            "policies": {
                "datasource": "neo4j",
                "parser": PolicyParser(),
                "validator": PolicyValidator()
            }
        }
    
    def route(self, query: str):
        # 1. 解析SQL
        parsed = parse_one(query)
        table = parsed.find("from").expressions[0].table
        
        # 2. 查找路由
        route = self.routes.get(table)
        if not route:
            raise ValueError(f"未知表名: {table}")
        
        # 3. 验证和转换
        validated = route["validator"].validate(parsed)
        transformed = route["parser"].transform(validated)
        
        # 4. 路由到对应数据源
        return route["datasource"].execute(transformed)

五、总结

方法 适用场景 优点 缺点
解析FROM子句 标准SQL查询 准确、直接 需要SQL解析器
字段名推断 非结构化查询 灵活 可能误判
上下文路由 API调用 简单明了 需要维护路由表
查询路由中间件 复杂系统 可扩展、可维护 实现较复杂

我的建议： 在项目中，我通常用SQL解析+映射表的组合方式。先用SQL解析器提取表名，如果找不到再通过字段名和上下文推断，最后通过路由表映射到具体的数据源。
