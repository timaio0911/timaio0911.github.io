面试模拟 - 第三十二组（311-320题）

基于简历项目经历，模拟面试回答

311. 这个法律服务平台的业务定位是什么？面向哪些用户？是自研产品还是外包项目？目前是否已经上线？

回答：

业务定位：

这个法律服务平台的核心定位是面向企业法务和个人用户的智能法律条款查询与合同审查助手。具体来说，它解决的是"法律条文太多、普通人看不懂、律师查起来也费劲"的问题。用户只需要用自然语言提问，系统就能从海量法律资料中精准找到相关法条，并给出合规建议。

面向的用户：

主要有两类用户：

  1. 企业法务部门： 日常需要查询大量法律法规、审查合同条款，用我们的系统可以大幅提高效率。比如一个法务以前查一个法条要翻半天书，现在30秒就出结果。
  2. 普通个人用户： 遇到法律问题（离婚、劳动纠纷、合同纠纷）想先了解法律依据，不需要直接请律师，系统先给一个初步的法律参考。

是自研还是外包？

这个是自研产品，不是外包项目。我们团队从需求分析、架构设计到开发测试，都是自己完成的。

目前是否上线？

目前系统已经完成了核心功能的开发和测试，处于内部试运行阶段。我们内部团队在用，也在邀请一些合作企业进行试用。正式对外发布还需要完善一些周边功能，比如用户权限管理、支付集成等。

313. 请完整介绍从约320份原始法律资料，到1.6万条文本切片和Milvus向量索引的处理流程

回答：

这个流程是整个法律助手项目知识库构建的核心，我分几个阶段来介绍：

阶段一：原始资料收集与整理

320份原始资料涵盖了法律法规、司法解释、案例和文书模板。来源包括国家法律法规数据库、政府公开文件、法律文书网站等。格式方面，有TXT、Word、文本型PDF和扫描版PDF，非常杂。

阶段二：PDF解析与文本提取

不同的文件格式用不同的解析方案：

  • TXT/Word： 直接读取，Word用python-docx库
  • 文本型PDF： 用PyMuPDF（fitz）直接提取文本，速度快，准确率高
  • 扫描版PDF： 走OCR流程，先用OpenCV做图像预处理（去噪、二值化、倾斜校正），然后用PaddleOCR做文字识别，复杂表格用PP-Structure的表格识别模型

阶段三：文本清洗

提取出来的原始文本质量参差不齐，需要做大量清洗：

  • 去除页眉页脚（“第1页/共10页”、"法律法规汇编"等）
  • 去除乱码和特殊字符
  • 纠正OCR识别错误（比如"民法典"识别成"民洪典"）
  • 统一格式：全角半角转换、多余空格删除
  • 结构化拆解：识别法律名称、章节标题、条号、条款内容

阶段四：文本切片

法律文本的结构很清晰——章、节、条、款、项。我们主要按"条"为单位切片：

  • 一条法律条文作为一个切片单元
  • 如果一条内容过长（超过500字），再按"款"二次切分
  • 同时设置overlap（50-100字），避免关键信息被切在边界上
  • 重要元数据保留：来源法律名称、章节信息、条号

最终从320份资料切出了约1.6万条文本切片。

阶段五：向量化与索引构建

  • Embedding模型：text-embedding-v3，输出1024维向量
  • 向量数据库：Milvus
  • 索引类型：IVF_FLAT（倒排文件索引），兼顾检索速度和精度
  • 同时把切片文本和元数据存到MySQL，用于精确检索和展示

阶段六：质量验证

建好的索引不是直接上线，而是先做验证：

  • 抽取100个测试问题，人工标注标准答案
  • 用这些测试问题跑一遍检索，看Top-5召回率
  • 初始召回率只有68%，经过循环优化（调整切片策略、调参、加Reranker）提升到94%

314. 法律法规、司法解释、案例和文书模板从哪里获取？为什么当前数据规模只有300多份？

回答：

数据来源：

  1. 法律法规： 主要来自国家法律法规数据库（flk.npc.gov.cn）和司法部的公开数据，这些是官方权威来源
  2. 司法解释： 最高人民法院和最高人民检察院的公开司法解释文件
  3. 案例： 裁判文书网公开的典型案例
  4. 文书模板： 从法律服务平台和律师事务所公开的模板整理

为什么只有300多份？

这个数据规模确实不大，有几个原因：

第一，项目是MVP阶段。 我们做的是最小可行产品，先验证技术路线，证明"用RAG做法律检索是可行的"，而不是一开始就追求覆盖所有法律。300多份资料覆盖了民事、刑事、行政三大领域的主要法律，对于MVP验证来说已经够了。

第二，质量问题优先于数量。 法律数据对准确性要求极高——如果一条法条是错的，那整个系统就不可信了。所以我们宁愿先精耕细作300份，确保每份资料都经过清洗、结构化、校验，而不是盲目堆量。

第三，数据获取有门槛。 虽然法律数据是公开的，但整理成结构化、可检索的格式需要大量人工。比如裁判文书网虽然有海量案例，但格式不统一、质量参差不齐，清洗成本很高。

第四，法律领域特殊性。 法律条文本身是有限的（民法典也就1260条），不像互联网数据那样是海量的。真正重要的是覆盖全、更新快，而不是数量大。

未来的扩展计划：

如果项目进入正式运营阶段，我们会把数据规模扩展到3000+份，覆盖更多部门法、地方法规和最新司法解释，同时建立自动化的数据更新机制。

315. TXT、Word、文本型PDF和扫描版PDF分别怎么解析？OCR、OpenCV、PaddleOCR和PP-Structure在其中怎么使用？

回答：

这是我们知识库构建中最头疼的问题之一，因为法律资料的格式实在太杂了。我详细说说每种格式的处理方案：

一、TXT文件

最简单，直接open().read()读取，编码统一用UTF-8。遇到ANSI编码的旧文件，用chardet检测编码后转换。

二、Word文件（.docx）

用python-docx库读取。提取所有段落文本，同时保留标题层级信息（Heading 1/2/3），这对后续切片非常有用——知道哪些是章标题、哪些是条，切片时就能按结构切。

三、文本型PDF

用PyMuPDF（fitz）提取。优点是速度快、准确率高，而且能保留PDF中的文本位置信息，方便判断页眉页脚。具体做法：

  • 逐页提取文本块
  • 根据文本块的坐标信息，判断哪些是页眉（顶部固定区域）、哪些是页脚（底部页码）
  • 合并连续文本块，恢复段落结构

四、扫描版PDF

这是最复杂的，因为扫描版PDF本质上是图片，没有可用文本，必须走OCR流程。

OCR流程：

  1. 图像预处理（OpenCV）：

    • 灰度化：把彩色图转成灰度图
    • 二值化：用Otsu算法把图像转成黑白，去除背景干扰
    • 去噪：用中值滤波去除椒盐噪声
    • 倾斜校正：检测文本行的倾斜角度，旋转校正，因为扫描件经常放歪

  2. 文字识别（PaddleOCR）：

    • 把预处理后的图片输入PaddleOCR模型
    • 输出识别的文本行及其位置坐标
    • PaddleOCR的准确率在清晰文档上能达到95%以上

  3. 表格识别（PP-Structure）：

    • 法律文档中常有表格（比如量刑标准表、费用计算表）
    • 用PP-Structure的表格识别模型，检测表格结构，还原行、列、单元格内容
    • 把表格转为Markdown格式或结构化JSON，方便后续检索

  4. 后处理：

    • OCR必然有识别错误，比如"民法典"识别成"民洪典"、“第"识别成"筇”
    • 我们建了一个法律术语词典，对OCR结果做模糊匹配纠正
    • 结合法律文本的格式特征（如"第X条"的规律），用正则二次校验

316. 法律文本怎么清洗和结构化？页眉页脚、乱码、表格、多栏排版以及法律名称、条款编号等信息怎么处理？

回答：

法律文本的清洗和结构化是一个系统工程，我按不同类型的问题来说明：

一、页眉页脚处理

页眉页脚通常有固定模式，比如"第1页/共10页"、“法律法规汇编”、"中华人民共和国合同法"等。我们的做法：

  • 利用PDF解析时获取的文本位置信息，页面顶部和底部各10%的区域重点检测
  • 建立页眉页脚模式库，用正则匹配常见模式
  • 统计全文中出现频率高但只在特定位置的文本，自动识别为页眉页脚

二、乱码处理

OCR识别产生的乱码主要有三种：

  1. 编码错误： 检测到Unicode替换字符（\ufffd）或异常字符，做编码转换
  2. OCR识别错误： 用法律术语词典做模糊匹配纠正
  3. 特殊符号： 法律文书中常见的"①、②"、"（一）、（二）"等，保留结构化信息，去除格式干扰

三、表格处理

法律文本中的表格（如量刑标准、费用计算）用PP-Structure提取后，转成Markdown或JSON格式。关键点：

  • 保留表格的行列结构
  • 把表头和数据分开存储
  • 表格内容同时作为独立文本切片，方便针对性检索

四、多栏排版

有些法律文本是两栏或三栏排版的。处理方式：

  • 通过文本块的x坐标分布，判断是否多栏
  • 如果是多栏，按栏从左到右、从上到下重新排列文本顺序
  • 合并同一段落被分栏切断的内容

五、法律名称和条款编号

这是最核心的结构化工作：

  • 法律名称识别： 用正则匹配"《XXX法》“、”《XXX条例》“、”《XXX司法解释》"等模式
  • 条款编号识别： “第X条”、“第X条之X”、“第X条第X款”、"第X项"等，用正则提取
  • 章节结构识别： “第一章”、“第二章”、“第一节”、"第二节"等，构建完整的目录树
  • 关联关系： 把条款编号和所在法律、章节关联起来，形成：法律名称 → 章 → 节 → 条 → 款 → 项的层级结构

六、存储结构

清洗后的数据存入MySQL，表结构大概是：

  • laws表：法律基本信息（名称、类型、生效日期、状态）
  • chapters表：章节信息（法律ID、章节编号、标题）
  • articles表：条款内容（法律ID、章节ID、条号、款号、全文、切片文本）
  • templates表：文书模板

这样，后续检索时既支持语义检索（向量检索），也支持精确检索（按法条编号查询）。

317. 法律文本怎么切片？章节、条、款、项的边界是通过规则、正则还是大模型识别？内容过长时怎么二次切分和设置overlap？

回答：

切片的核心策略：按法律文本的天然结构切分

法律文本和普通文章不一样，它有非常清晰的层级结构——章、节、条、款、项。所以我们不是用通用的固定长度切片，而是按结构切片，这样能最大程度保证每个切片是一个语义完整的单元。

一、边界识别：规则+正则为主，大模型为辅

规则和正则（主力）：

法律文本的格式规律性很强，用正则就能很准确地识别边界：

  • 条： 第[一二三四五六七八九十百千]+条 或 第\d+条
  • 款： 通常以换行和缩进区分，或者第X款的表述
  • 项： （[一二三四五六七八九十]+）、\d+、、[①-⑩]
  • 章： 第[一二三四五六七八九十]+章
  • 节： 第[一二三四五六七八九十]+节

这些正则的准确率在95%以上，因为法律文书的格式有严格规范。

大模型辅助（兜底）：

有少数法律文本格式不规范（比如旧版法规、OCR识别质量差的），正则匹配不上。这时我们用大模型做一次结构识别——把文本发给大模型，让它标注出"哪些是条、哪些是款、哪些是项"。不过大模型方案成本高、速度慢，只作为兜底方案。

二、切片粒度

我们以"条"为主要切片单元：

  • 一条完整的法律条文作为一个切片
  • 如果一条内容较短（100字以内），直接作为一个切片
  • 如果一条内容较长（超过500字），按"款"二次切分

三、二次切分和overlap设置

当一条内容过长时，按款切分后，每个子切片保留上下文的overlap：

原文：第X条（共800字，含5款）
切分结果：
  切片1：第X条 第1款 ~ 第2款 + 第3款前50字（overlap）
  切片2：第3款前50字（overlap）+ 第3款 ~ 第4款 + 第5款前50字（overlap）
  切片3：第5款前50字（overlap）+ 第5款

overlap长度的设置： 我们设为50-100字，具体取决于法律文本的复杂度。对法律条文来说，50字左右的overlap就足够覆盖上下文信息了，因为法律条文本身表述精炼，不需要像小说那样大段保留前文。

四、元数据保留

每个切片除了文本内容，还保留完整的元数据链条：

  • 来源法律名称（如《民法典》）
  • 所属章节（如"婚姻家庭编"）
  • 条号（如"第1046条"）
  • 款号、项号
  • 切片类型（全文、节选、分段）

这些元数据在后续检索和显示时非常有用——用户看到结果时，能直接知道"这个回答来自《民法典》第1046条"，可信度大幅提升。

318. MySQL和Milvus分别存什么？法律更新、修改或废止后，新旧版本数据怎么管理？

回答：

一、MySQL和Milvus的分工

存储 存储内容 用途
MySQL 原始法律文本、结构化元数据（法律名称、章、节、条、款、项、生效日期、状态）、切片文本、用户查询日志、标注数据 精确检索（按法条编号查）、数据管理、版本控制、日志分析
Milvus 文本切片的向量嵌入（1024维）、切片ID、元数据标签 语义相似度检索，支持Top-K召回

两者的关系：

MySQL是"数据源"，Milvus是"检索索引"。切片数据先写入MySQL，生成唯一ID，然后向量化后写入Milvus，关联同一个ID。检索时，Milvus返回Top-K的ID列表，再到MySQL查具体内容。

二、法律更新、修改或废止后的版本管理

法律是会变的——新法出台、旧法修订、司法解释更新。版本管理是我们非常重视的问题。

版本管理策略：

  1. 每条数据带版本号： 每条法律记录都有一个version字段，记录生效日期和版本号
  2. 软删除+历史保留： 法律废止或修改后，旧版本不删除，标为status='deprecated'，保留历史数据
  3. 新版本独立入库： 新法作为新记录入库，关联同一个法律ID但不同版本号

具体的数据变更流程：

法律废止/Case：
  MySQL：旧法律状态标记为'deprecated'，保留历史
  Milvus：对应的向量标记删除（不影响检索，但权重降低）

法律修订/Case：
  MySQL：新增一条修订版记录，版本号+1，生效日期更新
  Milvus：新增修订版的向量，旧版向量保留但标记为历史版本
  检索时：默认只检索最新生效版本，如果需要查历史版本，走单独接口

新法出台/Case：
  MySQL：新增法律记录
  Milvus：新增向量
  不需要动旧数据

三、检索时的版本控制

用户提问时，默认只检索status='active'且生效日期 <= 当前日期的数据。如果用户明确问"之前的XX法是怎么规定的"，则可以通过特殊的查询参数，检索历史版本。

四、数据一致性保障

MySQL和Milvus之间的数据一致性是个挑战。我们采用了双写+定期同步的策略：

  • 写入时：先写MySQL，成功后写Milvus
  • 如果Milvus写入失败，标记为"待同步"，定时任务补偿
  • 每天凌晨做一次全量对比，确保两者数据一致

319. 请介绍用户提问后的完整检索链路，包括Query Rewrite、MySQL精确检索、Milvus语义召回、结果合并和Reranker重排序

回答：

这是法律助手项目最核心的流程，我按顺序完整介绍一遍：

第一步：用户输入

用户输入一个自然语言问题，比如"离婚冷静期是多久？"

第二步：Query Rewrite（问题改写）

原始问题太口语化，直接检索效果不好。我们通过一个专门的Prompt，把问题改写成法律检索表达：

输入：离婚冷静期是多久？
输出：查询民法典关于离婚冷静期期限的规定

这样改写后，检索时匹配度更高。改写的原则是：不改变原始事实，只优化表达方式。

第三步：并行双路检索

改写后的query同时进入两条检索路径：

路径A：MySQL精确检索（关键词+结构化）

  • 从改写后的query中提取关键词（如"离婚冷静期"“民法典”）
  • 在MySQL中用全文索引搜索法律名称、章节标题、条款内容
  • 同时支持按法条编号精确查询（如果用户问了"民法典第1077条"）
  • 返回Top-10结果

路径B：Milvus语义检索（向量检索）

  • 用text-embedding-v3把query编码成1024维向量
  • 在Milvus中做向量相似度搜索（IVF_FLAT索引）
  • 返回Top-20结果

第四步：结果合并（RRF融合）

两路召回的结果用**RRF（Reciprocal Rank Fusion）**算法合并：

  • 每个chunk计算融合分：score = 1/(60 + rank_mysql) + 1/(60 + rank_milvus)
  • 在两路中都排在前面的chunk得分更高
  • 合并后取Top-30进入下一阶段

第五步：Reranker重排序

用bge-reranker-v2-m3交叉编码器，对Top-30的候选chunks逐一打分：

  • 把query和每个chunk拼接，输入模型
  • 输出一个相关性分数（0-1）
  • 按分数从高到低排序，取Top-5作为最终结果

第六步：答案生成

把Top-5的chunks拼接到Prompt中，加上原始问题，输入大模型生成答案：

  • 模型：Qwen-plus（云端）或 Qwen3-32B（本地部署）
  • Prompt中包含：用户问题、检索到的法条内容、以及"请基于以上法条回答，不要编造"的约束
  • 输出带引用标注的答案，用户可以看到每条回答对应的法条来源

第七步：结果展示

前端展示：

  • 最终答案（带法条引用）
  • 相关法条原文（可展开查看）
  • 答案可信度评分

整条链路的耗时优化：

  • 最初的链路耗时约1.5秒
  • 通过并行检索、Redis缓存热点query、Reranker并行推理等优化，降到约0.6秒
  • 检索响应速度提升了60%以上

320. Query Rewrite的Prompt怎么设计？如何把口语化问题转换成法律检索表达，同时不改变用户原始事实？

回答：

Query Rewrite（问题改写）是RAG检索链路中非常关键的一环，直接影响检索质量。我详细说说Prompt的设计思路：

一、核心原则

不改变原始事实： 这是底线。如果用户问"离婚要多久"，改写后不能变成"结婚要多久"，也不能添加不存在的条件。

优化检索表达： 口语化的问题往往省略了关键信息，或者用了模糊表达。改写要补全信息、明确化表达，使其更匹配法律文本的表述方式。

二、Prompt设计

你是一个法律检索助手，负责把用户的口语化问题改写成适合法律检索的查询语句。

要求：
1. 保持原始事实不变，不能添加、修改或删除用户问题中的关键信息
2. 把口语化表达转换成法律检索表达，使用法律术语
3. 如果用户提到了具体法条编号，保留并强调
4. 如果问题涉及多个方面，拆分成多个子查询
5. 输出格式：JSON

示例：
输入：离婚冷静期是多久？
输出：{"rewritten_query": "民法典关于离婚冷静期期限的规定", "query_type": "semantic", "keywords": ["离婚冷静期", "民法典"]}

输入：民法典第1077条说了什么？
输出：{"rewritten_query": "民法典第1077条 离婚冷静期", "query_type": "exact", "keywords": ["民法典", "第1077条", "离婚冷静期"]}

输入：公司拖欠工资三个月了怎么办？
输出：{"rewritten_query": "劳动合同法关于拖欠工资的维权规定", "query_type": "semantic", "keywords": ["拖欠工资", "劳动合同法", "维权"]}

三、关键设计点

1. 输出结构化

Prompt要求输出JSON格式，包含三个字段：

  • rewritten_query：改写后的检索语句
  • query_type：检索类型（semantic语义检索 / exact精确检索 / hybrid混合检索）
  • keywords：从问题中提取的关键词

这样后续的检索路由可以直接根据query_type做决策——精确检索走MySQL，语义检索走Milvus，混合检索走双路召回。

2. 示例引导

Prompt中给了3个典型示例，覆盖了不同场景：

  • 纯语义查询（离婚冷静期）
  • 精确法条查询（民法典第1077条）
  • 场景描述型查询（公司拖欠工资）

这些示例让大模型更快理解任务模式，提高改写质量。

3. 事实保护机制

在Prompt中明确要求"不改变用户原始事实"，并在示例中体现。但我们还加了一层校验——改写完成后，用规则对比改写前后是否保留了原始问题的关键实体（如法条编号、人名、金额等），如果发现实体丢失或变更，触发告警并降级使用原始问题。

四、实际效果

经过测试，加上Query Rewrite后，Top-5召回率从75%提升到了85%左右。主要原因是：

  • 口语化问题中的"这个"、“那个”、"啥"等模糊用词被替换成了具体法律术语
  • 省略的法律名称被补全（如"民法典"而不是"那个法"）
  • 检索query和法条文本的语义空间更接近
