291. 如果需要纯手写Agent，需要哪些核心模块

回答：

如果不用LangGraph、LangChain这些框架，纯手写一个Agent，需要以下几个核心模块：

一、感知模块（Perception）

负责接收和解析用户输入。包括：

  • 输入解析器：把用户自然语言转换成结构化指令
  • 意图识别器：判断用户想做什么（查政策、问法条、还是闲聊）
  • 上下文管理器：维护当前会话的历史对话，避免新问题丢失上下文

二、思维模块（Thinking / Reasoning）

这是Agent的"大脑"，负责决策。核心是：

  • LLM调用器： 封装对大模型的调用，支持流式输出、异步调用、重试机制
  • Prompt模板引擎： 管理不同场景的prompt模板，支持动态变量注入
  • 推理循环（ReAct Loop）： 实现"思考→行动→观察"的循环，让Agent能根据工具返回的结果动态调整下一步

三、工具模块（Tool System）

Agent需要能力去执行操作：

  • 工具注册中心： 管理所有可用的工具（查询数据库、调用API、发邮件等），包括工具的名称、描述、参数schema
  • 工具调度器： 根据LLM的决策，解析出要调用的工具和参数，执行并返回结果
  • 工具结果解析器： 把工具返回的原始结果（如JSON、数据库查询结果）转换成LLM能理解的文本

四、记忆模块（Memory）

让Agent能记住过去的事情：

  • 短期记忆： 当前会话的上下文，存在内存中（如一个列表）
  • 长期记忆： 跨会话的关键信息，存到外部存储（如Redis、向量数据库）
  • 记忆管理： 决定什么时候存、什么时候取、什么时候清理

五、状态管理模块（State Management）

管理Agent的运行时状态：

  • 当前处于哪个步骤
  • 已经完成了什么、还差什么
  • 异常状态的处理（重试、超时、回退）

六、安全模块（Safety）

  • 输入过滤：过滤恶意注入、敏感词
  • 输出审核：检查生成内容是否合规
  • 权限校验：工具调用前检查是否有权限

七、日志与监控模块

记录Agent的每次操作：输入、决策、工具调用、输出、异常。方便调试和审计。

292. 为什么选择LangGraph而非LangChain作为Agent框架，具体说明LangGraph的状态、对象、关系设计如何解决了项目中的实际问题

回答：

这个问题很深入，我结合政策补贴项目的实际场景来回答。

为什么不用LangChain？

LangChain的Agent模式是"一个Agent，一个工具列表，一个ReAct循环"。对于简单的工具调用场景（比如"查天气→查日历→收邮件"）够用，但对我们政策补贴系统这种多Agent、多步骤、有状态依赖的复杂流程来说，LangChain有几个硬伤：

  1. 状态管理薄弱： LangChain的Agent没有内置的状态共享机制，多个Agent之间传数据全靠"前面Agent的输出塞进后面Agent的输入"，非常脆弱
  2. 控制流有限： LangChain的Agent是线性链式的，不支持分支、条件跳转、并行、循环
  3. 没有持久化： 如果流程中断（比如等用户输入），无法恢复，只能重新开始

LangGraph如何解决实际问题：

一、状态（State）设计解决了"数据怎么在多个Agent之间流转"的问题

在LangGraph中，我们用TypedDict定义了一个全局State：

class PolicyMatchState(TypedDict):
    user_query: str              # 用户原始问题
    enterprise_profile: dict     # 企业画像采集结果
    matched_policies: list       # 政策检索结果列表
    eligibility_results: list    # 条件审核结果
    generated_materials: list    # 材料生成结果
    error_info: str              # 异常信息
    flow_status: str             # 流程状态（进行中/完成/异常）

实际效果： 每个Agent只关心State中的特定字段，企业画像Agent写enterprise_profile，政策检索Agent读enterprise_profile并写matched_policies，数据流转清晰可控，不会出现"数据在哪个Agent手里"的问题。

二、节点（Node）设计解决了"每个Agent做什么"的问题

每个Agent对应一个Node，是一个纯函数：输入是当前State，输出是更新后的State。比如条件审核Agent：

def eligibility_check_node(state: PolicyMatchState) -> dict:
    profile = state["enterprise_profile"]
    policies = state["matched_policies"]
    results = check_eligibility(profile, policies)  # 核心逻辑
    return {"eligibility_results": results, "flow_status": "审核完成"}

实际效果： 每个Agent职责单一，独立开发和测试，互不干扰。

三、边（Edge）设计解决了"流程怎么走"的问题

条件边让流程控制变得灵活：

def router(state: PolicyMatchState) -> str:
    if state["flow_status"] == "异常":
        return "异常处理节点"
    elif not state["enterprise_profile"]:
        return "企业画像采集节点"  # 回溯
    else:
        return "结果生成节点"

实际效果： 实现了回溯重试（数据不完整→重新采集）、条件分支（符合条件→结果展示，不符合→替代方案）、并行执行（多个Agent同时跑）。这些在LangChain中几乎无法实现。

293. 清洗和切分环节的具体操作方法是什么

回答：

以法律助手项目为例，知识库构建中的清洗和切分是RAG质量的关键。

一、数据清洗（Data Cleaning）

清洗的目的是把原始PDF/Word/Excel文档中的"噪音"去掉，只保留有用的文本内容。具体方法：

第一步：格式归一化。 统一文档编码为UTF-8，去掉多余的空白字符、不可见字符，统一换行符。

第二步：去噪。 去掉以下内容：

  • 页眉页脚（页码、公司名称、文档标题等，通过MinerU的布局分析识别）
  • 水印文字（半透明的"机密"、"草稿"等标记）
  • 脚注和尾注（法律文档中很多，但不属于正文内容）
  • 无关的元数据（如文档创建时间、作者信息）

第三步：内容去重。 法律文档中经常出现重复引用（比如同一条法条在不同文档中反复出现），通过SimHash或MinHash做近似去重，避免知识库中出现大量冗余内容。

二、文本切分（Chunking）

清洗完的文本需要切分成合适的切片，方便检索。我们用了分层切片策略：

第一层：基于文档结构的粗切分。 根据文档的标题层级（H1、H2、H3）做切分。比如一份法律文档，按"章→节→条"的结构切分，每个"条"作为一个独立切片的基础单元。这样切出来的切片语义完整，不会把一个法条拦腰切断。

第二层：基于token大小的细切分。 如果某个"条"的内容太长（超过500 tokens），按段落进一步切分，同时保留段落之间的语义关联（相邻切片有重叠，重叠约50 tokens）。

第三层：父子切片策略。 每个子切片（小段落）关联一个父切片（整个法条或章节），检索时命中子切片，但可以回溯到父切片获取更完整的上下文。

具体参数：

  • 切片大小：256-512 tokens（根据内容类型调整）
  • 重叠大小：50 tokens
  • 切片策略：按标题层级优先，按句号断句为辅助

实际效果： 这套清洗+切分策略，让法条召回率从68%提升到了94%。

294. 问题改写是怎么处理的

回答：

问题改写（Query Rewriting / Query Transformation）在RAG系统中非常重要，因为用户的问题往往不够精确，直接拿去检索效果不好。我们的做法分几种策略：

策略一：补充上下文

对于多轮对话中的追问，用户的问题通常是不完整的。比如用户先问"劳动合同到期不续签有赔偿吗"，然后追问"那需要提前通知吗"，这里的"那"指的是"劳动合同到期不续签"这个场景。我们需要把追问补充完整：“劳动合同到期不续签需要提前通知吗”。

实现方式：拼接上一轮的用户问题和系统回答，加上当前问题，让大模型生成一个完整的、独立的问题。

策略二：去口语化

用户经常用口语化的表达，比如"公司不给签合同咋办"，需要改写成更规范的表述：“用人单位未与劳动者签订劳动合同，劳动者有哪些维权途径”。这样改写后，检索效果更好，因为知识库中的文档通常是规范表述。

实现方式：用一个小模型（或者直接让大模型）做"口语→书面语"的转换，作为检索前的一个预处理步骤。

策略三：关键词提取与扩展

对于比较模糊的问题，提取关键实体并扩展同义词。比如用户问"深圳有什么补贴"，提取关键词"深圳"+“补贴”，扩展为"深圳市"、“深圳市补贴政策”、"深圳企业补贴"等，用这些扩展后的关键词去做检索，召回率更高。

策略四：多角度改写

同一个问题从不同角度改写，做多路检索。比如"劳动仲裁需要多久"改写为：

  • “劳动仲裁的审理期限”
  • “劳动仲裁从申请到出结果需要多长时间”
  • “劳动争议仲裁的时效规定”

然后每个改写后的查询分别去检索，取并集。

技术实现： 我们在代码中实现了一个QueryRewriter模块，接收原始问题和历史上下文，调用大模型生成改写后的查询。改写本身也是一个轻量级的大模型调用，耗时很短（约200-500ms），但带来的检索效果提升很明显。

295. 检测到错误数据后，知识库如何实现更新以避免重复错误

回答：

这是个很好的问题，在实际生产环境中非常重要。我们在法律助手项目中，知识库的错误数据检测和更新机制是闭环的：

一、错误检测机制

错误数据的来源有三种：

  • 用户反馈： 用户对回答不满意，点击"答案不准确"按钮，系统记录该答案对应的检索切片
  • 自动化评测： 定期用测试集跑评测，如果某个切片被频繁命中但准确率低，标记为可疑
  • 人工审核： 运营人员定期抽查知识库内容，发现错误直接标记

二、错误标记与隔离

检测到错误数据后，不会直接删除（因为可能还有其他用户正在使用），而是先软删除：

  • 给该切片打一个"已标记"或"低可信度"标签
  • 在检索时，降低该切片的权重，或者直接排除标记为"已标记"的切片
  • 不影响其他正常切片的检索

三、修正与验证

运营人员收到错误标记后，去核查原始文档，如果是解析错误（比如PDF解析时把法条内容弄错了），重新解析并替换该切片；如果是文档本身的问题（比如引用了已废止的法条），则更新源文档，重新入库。

四、避免重复错误的机制

这里的关键是错误指纹：

  • 每条错误数据入库时，生成一个"错误指纹"（基于切片内容的Hash）
  • 修正后的新切片入库时，先检查该指纹，如果和之前错误数据的指纹匹配，说明是同一个问题的修正版本，不会重复标记
  • 如果后续有新的数据入库，且内容和之前被标记的错误数据相似度超过阈值，自动触发人工审核，而不是直接入库

五、更新后的回测

修正完成后，自动触发一次回测：用之前导致这个错误的用户问题重新测试，确保修正后的检索结果正确。如果回测通过，解除该切片的软删除状态。

296. 请介绍你在Docker、本地化部署等工程化环节的实际经验

回答：

在两个项目中，工程化部署的经验主要分几个方面：

一、Docker容器化

法律助手项目的部署架构：

  • 前端：Nginx + Vue3静态文件，打包成单个镜像
  • 后端：FastAPI服务，打包成Python镜像（基于python:3.10-slim，减少体积）
  • 向量数据库：Milvus用官方镜像，通过Docker Compose编排
  • 缓存：Redis官方镜像
  • 图数据库：Neo4j官方镜像

Docker Compose配置的核心是服务编排和网络互通：

# 核心服务
services:
  backend:
    build: ./backend
    ports: - "8000:8000"
    depends_on: [milvus, redis, neo4j]
    environment:
      - MILVUS_HOST=milvus
      - REDIS_HOST=redis
  milvus:
    image: milvusdb/milvus:v2.3.0
  redis:
    image: redis:7-alpine

二、本地化部署

政策补贴项目要求完全本地化部署，不能依赖外网API。所以：

  • 大模型用Qwen3-32B本地部署，通过vLLM提供推理服务
  • Embedding模型也本地部署（text-embedding-v3的本地版本或BGE-large-zh）
  • 所有数据库（Milvus、Neo4j、Redis、PostgreSQL）都在内网
  • 用Docker Compose一键启动，不需要外网连接

三、环境管理

  • 开发、测试、生产三套环境，用Docker Compose的override文件区分配置
  • 敏感信息（数据库密码、API Key）通过环境变量注入，不写死在镜像中
  • 日志统一收集到ELK或Loki，方便排查问题

四、更新部署

  • 后端代码更新：重新build backend镜像，docker-compose up -d backend，滚动更新
  • 知识库更新：不需要重启服务，通过API接口增量入库
  • 模型更新：替换vLLM加载的模型路径，重启推理服务

五、遇到的坑

  • Milvus在Docker中默认使用内存做索引，内存不够时容易OOM，需要配置swap
  • 多个容器之间网络通信要处理好，特别是Milvus的standalone模式需要配置正确的端口映射
  • 本地化部署时，没有GPU的情况下，用CPU推理Qwen3-32B非常慢，需要量化（4-bit量化可以降到16G显存以内）

297. SFT监督微调的逻辑

回答：

SFT（Supervised Fine-Tuning，监督微调）是让预训练模型适配特定任务的核心方法，我以法律助手项目中对Qwen3-32B的微调为例说明：

一、SFT的核心逻辑是什么？

预训练模型学的是"下一个词是什么"的语言规律，但不知道"如何回答用户的问题"。SFT做的就是用高质量的问答对，让模型学会"用户问什么，我该怎么回答"这个模式。

通俗理解： 预训练模型像一个读过万卷书的人，知识丰富但不知道怎么回答问题。SFT就是教他"别人问问题的时候，你要这样回答"。

二、SFT的训练方式

SFT并不是从头训练整个模型，而是在预训练模型的基础上，用监督数据做有监督的损失计算：

  1. 输入：用户问题（作为prompt）
  2. 输出：期望的答案（作为label）
  3. 损失计算：只计算模型在"答案部分"的交叉熵损失，prompt部分的损失被mask掉
  4. 反向传播更新参数
# 伪代码逻辑
inputs = tokenizer("[用户问题]")
labels = tokenizer("[期望答案]")
# 只有答案部分参与损失计算
loss = cross_entropy(model_output, labels, ignore_index=prompt_tokens)
loss.backward()
optimizer.step()

三、SFT的关键参数

在法律助手项目中，QLoRA微调的关键参数：

  • LoRA秩（r）：16
  • LoRA alpha：32
  • 目标模块：q_proj, v_proj（只微调注意力层的Q和V矩阵）
  • 学习率：2e-4
  • 批次大小：4（因为QLoRA节省了显存，可以用相对大的batch）
  • 训练轮数：3个epoch
  • 优化器：AdamW

四、SFT的注意事项

  • 过拟合风险： 数据量不大（2万条）时，3个epoch之后可能过拟合，需要通过验证集loss监控
  • 灾难性遗忘： SFT可能让模型忘记预训练时学到的通用知识，所以需要保留一部分通用数据做混合训练
  • 数据质量>数据数量： 1万条高质量数据的效果远好于10万条低质量数据，宁可少但要精

298. Agent和Loop的介绍

回答：

一、Agent是什么？

Agent是一个智能体，它能够自主地感知环境、做出决策、执行行动来完成目标。在AI领域，Agent通常指"大模型+工具+记忆+规划能力"的组合体。

Agent的核心能力：

  • 理解： 理解用户意图和当前状态
  • 推理： 分析问题，制定计划
  • 执行： 调用工具，获取信息
  • 反思： 根据结果调整策略

二、Loop（循环）是什么？

Loop指的是Agent的推理-行动循环，也叫ReAct（Reasoning + Acting）模式。它的工作流程是：

1. 思考（Thought）：Agent分析当前状态，决定下一步做什么
2. 行动（Action）：调用一个工具或生成一段回答
3. 观察（Observation）：获取工具返回的结果或环境的反馈
4. 重复：根据观察结果，继续思考下一步

这个循环会一直持续，直到Agent认为任务完成，或者达到最大轮次限制。

三、为什么要用Loop？

不循环的Agent就像"问一句答一句"——用户说"查一下政策"，Agent直接去查，查完就结束。但如果第一次查到的结果不完整，或者需要进一步筛选，它就不知道怎么办了。

有循环的Agent可以做到：

  • 第一次查政策→发现结果太多→决定再加一个条件筛选→再查一次→得到精确结果
  • 第一次工具调用失败→自动重试→成功
  • 根据工具返回的数据，动态调整下一步行动

四、Loop的实现方式

在LangGraph中，Loop是通过有环图（Cyclic Graph） 实现的。节点A执行完后，通过条件边判断，如果条件不满足，就回到节点A自身继续执行，形成一个循环。

# 伪代码：ReAct循环
def agent_loop(state):
    thought = llm.think(state)  # 思考
    if thought.decided_to_stop:  # 决定停止
        return {"final_answer": thought.answer}
    action = thought.action       # 行动
    observation = execute_tool(action)  # 观察
    return {"observation": observation}  # 继续循环

五、实际项目中的应用

在政策补贴系统中，条件审核Agent内部就有Loop：它先审核一个政策，如果发现数据不完整，就触发"补全数据"的循环，直到数据完整才继续往下走，而不是直接报错。

299. 决策模型的选型理由

回答：

在政策补贴系统中，决策模型选的是 Qwen3-32B，选型理由从几个维度考虑：

一、任务需求匹配度

政策补贴匹配的核心任务包括：

  • 理解复杂的政策文本（中文自然语言理解）
  • 做条件判断（企业数据 vs 政策条件的匹配）
  • 多步骤推理（需要理解"如果A且B，则C，但D情况例外"这类逻辑）
  • 工具调用和结构化输出

Qwen3-32B在中文理解能力上非常强，特别是对长文本、复杂逻辑的处理能力，满足这些需求。

二、本地化部署约束

政策补贴项目要求完全本地化部署，不能依赖外网API。所以模型必须能在本地部署运行。Qwen3-32B用4-bit量化后，显存占用约16-18G，可以用一张24G的消费级显卡（如RTX 4090）运行，部署成本可控。

三、上下文长度

Qwen3-32B原生支持128K上下文，对于政策匹配场景足够。政策文档虽然长，但检索阶段已经做了切片，输入到模型的是经过筛选的最相关部分，不会超过128K。

四、对比其他模型的考虑

  • GPT-4/Claude： 效果更好，但无法本地化部署，政策补贴项目涉及企业敏感数据，不能走外网
  • 开源模型（如Llama-3-70B）： 70B参数本地部署成本太高，需要多卡，而且中文能力不如Qwen
  • DeepSeek： 中文能力也好，但当时DeepSeek的本地部署工具链（vLLM支持、量化工具）不如Qwen成熟
  • Qwen-72B： 参数更大，效果更好，但部署成本太高，性价比不如32B

五、微调适配性

Qwen3-32B对QLoRA微调的支持很好，huggingface的transformers库和peft库都原生支持，微调门槛低。我们在2万条数据上微调了3个epoch，效果提升明显。

总结： Qwen3-32B是在"效果、部署成本、中文能力、可微调性"四个维度上平衡后的最优选择。

300. 记忆的留存时间怎么设置

回答：

在政策补贴系统中，记忆的留存时间分不同层级来设置，不是一刀切的：

一、短期记忆（会话内）

留存时间： 会话结束后立即清除

存储内容： 当前会话的对话历史、Agent的执行状态、临时的中间结果

实现方式： 存在内存中（Python字典或LangGraph的State），会话结束后释放。如果用户30分钟内无操作，会话自动过期，内存释放。

二、中期记忆（用户维度）

留存时间： 7天

存储内容： 用户在当前会话中的偏好信息，比如：

  • 用户偏好的回答风格（详细模式还是简洁模式）
  • 用户最近查询过的政策类型
  • 用户上次操作到的步骤（比如上次匹配做到一半，这次可以继续）

实现方式： 存在Redis中，设置TTL为7天。每次用户有新的交互时，刷新TTL。如果用户7天没有登录，记忆自动过期。

三、长期记忆（企业维度）

留存时间： 永久保存（除非企业主动删除或数据更新）

存储内容：

  • 企业画像数据（行业、规模、资质等）
  • 企业的历史申报记录
  • 企业的匹配偏好（哪些政策类型更关注）
  • 用户的历史反馈（哪些回答被标记为有用/无用）

实现方式： 存在Neo4j（图数据库）和PostgreSQL（关系数据库）中，不作为临时缓存，而是持久化存储。数据更新时（比如企业信息变更）手动触发更新，而不是自动过期。

四、记忆管理的决策逻辑

设置留存时间时，我们遵循几个原则：

  1. 越重要的记忆，留存越久： 企业画像数据永久保存，用户的临时偏好7天过期
  2. 越隐私的记忆，留存越短： 用户的对话历史（可能包含敏感信息）只保留在会话期内
  3. 越容易获取的信息，留存越短： 比如政策检索结果，随时可以重新检索，不需要长期缓存
  4. 用户可控： 用户可以在设置中手动清除记忆（“忘记我的偏好”、“重置对话”）

一个实际例子： 某企业用户上周查询了"高新技术企业认定"相关的政策，系统记住了这个偏好（中期记忆，7天）。这周用户再次登录，系统会自动优先展示高新技术企业相关的最新政策，而不需要用户重新描述。但如果用户连续两周没登录，这个偏好就过期了，系统重新以默认方式展示。
