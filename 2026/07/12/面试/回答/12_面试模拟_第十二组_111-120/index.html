面试模拟 - 第十二组（111-120题）

基于简历项目经历，模拟面试回答

1. 超出上下文后该怎么处理？

回答：

上下文超出窗口是大模型应用中的常见问题，我在政策补贴系统中遇到过多次。

问题场景： 政策补贴系统需要处理企业信息、政策文档、匹配结果、历史对话等，很容易超过模型的上下文窗口（比如Qwen3-32B的32K tokens）。

处理策略：

1. 上下文压缩

  • 摘要压缩：把长文本用LLM压缩成摘要，保留关键信息
  • 结构化提取：从非结构化文本中提取关键字段，用JSON格式存储
  • 去重合并：重复信息只保留一份

我在政策补贴系统中，把企业信息压缩成"行业、规模、资质、地区"等结构化字段，从2000字压缩到200字。

2. 分层存储

  • 短期记忆：当前对话上下文，用完即丢
  • 长期记忆：关键信息存Redis，需要时再读取
  • 外部存储：政策文档、企业画像存数据库，按需检索

3. 滑动窗口
只保留最近N轮对话，早期对话压缩成摘要或丢弃。

4. 按需检索
不是所有信息都需要在上下文里。比如政策详情，Agent知道政策ID就行，需要时再从数据库检索。

5. 技术实现
我在项目中用Redis做状态存储：

  • 每个Agent处理完，把结果存Redis，key是任务ID
  • 下一个Agent从Redis读取，而不是从上下文传递
  • 最终生成报告时，再汇总所有中间结果

实际效果： 通过状态压缩+Redis存储，上下文长度控制在3000字以内，模型处理稳定。

2. 为什么vllm推理效率高？

回答：

vLLM（Virtual Large Language Model）推理效率高，主要是因为它解决了LLM推理中的两个核心瓶颈：内存管理和计算调度。

核心技术：PagedAttention

传统推理中，KV Cache（注意力计算的中间结果）需要连续内存，容易造成内存碎片和浪费。vLLM的PagedAttention把KV Cache分成固定大小的"页"，按需分配，就像操作系统的虚拟内存一样。

优势：

  1. 内存利用率高：不需要连续内存，减少碎片，可以服务更多并发请求
  2. 动态分配：根据序列长度动态分配内存，短序列不浪费空间
  3. 高效调度：支持连续批处理（Continuous Batching），不用等所有请求都完成才处理下一批

其他优化：

  1. Tensor Parallelism：张量并行，把模型切分到多个GPU上
  2. CUDA优化：底层用CUDA核函数优化注意力计算
  3. 量化支持：支持INT8/INT4量化，减少计算量

我在项目中的应用： 法律助手和政策补贴系统都用vLLM部署Qwen3-32B。部署后，推理速度提升明显，单卡可以支持更多并发请求。

对比传统推理： 传统HuggingFace推理，内存管理粗糙，容易OOM；vLLM通过PagedAttention，同样的GPU可以服务2-3倍的并发。

3. 你怎么确保你训练数据的质量？

回答：

训练数据质量直接影响模型效果，我在法律助手项目的QLoRA微调中非常重视数据质量。

数据质量保障方法：

1. 数据来源把控

  • 权威来源：法律条文从官方法律数据库获取，政策文档从政府官网下载
  • 版本控制：确保数据是最新版本，法律法规会更新

2. 数据清洗

  • 去重：重复数据会影响训练效果，用哈希或语义相似度去重
  • 去噪：删除乱码、格式错误、无关内容
  • 标准化：统一格式，比如日期、数字、法律条款编号

3. 数据标注

  • 人工校验：关键数据人工抽查，确保准确
  • 一致性检查：同一问题不同人标注的结果应该一致
  • 边界案例：特别关注容易出错的边界情况

4. 数据分布

  • 类别均衡：不同类型的法律问题都要有，不能偏科
  • 难度分布：简单、中等、困难的问题都要有
  • 覆盖全面：劳动法、合同法、知识产权法等都要覆盖

5. 数据验证

  • 交叉验证：用留出的数据验证模型效果
  • A/B测试：新旧数据集训练的模型对比
  • 人工评估：随机抽样，人工判断回答质量

我在项目中的实践： 法律助手微调时，我准备了5000条高质量的问答对，每条都经过人工校验。训练后，模型在法律问答任务上的准确率提升了15%。

核心原则： 数据质量 > 数据数量。1000条高质量数据，比10000条低质量数据效果好。

4. langgraph的记忆是怎么管理的？

回答：

LangGraph的记忆管理是多Agent协作的关键，我在政策补贴系统中用LangGraph实现了状态管理。

LangGraph的记忆机制：

1. 状态图（State Graph）
LangGraph的核心是状态图，每个节点处理完后更新状态，状态在节点间传递。状态可以用TypedDict定义，包含所有需要的信息。

2. 状态存储

  • 内存存储：默认状态存在内存中，适合短期任务
  • 持久化存储：可以配置Redis或数据库，支持长期记忆
  • 检查点（Checkpoint）：支持状态快照，可以回溯和恢复

3. 记忆类型

  • 短期记忆：当前对话的上下文，任务完成就丢弃
  • 长期记忆：关键信息存Redis，跨对话共享
  • 工作记忆：当前任务的中间状态，任务完成后压缩存储

我在项目中的实现：

政策补贴系统用LangGraph管理多Agent协作，状态定义如下：

  • user_input: 用户输入
  • company_info: 企业信息（结构化）
  • matched_policies: 匹配的政策列表
  • nalysis_result: 分析结果
  • inal_report: 最终报告

状态流转：

  1. 意图识别Agent更新user_input
  2. 企业画像Agent更新company_info
  3. 政策匹配Agent更新matched_policies
  4. 报告生成Agent更新 inal_report

记忆压缩：
中间状态处理完后，压缩成摘要存Redis，避免状态膨胀。

实际效果： 通过LangGraph的状态管理，多Agent协作顺畅，上下文长度可控，任务完成率高。

5. 语义切片，父子切片递归切片的适用于什么业务场景？

回答：

切片策略是RAG知识库构建的核心，不同切片方法适用于不同场景。

语义切片：

  • 原理：根据语义边界切分，比如按段落、按主题
  • 适用场景：文档结构清晰、段落独立性强的场景
  • 优点：每个切片语义完整，检索准确率高
  • 缺点：切片大小不均匀，可能有长有短

我在法律助手中的应用： 法律条文适合语义切片，每条法律是一个独立的切片，语义完整。

父子切片：

  • 原理：大块作为父节点，小块作为子节点，检索时先找子节点，再关联父节点
  • 适用场景：需要上下文的场景，比如问答需要引用原文段落
  • 优点：检索精准（子节点），同时有上下文（父节点）
  • 缺点：存储开销大，需要维护父子关系

我在政策补贴系统中的应用： 政策文档用父子切片，政策大标题是父节点，具体条款是子节点。检索时先找到相关条款，再返回整个政策上下文。

递归切片：

  • 原理：按层级递归切分，先按大标题，再按小标题，最后按段落
  • 适用场景：结构化文档，比如技术文档、法律文档
  • 优点：保留文档层级结构，切片有明确的归属
  • 缺点：实现复杂，需要解析文档结构

我在项目中的实践： 法律助手用递归切片，先按"编-章-节"切分，再按条款切分。这样每个切片都有明确的归属，检索时可以定位到具体条款。

选择原则：

  1. 文档结构清晰→递归切片
  2. 段落独立性强→语义切片
  3. 需要上下文→父子切片
  4. 混合场景→组合使用

6. 粗排和精排的区别是什么？

回答：

粗排和精排是信息检索的两个阶段，我在法律助手项目中实现了完整的检索流程。

粗排（First Stage Ranking）：

  • 目的：从海量文档中快速筛选出候选集
  • 方法：向量检索、BM25关键词检索
  • 特点：速度快、召回率高、精度一般
  • 数量：从10万文档中筛选出100-200个候选

精排（Re-ranking）：

  • 目的：对候选集精细排序，选出最相关的
  • 方法：交叉编码器（Cross-Encoder）、LLM打分
  • 特点：速度慢、精度高
  • 数量：从100-200个候选中选出Top 5-10

我在项目中的实现：

法律助手用两阶段检索：

  1. 粗排阶段：

    • 向量检索：用Milvus的HNSW索引，召回Top 100
    • BM25检索：用Elasticsearch，召回Top 100
    • 合并去重：得到150个候选

  2. 精排阶段：

    • 用交叉编码器对150个候选重新打分
    • 取Top 5作为最终结果

为什么需要两阶段：

  1. 效率考虑：粗排速度快，可以处理海量数据；精排精度高，但速度慢，只处理候选集
  2. 效果考虑：粗排保证召回率，精排保证准确率
  3. 成本考虑：精排模型计算量大，不能对所有文档都做精排

实际效果： 法律助手通过粗排+精排，召回率从68%提升到94%，准确率也大幅提升。

7. 对一个多模态知识库，处理图标表格公式怎么实现？

回答：

多模态知识库是RAG的难点，我在法律助手项目中处理过PDF中的表格和公式。

图表处理：

  1. 图表识别：用OCR模型（如MinerU）识别图表中的文字
  2. 图表理解：用多模态大模型（如GPT-4V）理解图表内容
  3. 结构化存储：把图表转换成结构化数据（JSON或表格）

表格处理：

  1. 表格检测：用目标检测模型定位表格区域
  2. 表格识别：用OCR识别表格中的文字
  3. 表格解析：把表格转换成结构化格式（行列对应）

公式处理：

  1. 公式检测：用目标检测模型定位公式区域
  2. 公式识别：用LaTeX识别模型（如Mathpix）把公式转换成LaTeX格式
  3. 公式存储：LaTeX格式存储，支持语义检索

我在项目中的实践：

法律助手用MinerU处理PDF：

  1. PDF解析：MinerU自动识别PDF中的文字、表格、图片
  2. 内容提取：分别提取文字、表格、公式
  3. 结构化存储：文字按段落切片，表格按行列存储，公式用LaTeX存储
  4. 索引构建：文字用向量索引，表格用关键词索引，公式用语义索引

技术栈：

  • MinerU：PDF解析和OCR
  • 多模态大模型：图表理解
  • 向量数据库：存储文本向量
  • 关系数据库：存储结构化表格

挑战和解决：

  1. 表格跨页：用MinerU的跨页表格合并功能
  2. 公式识别准确率：用多个OCR模型交叉验证
  3. 图表语义理解：用大模型辅助理解图表含义

实际效果： 法律助手的多模态处理，表格识别准确率95%以上，公式识别准确率90%以上。

8. 工具调用返回错误，怎么让大模型理解到？

回答：

工具调用错误处理是Agent系统的关键，我在政策补贴系统中实现了完善的错误处理机制。

错误类型：

  1. 参数错误：调用工具时参数格式错误
  2. 执行错误：工具执行过程中出错（如网络超时、数据库连接失败）
  3. 结果错误：工具返回的结果不符合预期

让大模型理解错误的方法：

1. 结构化错误信息
把错误信息格式化，让大模型容易理解：

json
{
  "status": "error",
  "error_type": "timeout",
  "message": "政策检索超时，请重试",
  "suggestion": "可以尝试简化查询条件"
}

2. 错误分类和提示
不同错误类型给大模型不同的提示：

  • 参数错误→提示正确的参数格式
  • 执行错误→建议重试或换方法
  • 结果错误→提示检查输入或换个工具

3. 重试机制
大模型可以根据错误信息决定是否重试：

  • 网络超时→重试
  • 参数错误→修改参数后重试
  • 逻辑错误→换工具或换策略

我在项目中的实现：

政策补贴系统的工具调用错误处理：

  1. 错误捕获：每个工具调用都用try-catch包装
  2. 错误格式化：把错误转换成结构化信息
  3. 错误传递：把错误信息传给大模型
  4. 智能决策：大模型根据错误类型决定下一步

实际案例：
政策检索工具超时，大模型收到错误信息后，决定：

  1. 先用缓存的政策数据返回部分结果
  2. 后台异步重试检索
  3. 告诉用户"正在查询，请稍候"

核心原则： 错误信息要结构化、可理解、可操作，让大模型能做出正确决策。

9. 如果调用工具用的json，调用大模型不能输出准确的json，怎么兜底？

回答：

大模型输出JSON不准确是常见问题，我在项目中遇到过多次，有完善的兜底策略。

问题场景：
大模型输出的JSON可能有以下问题：

  1. 格式错误：缺少引号、括号不匹配
  2. 字段缺失：缺少必要字段
  3. 类型错误：字符串写成数字，数组写成对象
  4. 内容错误：字段值不符合预期

兜底策略：

1. JSON解析兜底

python
try:
    result = json.loads(llm_output)
except json.JSONDecodeError:
    # 尝试修复常见错误
    result = fix_json(llm_output)

2. 字段验证和补全

python
required_fields = ["tool_name", "parameters"]
for field in required_fields:
    if field not in result:
        result[field] = default_value

3. 类型转换

python
if isinstance(result["parameters"], str):
    result["parameters"] = json.loads(result["parameters"])

4. 多次重试
如果JSON解析失败，让大模型重新生成，最多重试3次。

5. 降级处理
如果多次重试都失败，用规则引擎兜底，根据用户输入直接调用工具。

我在项目中的实现：

政策补贴系统的工具调用：

  1. Prompt优化：在Prompt中明确JSON格式要求，给示例
  2. 输出验证：用Pydantic模型验证输出格式
  3. 错误修复：用正则表达式修复常见JSON错误
  4. 重试机制：最多重试3次，每次重试都优化Prompt
  5. 降级方案：如果JSON始终不对，用关键词匹配直接调用工具

实际效果： 通过多层兜底，工具调用成功率从85%提升到98%。

核心原则： 不要完全依赖大模型输出，要有验证、修复、降级的完整链路。

10. agent如何结合mcp和skill？如何保证自建的mcp开发？

回答：

MCP（Model Context Protocol）和Skill是Agent能力扩展的两种方式，我在项目中都有实践。

MCP和Skill的区别：

MCP：

  • 定义：标准化的工具调用协议，定义了工具的接口规范
  • 特点：跨模型、跨框架通用，一次开发多处使用
  • 适用场景：通用工具，如数据库查询、API调用、文件操作

Skill：

  • 定义：特定领域的技能包，包含工具、Prompt、工作流
  • 特点：领域专用，包含完整的业务逻辑
  • 适用场景：特定业务，如法律查询、政策匹配

如何结合：

  1. MCP提供基础能力：数据库查询、API调用、文件操作等用MCP实现
  2. Skill封装业务逻辑：把多个MCP工具组合成业务流程，加上Prompt和工作流
  3. Agent调用Skill：Agent根据任务选择合适的Skill执行

我在项目中的实践：

政策补贴系统的架构：

  • MCP层：数据库查询MCP、政策检索MCP、企业画像MCP
  • Skill层：政策匹配Skill（调用多个MCP）、报告生成Skill
  • Agent层：根据用户意图选择Skill执行

如何保证自建MCP开发质量：

  1. 接口规范：严格遵循MCP协议，定义清晰的输入输出
  2. 测试覆盖：每个MCP工具都要有单元测试、集成测试
  3. 文档完善：每个工具的参数、返回值、错误码都要文档化
  4. 版本管理：MCP工具要有版本号，支持平滑升级
  5. 监控告警：监控MCP调用成功率、延迟、错误率

技术实现：

  • MCP用Python实现，FastAPI提供HTTP接口
  • 用Pydantic做参数验证
  • 用Redis做缓存，提升性能
  • 用Docker容器化部署

实际效果： 通过MCP+Skill架构，系统扩展性强，新功能开发快，维护成本低。
